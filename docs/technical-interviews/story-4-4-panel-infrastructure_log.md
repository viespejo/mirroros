## DEC-030
- **Question**: Through which channels are the panels reached, and where does their IPC live? (seed Q3, remainder of Q4)
- **Context/Nuances**: Omarchy 4.5 reaches panels through three channels. (1) Native `qs ipc`: `ShellIpc` is an `IpcHandler`, but each per-monitor bar instance declares the same target and Quickshell answers with the first live handler, not the focused monitor's. (2) Its own socket (`SocketServer` in `shell.qml`, `omarchy-shell` CLI, `IpcRegistry`, requires `OMARCHY_PATH`), added in upstream commit `c231097` for performance: a `qs ipc` client costs ~45 ms per call versus ~5 ms for `socat`; `ping` went from ~61 ms to 13-18 ms and `omarchy-osd` from ~77 ms to ~36 ms. Omarchy needs it because much user-visible interaction is Bash `omarchy-*` scripts calling the shell (56 files in `v4.5.0`): OSD on auto-repeating volume/brightness keys, theme switching with a polling loop, toggles followed by bar refreshes, idle lock queries. (3) Hyprland global shortcuts, the actual key path: `o.bind(..., { panel = "omarchy.audio" })` becomes `hl.dsp.global("omarchy:panel.omarchy.audio")`, received by a native Quickshell `GlobalShortcut`; no process is spawned, and `shell.toggle` → `summonBarWidget` → `findPanelWidget` → `BarModel.pickPanelSlot` opens the focused monitor's panel. In 4.5 volume and brightness keys are also handled in-shell through `GlobalShortcut`. MirrorOS today: every shell binding uses `exec_cmd("qs ipc -p … call …")` (one client per press); there is no `GlobalShortcut`; there is a single `Bar` object (in `shell.qml`) with per-screen `Variants` inside, a `moduleSlots` registry and a shared `activePopout`. Copying only channel 1 (as the prototype did) would lose focused-monitor routing, spawn-free key presses and positional panel summoning. `GlobalShortcut` and the `global` dispatcher are native Quickshell and Hyprland, not Omarchy coupling; only the socket and `omarchy-shell` are Omarchy-specific.
- **User Response**: Approved after reviewing why Omarchy needs the socket.
- **Decision**: Panel key bindings use a native Quickshell `GlobalShortcut` (`appid: "mirroros"`), declared once in the shell, triggered from Hyprland with `hl.dsp.global("mirroros:panel.<name>")`. Focused-monitor routing is ported into the adapted `bar/Bar.qml` (`summonBarWidget`/`findPanelWidget` from 4.5 `shell/plugins/bar/Bar.qml`, `pickPanelSlot`/`pickDrawnSlot` from 4.5 `BarModel.js`). For scripts and tests, one native `IpcHandler` per panel is declared once in the bar, outside `Variants`, with plain target names following the existing convention (`audio`, `display`, `power`; convention fixed for `network` in 02-28 and `bluetooth` in 02-29) and only `open`, `close` and `toggle`, using the same focused-monitor routing; panels set `manageIpc: false`. No own socket or CLI; proposing one later requires an ADR. Notifications keep their existing `notifications` target (`togglePanel`/`openPanel`/`closePanel`) and only gain a binding. Concrete chords, including positional `SUPER+CTRL+<1-9>`, are decided with the bindings question.
- **Status**: Accepted

## DEC-039

- **Context/Nuances**: Under DEC-032 a panel choice runs `audio-device default`, which calls `wpctl set-default`, setting the `default.configured.audio.sink`/`source` metadata that WirePlumber persists itself under `$XDG_STATE_HOME/wireplumber/` (default-nodes state). MirrorOS only delivers `bluetooth-a2dp-autoconnect.conf` and does not alter WirePlumber state persistence. Expected, to verify: restore at login; fallback to the next device by priority when the chosen one is absent; return to the chosen device when it reappears (WirePlumber 0.5 keeps a history of configured defaults). A panel-side copy of the choice would duplicate and could contradict WirePlumber. The prototype left persistence unverified.
- **User Response**: Accepted.
- **Decision**: Persistence is delegated to WirePlumber through `wpctl set-default`; neither the panel nor the shell keeps its own default-device state. Validation: in the laboratory with `--audio`, select the other device, restart the user session (or `pipewire`/`wireplumber`) and check `@DEFAULT_AUDIO_SINK@`/`@DEFAULT_AUDIO_SOURCE@` and the panel; on the T14s, the same across a reboot plus the absent-device case (headphones or Bluetooth off and back on) to confirm the return to the chosen device. A failure is recorded as a finding and its fix decided separately in `system/audio` configuration, never by adding panel state.
- **Status**: Accepted

## DEC-042
- **Question**: How is disabling an output protected against mirror dependencies and concurrent invocations? (plan review, amends DEC-034)
- **Context/Nuances**: Counting enabled outputs misses two cases that can leave the user without an image: disabling the source of a mirrored output (the mirror counts as enabled but goes blank), and two concurrent invocations (panel click plus chord, or double click) both reading two active outputs and each disabling one. The existing Hyprland `display` helper already detaches mirrors with `unmirror()` before disabling the internal panel, but reads `hyprctl monitors` and applies without any lock, and the planned `output` subcommand did not require reusing `unmirror()`.
- **User Response**: Accepted the review correction.
- **Decision**: Every mutating `display` subcommand (`output`, `scale`, `laptop`, `mirror`, `clamshell`) runs under one `flock` on a lock file in `$XDG_RUNTIME_DIR`; inside the protected section the helper re-reads `hyprctl monitors all -j`, validates and applies in a single `hyprctl eval`. `output <name> off` first detaches outputs mirroring `<name>` (reusing `unmirror()`) and refuses when no independent (non-mirroring) enabled output would remain. Tests cover the mirror-source case, a single independent output with another mirroring it, and two concurrent invocations (a blocking `hyprctl` double).
- **Status**: Accepted

## DEC-043
- **Question**: How does `audio-device` identify the node it makes default? (plan review, amends DEC-032, DEC-039, DEC-040)
- **Context/Nuances**: Upstream `omarchy-audio-output-switch` passes `pactl`'s `.index` to `omarchy-audio-output-set-default`, which runs `wpctl set-default "$node_id" || true` and then `pactl set-default-sink "$name" || true`. On the planning host `pactl` sink `.index` equals PipeWire `object.serial` (66, 282), not the `object.id` `wpctl` expects (46, 63): `wpctl` fails silently while `pactl` switches audio, a false success that also undermines WirePlumber persistence.
- **User Response**: Accepted the review correction.
- **Decision**: `audio-device default output|input` takes only the node name; it resolves the PipeWire `object.id` with `pw-dump` (package `pipewire`) filtered by `node.name` and `media.class`, runs `wpctl set-default <id>`, and exits 4 with no success OSD if resolution or `wpctl` fails (no `|| true`). The redundant `pactl set-default-*` call is dropped so two paths cannot diverge. The panel passes names, never ids; `cycle` uses the same path. Bats doubles use distinct index, id and serial values. Persistence validation (DEC-039) also runs after a switch made by the cycle shortcut, not only from the panel.
- **Status**: Accepted

## DEC-044
- **Question**: Which streams does `audio-device` move when the default device changes? (plan review, amends DEC-032)

## DEC-045
- **Question**: What do `open`, `close` and `toggle` do when a panel is open on one monitor and another monitor is focused? (plan review, amends DEC-030, DEC-031)
- **Context/Nuances**: Upstream `BarModel.pickPanelSlot` prefers an already opened copy on any monitor before the focused monitor's copy, so with a panel open on A and focus on B, `open()` stays on A and `toggle()` closes A, contradicting AC-4's "on the focused monitor" and letting tests accept incompatible outcomes. MirrorOS has one `Bar` object with a shared `activePopout` across screens and `requestPopout` closes the previous popout, so at most one panel is open at a time; only where it appears matters. MirrorOS does not override Hyprland `follow_mouse` (default 1), so the focused monitor is where the user works.
- **User Response**: Accepted the "focused monitor wins" recommendation after reviewing the trade-off.
- **Decision**: Keyboard and IPC requests follow "focused monitor wins": `open` opens on the focused monitor, moving the panel there if it is open elsewhere, and does nothing if already open there; `close` closes the open copy wherever it is; `toggle` (chords and `panel-at N`) closes when open on the focused monitor and otherwise opens on the focused monitor, moving it if open elsewhere. A focus change does not move an open panel by itself. A click on a bar icon acts on that instance. `SUPER+CTRL+1..9` count the right section of the focused monitor's bar. If the focused monitor does not draw the widget, a drawn copy elsewhere is used (`pickDrawnSlot`). The adapted selection replaces upstream's opened-first priority and is documented as a divergence in the header and `UPSTREAM.md`; tests cover every case, including a focus change with a panel open. Trade-off accepted: closing a panel open on another monitor from the focused one takes a second press (or Escape/outside click).
- **Status**: Accepted

## DEC-047
- **Question**: How do `display` and the display panel deal with Hyprland applying monitor changes asynchronously? (plan 02-27 execution, laboratory checkpoint, amends DEC-042)
- **Context/Nuances**: Right after `display scale 1.6`, `display state` still reported the previous scale for about 0.5 s, so a following locked action could read stale state and the panel's selection lagged until its poll. Hyprland emits no monitor event for a runtime scale change, and Qt's `Screen.devicePixelRatio` follows only the integer Wayland scale, so a refresh on that property did not work.
- **User Response**: Approved both fixes after laboratory verification.

- **Status**: Accepted

## DEC-049
- **Question**: How does a configure publication reach a running shell without the hot reload failure of TODO-018?
- **Context/Nuances**: Isolated `qs -p` reproductions in the laboratory guest (Quickshell 0.3.2, qt6-declarative 6.12.0) show the in-process reload fails with "`X` is not a type" whenever a file gains an inline component name it lacked at first load, including a file that already had others; changing an existing component's body or removing components reloads, and a fresh process always loads. Each reload creates a new `QQmlEngine` under the same `qs:@/qs/…` URLs, so process-global Qt type state keyed by URL survives. After `install-runtime`'s `mv --exchange` the reload often did not fire at all, so the outcome after configure was nondeterministic. Restarting the shell from configure would cross the rule that configure never starts or restarts anything; forbidding new inline components would be a fragile authoring rule.
- **User Response**: Approved the recommendation.
- **Decision**: `shell.qml` sets `settings.watchFiles: false`; a published runtime takes effect at the next `mirroros-shell.service` restart or session. Configure behaviour is unchanged and needs no ADR (ADR 0012 sets no lifecycle rule). `shell-lifecycle.test.mjs` pins the setting; `docs/procedures/desktop-shell.md` documents the behaviour. An upstream Quickshell report is drafted for the maintainer to file.
- **Status**: Accepted
