# Story 4.4 Hardware and Connectivity Planning — Decision Log

## DEC-001
- **Question**: Which role does each available environment (laboratory guest, reference VM, ThinkPad T14s) play in Story 4.4?
- **Context/Nuances**: The Epic 4 common contract requires a clean installation plus `configure` in the reference VM without manual steps, a no-mutation rerun, and both execution contexts. The laboratory (`~/qemu/mirroros-lab`) has no audio device, battery, Wi-Fi or backlight. The T14s runs MirrorOS from the latest built ISO and is reachable over SSH, but ADR 0023 makes it a recognized unqualified profile; the Framework Laptop 13 Pro remains the sole qualified laptop. `TODO-582784b9` keeps an open `mt7921e` Wi-Fi resume finding (`-110`).
- **User Response**: Approved the recommended three-role split.
- **Decision**: (1) The T14s, over SSH, is the hardware exploration and daily-use validation environment for audio, Bluetooth, brightness, media keys, battery, lid, suspend/hibernate and Wi-Fi, after backing up any user configuration to be touched; its evidence is exploratory and non-qualifying, and the Framework remains "pending target-laptop validation". (2) A clean reference VM provides reproducible acceptance: clean install plus `configure`, no-mutation rerun, both execution contexts, and postconditions that tolerate absent hardware by reporting it unavailable without failing or claiming it works. (3) The laboratory guest is used only if the bar panels need UI iteration without risking the T14s session; otherwise it is not used.
- **Status**: Accepted

## DEC-002
- **Question**: Should an agent run inside each test environment, or is the host agent sufficient?
- **Context/Nuances**: Suspend, hibernate and lid tests interrupt any in-machine session. Physical actions (lid, media keys, Bluetooth pairing, listening to audio, unplugging the charger) require the maintainer in every environment. The T14s is the maintainer's real laptop with personal credentials and data. Graphical-session commands can run over SSH by inheriting the session environment. Story 4.3 used a supervised guest agent in the laboratory with a snapshot, a checksummed Git bundle and host review.
- **User Response**: Approved, including the optional guest agent for panel iteration if needed.
- **Decision**: The host agent drives all tests over SSH on the T14s and the reference VM; no agent is installed inside them. Tests needing physical action follow a supervised script: the agent requests the action, the maintainer performs it, and the agent verifies and collects evidence after reconnecting. Suspend and hibernate cycles are verified by reconnecting and reading the boot journal. Graphical-session checks inherit the session environment (`XDG_RUNTIME_DIR`, `WAYLAND_DISPLAY`, `HYPRLAND_INSTANCE_SIGNATURE`). If bar-panel iteration is needed and proves slow from the host, a guest agent may be used in the laboratory under the Story 4.3 protocol: recoverable snapshot, checksummed Git bundle handoff and host review before integration.
- **Status**: Accepted

## DEC-006
- **Question**: Which interfaces connect Wi-Fi and Bluetooth, given that Omarchy Quattro replaced its TUIs with shell panels? (refines DEC-003)
- **Context/Nuances**: Inspection of `omarchy-4.0.6.iso` (Quattro) shows NetworkManager as the network stack; `omarchy-upgrade-to-quattro` retires `impala`, `iwd`, `bluetui`, `blueberry`, `wiremix`, `pavucontrol` and `playerctl`. Wi-Fi, Bluetooth, audio and power are handled by Quickshell panels (`shell/plugins/panels/{network,bluetooth,audio,power,monitor}`) bound to SUPER+CTRL+W/B/A/P, over `omarchy-*` helpers using `nmcli`, `bluetoothctl`, `pactl`/`wpctl`, `brightnessctl` and `power-profiles-daemon`. The network panel covers PSK, hidden SSIDs and enterprise PEAP/MSCHAPv2 only; it does not cover EAP-TLS/TTLS with certificates, static IP/DNS, VPN, proxy or profile editing. Bluetooth pairing relies on the `bt-agent -c NoInputNoOutput` user unit (`bluez-tools`), auto-accepting while the panel scans, which may not suit PIN or passkey devices. Panels are unavailable when the shell fails or outside a graphical session (TTY, SSH, greeter, recovery). `nmcli`/`nmtui` (in `networkmanager`) and `bluetoothctl` (in `bluez-utils`) are always present because the providers ship them and the panels depend on them.
- **User Response**: Approved option (a′) after reviewing what a panels-only approach would lose.
- **Decision**: The plan 02-26 panels are the primary Wi-Fi and Bluetooth interface, Quattro style, with SUPER+CTRL+W/B/A/P. The terminal path (`nmtui`/`nmcli` and `bluetoothctl`) is the permanent, documented fallback and recovery path, not an interim one: it adds no package and no dedicated key binding. Plan 02-25 satisfies the story's connection criterion through that terminal path. `impala`, `iwd`, `bluetui` and `wiremix` are not added. The two-plan split of DEC-003 is unchanged; this decision replaces its unspecified "terminal interface".
- **Status**: Accepted

## DEC-009
- **Question**: Which hardware key bindings does plan 02-25 deliver?
- **Context/Nuances**: Quattro `default/hypr/bindings/media.lua` binds volume ±5/±1 (ALT), mute, mic mute, brightness ±5%/±1% (ALT) and max/min (SHIFT), keyboard backlight, media next/previous/play-pause (plus ALT/ALT+SHIFT Play variants), audio output/source switch (SHIFT+Mute/Play/Pause), touchpad toggle and eject. MirrorOS already provides `MirrorOSKeys.bind(id, chord, description, …)` with a registry and tests, plus `shell_ipc(...)`; the OSD exposes `showSource volume|brightness`, which reads the measured value and never fabricates one. ThinkPad keyboard backlight is often firmware-handled (Fn+Space).
- **User Response**: Approved.
- **Decision**: Plan 02-25 binds, with Quattro's chords and options (`locked = true`, `repeating` where Quattro uses it): volume ±5 and ±1 and mute through `wpctl set-volume -l 1.0 @DEFAULT_AUDIO_SINK@ …` (no amplification above 100%); mic mute; brightness ±5%, ±1% and max/min through `brightnessctl`; media next/previous/play-pause through `playerctl` [DEC-008]. Each volume or brightness change then calls `osd showSource …` so the OSD shows the measured value. Keyboard-backlight keys are bound only if T14s exploration shows `XF86KbdBrightness*` reaching Hyprland. Audio output/source switching (to plan 02-26 with the audio panel), touchpad toggle and eject are excluded and recorded as reserved in `UPSTREAM.md`. Mic mute is reported through `osd show` with a fixed message payload and no fabricated level; no `microphone` OSD source is added.
- **Status**: Accepted

## DEC-010
- **Question**: Which logind lid and power-key policy does plan 02-25 apply?
- **Context/Nuances**: MirrorOS `hypridle` already locks before sleep (`before_sleep_cmd = loginctl lock-session`), and Story 4.3 binds `XF86PowerOff` to the system menu, but no logind drop-in exists; logind's default `HandlePowerKey=poweroff` likely makes the power key both open the menu and power off. Quattro ships `HandlePowerKey=ignore`, locks immediately on `switch:on:Lid Switch`, and raises `InhibitDelayMaxSec` to 15 s because the 5 s default let logind suspend before the lock was secure. Restarting `systemd-logind` tears down the session.
- **User Response**: Approved.
- **Decision**: Plan 02-25 delivers a MirrorOS-owned logind drop-in with `HandlePowerKey=ignore`, so the key only opens the system menu; current T14s behaviour is checked first as defect evidence, and the firmware long-press hard off is unaffected. A postcondition reads the effective value from logind through `busctl`. Lid close without an external monitor keeps the logind default (suspend), with locking through `hypridle` `before_sleep_cmd`. T14s exploration measures whether the session is locked before suspend, so that no content is visible on resume; only if it is not are the `InhibitDelayMaxSec` drop-in and/or Quattro's immediate lid-close lock added, never pre-emptively. Logind drop-ins take effect through `systemctl reload systemd-logind`, never restart; in the installer context the file is only written. Clamshell behaviour is a separate decision.
- **Status**: Accepted

## DEC-012
- **Question**: How do Story 4.4 changes take effect in the running context: enable-only (effective after reboot) or activated live?
- **Context/Nuances**: `capabilities/lib/units.sh` is enable-only, and `tests/capabilities/mechanism.contract.bats` forbids direct `systemctl` in `apply`. The rule "never starts, restarts or reloads the shell, hypridle or the desktop" is a procedure convention (`docs/procedures/configure.md`), not an ADR; Epic 4 lets machinery grow when a slice consumes it, within ADR 0010. Three layers were costed: system services (low), logind reload (low–medium; reload only, never restart, and only when the drop-in changed, to keep reruns mutation-free) and the user session (PipeWire user sockets, new Hyprland bindings, a shell restart because `ProviderState` detects BlueZ/UPower only at startup; high cost and contrary to the convention). Even with the system layers, a logout/login remains necessary; the gain is replacing reboot with re-login on an already-installed system.
- **User Response**: Chose option (d).
- **Decision**: Plan 02-25 adds two mechanism helpers. `cfg_unit_start` starts a system unit in the running context only if it is inactive (recorded as a change) and is a no-op in the target context. `cfg_unit_reload` is restricted to `reload`, never restart, and runs only when its governing delivered file changed in the current run. They activate `bluetooth.service` and `power-profiles-daemon` and reload `systemd-logind`; T14s exploration confirms that the installed systemd supports logind reload. The user-session layer is not activated live: bindings, user audio and shell indicators take effect at the next login, and the shell/hypridle/desktop rule stays intact. Postconditions check effective state in the running context (for example `HandlePowerKey` through `busctl`, units active) and declared state in the target context (delivered files, enabled units). Mechanism tests, `docs/procedures/configure.md` and `capabilities/README.md` are updated with the helpers. No ADR is required. This refines DEC-010's reload and postcondition clauses.
- **Status**: Accepted

## DEC-013
- **Question**: How are the slice's sources organised?
- **Context/Nuances**: The story's fourth criterion requires that replacing a hardware provider leaves unrelated desktop and workflow configuration without redesign. Quattro encapsulates provider tools behind `omarchy-*` action commands called by its bindings. MirrorOS keeps bindings in the Hyprland provider (`shell-bindings.lua`, `window-bindings.lua`) with a duplicate id/chord test, and runs steps in the explicit `CFG_STEPS` order.
- **User Response**: Approved.
- **Decision**: One configure step per `docs/mvp-scope.md` row under `capabilities/system/`, each with `apply`, `packages` and `sources.md`: `system/audio` (PipeWire, WirePlumber, `pipewire-pulse`, `pipewire-alsa`, `playerctl`), `system/bluetooth` (`bluez`, `bluez-utils`, unit enable and start), `system/power` (UPower, `power-profiles-daemon`, `brightnessctl`, logind drop-in) and `system/vpn` (`networkmanager-openconnect`). Owned action commands with a command/sub-action shape, such as `/usr/share/mirroros/hardware/volume raise|lower|mute|…`, `brightness …`, `media …` and `display laptop|mirror|scale|clamshell`, encapsulate the provider tool (`wpctl`, `brightnessctl`, `playerctl`, `hyprctl`) and the OSD call, so replacing a provider touches only its step and command. Audio, brightness and media commands are delivered by their system steps; `display` is Hyprland-specific and lives under `desktop/compositor/providers/hyprland/`. A new `hardware-bindings.lua` in the Hyprland provider, loaded like `shell-bindings.lua` and covered by the existing duplicate id/chord test, calls only these commands. The four `system/*` steps precede `desktop/compositor/providers/hyprland` in `CFG_STEPS`. Commands take argv arguments and validate inputs (connector names, values). They adapt Quattro's pattern rather than copy it; any literal Quattro fragment reused records its provenance (Omarchy 4.0.6, MIT) in the governing `UPSTREAM.md`.
- **Status**: Accepted

## DEC-014
- **Question**: Does plan 02-25 switch power profiles automatically by AC/battery state, as Quattro does?
- **Context/Nuances**: Quattro's `omarchy-powerprofiles-set [autodetect|ac|battery] [profile]` remembers one profile per state under `~/.local/state/omarchy/powerprofiles/{ac,battery}`, defaulting to `performance` on AC (or `balanced` when unavailable) and `balanced` on battery. The switch is triggered by the shell battery service (`plugins/services/battery/Service.qml`) on `UPower.onBattery` changes and by `omarchy-powerprofiles-init` at Hyprland autostart; earlier udev rules were removed by a migration. Bare `power-profiles-daemon` only keeps the last chosen profile. ADR 0012 prevents adding a shell service before plan 02-26's ADR.
- **User Response**: Chose option (b) with Quattro's defaults.
- **Decision**: Plan 02-25 delivers an owned `/usr/share/mirroros/hardware/power-profile set [autodetect|ac|battery] [profile]` with `omarchy-powerprofiles-set` semantics: it remembers the choice per state in `$XDG_STATE_HOME/mirroros/power-profiles/{ac,battery}`, validates profile availability, and defaults to `performance` on AC (`balanced` when `performance` is unavailable) and `balanced` on battery. A user unit applies `autodetect` at login and listens to UPower `OnBattery`; it is enabled, not started, and takes effect at the next login [DEC-012]. The visible behaviour matches Quattro; only the trigger mechanism differs, being a user unit instead of a shell service because of the ADR 0012 boundary. Plan 02-26 may move it into the shell under its ADR (refined by DEC-015: by default it does not). The owned command replaces `powerprofilesctl` as the terminal path, amending DEC-005; `powerprofilesctl` remains for diagnostics. Exploration records which profiles the T14s exposes.
- **Status**: Accepted

## DEC-016
- **Question**: Which Quattro hardware tunings does plan 02-25 adopt?
- **Context/Nuances**: Quattro ships NetworkManager `wifi.powersave = 2` (latency spikes and drops with some Intel firmware), WirePlumber `bluetooth-a2dp-autoconnect.conf` (A2DP profiles on auto-connect), an ASUS-specific `keyboard-backlight` hibernate hook, and global `usbcore autosuspend=-1` (no documented rationale in Quattro; it trades battery for robustness against peripherals, docks, USB audio and `btusb` disconnects). On the T14s, internal Bluetooth (`mt7921` through `btusb`), webcam and fingerprint reader are USB devices, so a global setting raises idle power. Network is an installation-delivered capability.
- **User Response**: Approved after reviewing the USB autosuspend trade-off.
- **Decision**: No Quattro tuning is adopted pre-emptively [DEC-004]. T14s exploration checks all four through a checklist and adopts only those evidence justifies, each with Omarchy 4.0.6 (MIT) provenance. `wifi.powersave` is tested enabled and disabled (latency, suspend/hibernate resume) for its possible relation to the open `mt7921e` finding; its delivery route stays open. A2DP auto-connect becomes a user drop-in under `system/audio` only if HFP fallback is observed. The ASUS hook is rejected. USB autosuspend is never disabled globally; if needed, a targeted setting is used instead (`btusb enable_autosuspend=0` for Bluetooth issues, or a per-device udev `power/control=on` rule), recorded with its evidence.
- **Status**: Accepted

## DEC-017
- **Question**: How do candidate changes reach the T14s during iteration, and how is T14s acceptance closed?
- **Context/Nuances**: On an installed system, `configure` runs from a checkout (`sudo operations/configure`); `/usr/local/bin/mirroros-configure` is the installer's copy pinned to the ISO commit and unsuitable for iteration. Story 4.3 used a checksummed Git bundle over SSH for handoff. The installation provides Snapper snapshots (ADR 0003). Clean reconstruction is covered by the reference VM [DEC-001], and the T14s is non-qualifying.
- **User Response**: Approved.
- **Decision**: The host agent transfers a checksummed Git bundle of the candidate commit to the T14s over SSH, verifies it there, extracts it into a working checkout (for example `~/code/mirroros-candidate`) and runs `sudo operations/configure` in the running context. Nothing is published and no automatic synchronization is introduced; every run keeps sanitized evidence and records the tested commit. Before the first run, the user configuration it will touch is backed up and a Snapper snapshot is taken as a full rollback point. T14s acceptance closes on the installed system (configure, then reboot or re-login, plus a mutation-free second run); no reinstallation from a new ISO is required, and an optional reinstall remains the maintainer's choice, as in plan 02-24.
- **Status**: Accepted
