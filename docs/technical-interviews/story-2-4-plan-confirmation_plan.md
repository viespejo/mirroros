# Story 2.4 — Plan confirmation and safe cancellation: Consolidated Plan

## Context

Story 2.4 (FR14, FR15, FR16) adds target- and digest-bound confirmation and safe cancellation on top of the plan produced by Story 2.3 (`installation-plan.json`, `facts_binding`, `policy_binding`, approval not representable in the plan). It builds on ADR 0004 (Gum with six mandatory wrappers; Ctrl+C mapping carried to this story) and the architecture's *Destructive authorization*, *Interaction model*, and *Plan review flow*. The execution engine is Story 2.5.

## Approval model

Approval is ephemeral and single-use: it exists only inside the one process that asks for it and is never persisted as something that can authorize execution. A single interactive command, `operations/install apply` (see *Command surface and components*), revalidates the plan and its digest, reruns read-only discovery and compares it with the plan's `facts_binding`, presents the six-step review flow, asks for confirmation, and re-checks target identity and plan digest immediately before execution. The only persisted trace is a non-reusable evidence record (`approval-record.json` with digest, target identity, outcome, and timestamp). In this story the command stops at an explicit "engine pending" boundary after confirmation; Story 2.5 connects that boundary to `install/engine/apply`. This keeps every retry under renewed confirmation and leaves no token that a non-interactive run could consume. A persisted approval artifact was rejected for that reason [DEC-001].

## Command surface and components

The user-facing entry point is `operations/install apply`, delegated in the same way as `discover` and `plan`, with `--plan <file>` optional for reviewing an existing plan rather than being the primary input [DEC-006]. It invokes the orchestrator `install/confirmation/confirm-plan`, the path the architecture tree already reserves, and from Story 2.5 onward hands over to `install/engine/apply` within the same process. Inside `install/confirmation/`, pure logic such as binding comparison, review content, and status mapping is written as Node.js ESM modules, while the Gum interaction and the six ADR 0004 wrappers are Bash, matching how the wrappers were defined and how Gum is invoked. A separate `confirm` subcommand was rejected because it would produce a confirmation that authorizes nothing and duplicate the flow in a later `apply` [DEC-002].

## Outcomes and the engine boundary

Because no engine exists in this story, a confirmation that passes the final re-check ends with exit `2` and the reason `engine_not_available`, stating that nothing was executed and that installation arrives with Story 2.5, while `approval-record.json` records `outcome: "approved"`. `apply` therefore never returns `0` without having installed anything. The three paths stay distinguishable by status and recorded outcome: approved gives `2` with `approved`, cancelled gives `3` with `cancelled`, and invalidated gives `2` with `invalidated` and a specific reason. The boundary is a single point, the absence of `install/engine/apply`, so Story 2.5 replaces exactly that point. Returning `0` with a "confirmed; engine pending" message was rejected because a status-only consumer would read it as a successful installation [DEC-003].

## Interruption and Ctrl+C

Ctrl+C during the interactive review and confirmation phase, covering steps 1 to 6 of the plan review flow, is an explicit cancellation: `apply` exits `3`, records `outcome: "cancelled"`, and still writes `approval-record.json`. Outside that phase, for example while the plan is revalidated or the target is rediscovered read-only, SIGINT keeps the shell convention `128+n`, as do SIGTERM, SIGHUP, and any other signal. The mapping lives in the `confirm-plan` layer rather than in the `confirm_status_map` wrapper, which keeps returning `130` unmapped exactly as ADR 0004 requires; ADR 0004 is not amended because it already delegates this choice, and the mapping is documented in the contract and the install procedure. Mapping every SIGINT during `apply` to `3` was rejected because it blurs the signal convention outside interaction, and never mapping was rejected because it contradicts the story's acceptance criteria [DEC-004, closes ADR 0004 TODO-002].

## Invalidation checks

Comparing `facts_binding.facts_sha256` is not possible because facts carry their own `run_id`, so `apply` reruns full read-only discovery through `install/discovery/discover` with the plan's `target_id` and keeps that output in its own run directory. The fresh facts must be valid; if they are not, `apply` exits `2` with `outcome: "invalidated"` and the discovery reason. It then compares a safety projection of the plan against the fresh facts: the `target_id`, `firmware.boot_mode` and `secure_boot`, the selected disk's identity (`path`, `by_id`, `wwn`, `serial`, `model`, `size_bytes`), its eligibility, and its `current_layout` down to partition UUIDs, PARTUUIDs, sizes, filesystem types, labels, and mountpoints, together with `policy_binding`, whose policy and target-override hashes are recomputed from the embedded code. Any difference exits `2` with `outcome: "invalidated"`, a specific code such as `target_identity_changed`, `target_layout_changed`, or `policy_changed`, and the next step "Regenerate and review the installation plan". The comparison runs once before the review is presented and once more immediately after confirmation, which is the final re-check of DEC-001. Network readiness is not part of the projection, because unready network already makes the facts invalid. A disk-identity-only comparison was rejected because it would miss a new partition or a policy change between plan generation and `apply` [DEC-005].

The plan contract's sentence describing approval as "a separate, digest-bound artifact of a later stage" must be amended to describe ephemeral, in-process confirmation with a non-authorizing evidence record [TODO-001].

## Unified interactive flow

Instead of separate `plan` and `apply` experiences, this plan delivers one interactive flow under `operations/install apply`. It discovers the target read-only, generates a plan with the existing Story 2.3 generator, and presents the review (steps 1 to 5) with an edit loop: every currently editable choice (`target_disk`, `storage_option`, `swapfile_size`, `locales`, `lang`, `console_keymap`, `timezone`, `hostname`, `user_name`, `root_account`) can be changed with Gum in any combination the validator accepts, and each edit regenerates the plan with a new digest before returning to the review. Confirmation (step 6), the final re-check, and the engine boundary follow. The user does not pass `--target` on the command line; the target is chosen during the flow (see *Target selection*). `--plan <file>` is optional for reviewing an existing plan. The non-interactive `discover` and `plan` subcommands stay as reusable, testable pieces, which keeps the architecture's rule that reproducible non-destructive operations run without interaction and ADR 0004's rule that the plan and its digest do not depend on Gum [DEC-006].

Making policy-fixed keys such as the kernel, packages, partition table, ESP, bootloader options, zram, or sudoers editable is out of scope and needs its own decision [TODO-002]. Installing on hardware other than the reference VM and the target laptop is excluded by the PRD and would need an ADR and a PRD change [TODO-003].

## Target selection

The target is chosen, not detected. A target definition does not decide plan options, which come from detected hardware and editable choices; it declares a qualified, supported machine and carries device-specific overrides, so choosing it states the user's intent and discovery verifies that intent against the real hardware. The flow lists the definitions under `targets/` with `gum choose` and calls `discover --target <id>` unchanged: a mismatch exits `2` with `target_identity_mismatch`, and the Framework exits `2` with `target_identity_pending_capture` until its DMI identity is captured. The facts and discovery contracts do not change. Automatic detection was rejected because it would change several contracts to save a two-entry menu and would replace verification of intent with a system decision; it can later be added as a preselection in the menu [DEC-007, supersedes the detection part of DEC-006, closes TODO-004].

## Confirmation gesture

The final confirmation is a single two-part gesture at the end of the review. A `gum confirm`, or its `colorless_confirm` `gum choose` variant, starts with focus on No and asks "Erase `<disk path> <model> <size>` and apply plan `<digest[0:12]>`?"; declining or pressing Esc exits `3`. The user then types the device kernel name, such as `vda` or `nvme0n1`, with `gum input`. A mismatch exits `3` with `outcome: "cancelled"` and the reason `confirmation_mismatch`, with no second attempt, so a retry means rerunning `apply` and confirming again. Esc or Ctrl+C at either prompt is a cancellation under the Ctrl+C rule [DEC-004]. The gesture is the same for virtual and physical targets. Binding to the plan is enforced mechanically by the in-process digest and the post-confirmation re-check, so the gesture only has to break reflexive confirmation and name the disk being erased. Typing twelve digest characters was rejected as too heavy, a confirm-only gesture as passable by a reflexive keypress, and typing digest characters as binding the plan but not the disk [DEC-008].

## Gum on the live medium

Gum enters production here and is added unpinned to `image/archiso/packages.x86_64`, in the same way as `nodejs`, which follows the architecture's rule that observed versions are dated observations and builds record what was actually installed. ADR 0004's "pinned package version" is met as "recorded and checked": the bundle's package manifest, already hashed into `artifact-metadata.json`, records the installed Gum version; `apply` checks `gum --version` against the measured major version 2 at runtime and exits `6` with a reason stating that Gum's behavior is not qualified when it differs, which is ADR 0004's revisit trigger; and the actual version is written to `approval-record.json`. ADR 0004 is not amended, and the interpretation is documented in the build procedure. A true pin through a local package or an Arch Archive snapshot was rejected as contrary to the rolling model and as Story 3.2 provenance work [DEC-009].

## Testing and qualification

Verification has four layers. Pure logic, meaning the safety projection and its codes, status and outcome mapping, the path from a choice edit to a choices file to a regenerated plan, and the review content, is covered by `node --test`. Bats then drives the whole flow with a `gum` double on `PATH`: approval ending in `2` with `engine_not_available`; decline, Esc, Ctrl+C during the review, and `confirmation_mismatch` ending in `3`; Ctrl+C outside the review keeping `130`; a tampered plan, a target or layout change before and after confirmation, and a policy change ending in `2` with `invalidated`; a missing TTY or `--yes`/`--non-interactive` flags ending in `2`; `NO_COLOR` and `TERM=dumb` switching to the `gum choose` variant; an unexpected Gum major version ending in `6`; a `sudo` double that fails if invoked; and a secret canary. Counted qualification on the reference VM adds a scenario, either in `qualify-discovery` or a sibling `qualify-confirmation` to be chosen while drafting, in which the guest runs `apply` under `script` with scripted keystrokes and real Gum, as plan 02-03 did: approval exits `2` with an identical disk, cancellation exits `3` with an identical disk, a mistyped device name exits `3`, and a partition table written on the disposable VM disk between `plan` and `apply --plan` exits `2` with `target_layout_changed`, the only case that writes to a disk. Finally, an attended checkpoint has the maintainer review the rendering on the live ISO console, as ADR 0004 requires, with the verdict kept as evidence. The Framework laptop is not exercised in this plan. A Bats-only approach was rejected because it would not exercise real Gum on the ISO or invalidation by a real target change [DEC-010].

## Secret requirements

Secrets are shown, not collected. The review lists each secret requirement by name, channel, and consumer, for example "`user_password` — protected prompt — required by `create_user`", and no value is requested at any point in this story, including after confirmation, because no engine would consume it. Collecting values with `gum input --password` belongs to Story 2.5, immediately before execution, so that a value lives as briefly as possible. Changing `root_account` in the edit loop adds or removes `root_password` from the displayed list through the existing generator. Collecting and discarding values in this story was rejected because it would handle a secret with no consumer [DEC-011].

## Stage reuse and evidence

`apply` reuses discovery and planning as processes through their existing command-line interfaces, `install/discovery/discover --target <id> --output <dir>` and `install/plan/plan --facts <file> --choices <file> --output <dir>`, so components keep communicating through arguments, files, and exit statuses and each stage still leaves its own evidence. Everything lands in one run directory, `evidence/install/<run-id>/` or `--output`, with `0700` directories and `0600` files. `apply-run.json` holds the run id, timestamp, target id, Gum version, the digests in order, the final digest, the exit status, the outcome, and the reasons. `approval-record.json` is the non-authorizing evidence record of DEC-001 with the final digest, disk identity, outcome, reason, and timestamp. `discovery/initial/` holds the facts used to generate the plan, or for the pre-review check when `--plan` is given, and `discovery/final/` the post-confirmation rediscovery. Each regeneration gets its own `plans/NN/` with the plan, its render, `plan-run.json`, and the `choices.json` that produced it, which never contains secrets. `apply.log` is plain text without ANSI sequences or secrets. With `--plan <file>` the plan is validated and copied into `plans/01/`, leaving the original untouched. `apply-run.json` and `approval-record.json` are written on every outcome, including cancellation and invalidation, except for argument or TTY errors detected before the run starts, which report on stderr and exit `2`. Importing the discovery and plan modules directly from a Node orchestrator was rejected because it couples to their internals and loses the per-stage evidence [DEC-012].

## Review dashboard and editing

After comparing a step-by-step wizard with a single dashboard in two throwaway demos, the review is a single dashboard. `gum format` renders the plan digest in the header, the target, the choices with their provenance, the destructive operations, and the required secrets, and a `gum choose` menu below offers `Cancel` first as the safe option, then `Edit a choice` and `Continue to confirmation`. The dashboard covers review steps 1 to 5, and step 6 is the confirmation gesture [DEC-008]. `gum pager` is not used because of its search defect. Each editable key has its own widget: `gum choose` for the target disk among eligible disks, the storage option with its tier, `lang` among the current locales, and `root_account`; `gum filter` for the console keymap and timezone; `gum filter --no-limit` for locales; and `gum input` for the swapfile size, hostname, and user name. When an edit produces an invalid combination and `plan` exits `2`, the dashboard shows its message and next step, discards the edit, and keeps the previous plan. Each `choices.json` accumulates every edit of the run, and with `--plan` the starting choices are the plan entries whose source is `choice`. Esc inside an edit widget returns to the dashboard unchanged; only `Cancel`, the final No, or Ctrl+C cancel with `3` [DEC-013].

Styling follows the grayscale palette of the 02-03 prototype throughout, including inverted `DESTRUCTIVE` markers and inverted menu selection, with a project grayscale glamour style replacing the default pink theme of `gum format`, and with a larger top margin above the menu header to be tuned during implementation. Because a single dashboard may not fit an 80×25 console without scrolling, the attended live ISO console checkpoint checks the fit explicitly; if it does not fit, the dashboard is compacted by grouping choices and putting non-destructive operations on one line, and returning to a wizard requires the maintainer's agreement [DEC-013].
