# Story 2.2 — Target discovery and normalization: Decision Log

## DEC-001
- **Question**: What is the scope of this plan?
- **Context/Nuances**: `install/`, `hardware/`, `targets/`, and `contracts/` do not exist yet; this is the first production code under `install/`. Hardware rules (`hardware/rules/`), plan generation, confirmation, the engine, and the ADR 0003 storage selector belong to Stories 2.3–2.6. The architecture forbids speculative final schemas under `contracts/` without fixtures and contract tests.
- **User Response**: Accepted the recommendation as proposed.
- **Decision**: The plan covers Story 2.2 only: read-only discovery, normalization with distinguishable precedence layers, and validation with normalized exits. Out of scope: plan generation and digest (2.3), confirmation (2.4), engine (2.5), hardware rules and the storage selector (2.6, ADR 0003). In 2.2, the "detected selection" layer only records detected capabilities (for example GPU vendor, battery presence, virtualization) without mapping them to configuration.
- **Status**: Accepted

## DEC-002
- **Question**: Where and how does discovery run, and how does MirrorOS code reach the live environment?
- **Context/Nuances**: The live ISO ships no `nodejs`, `pciutils`, `git`, or MirrorOS code. The architecture assigns normalization to Node.js. Options considered: Bash collectors + Node normalization with `nodejs` added to the ISO; Bash + `jq` only (rejected: violates the language policy); host-side normalization (rejected: does not work on the laptop). Deferring code embedding behind NoCloud was initially recommended and then withdrawn: the ISO must be rebuilt anyway for `nodejs`, NoCloud is a test channel rather than a production path, the "target laptop" criterion would be unexercisable, and Stories 2.3–2.5 would inherit an unresolved boundary decision. Splitting into two plans (embedding then discovery) was offered and declined.
- **User Response**: Chose to embed in this plan (option 1); confirmed the summary.
- **Decision**: Bash collectors read `/sys`, `lsblk -J`, `ip -j`, `systemd-detect-virt`, and `dmidecode` (GPU through `/sys/bus/pci`, so no `pciutils`). Normalization and validation run in Node.js ESM. This plan adds `nodejs` to the ISO and embeds MirrorOS production code (at least `install/`, plus what is needed from `operations/` and `hardware/`) with commit traceability recorded in the artifact metadata. This touches `image/builder/` and `image/archiso/` and requires an ISO rebuild and boot requalification (Story 1.4) of the new bundle. NoCloud remains a development channel only; counted qualification uses the embedded code at a clean commit.
- **Status**: Accepted

## DEC-003
- **Question**: How is MirrorOS production code embedded into the ISO?
- **Context/Nuances**: `image/builder/lib/source-capture.sh` captures only `image/archiso/` (clean: `git archive`; dirty: copy of non-ignored paths), mounts the private copy read-only into the container, and Gitleaks scans that copy. `artifact-metadata.json` records `commit`, `dirty`, `profile_identity` (tree hash of `HEAD:image/archiso`), and `dirty_paths`. Alternatives rejected: committing a copy or symlink under `image/archiso/airootfs/` (duplicates ownership; the builder rejects symlinks leaving the profile) and a local pacman package (too heavy now; adds package-provenance work belonging to Story 3.2).
- **User Response**: Accepted option A as proposed.
- **Decision**: Build-time additional capture. `source-capture.sh` captures an explicitly declared list of repository subtrees (no globs; for example `install/`, `hardware/`, `targets/`, and the needed parts of `operations/`) with the same clean/dirty mechanism and places them inside the captured profile at `airootfs/usr/local/lib/mirroros/`. The existing captured-profile Gitleaks scan covers them. Artifact metadata gains an `embedded_code` block (ISO path, subtree list, per-subtree tree hash). An identity file inside the ISO (commit and `dirty`) lets discovery record which code it ran. Single ownership is preserved. The user-facing entry point is decided separately.
- **Status**: Accepted

## DEC-005
- **Question**: How is the target selected, and what is the supported target boundary?
- **Context/Nuances**: Precedence requires knowing which `targets/<id>/overrides/` to read, and the story requires rejecting out-of-boundary targets with `2`. DMI auto-detection (guessing on failure, contrary to explicit reviewable overrides) and auto-detection with an optional override (two paths to test) were rejected. The user stated that the physical target is no longer the Slimbook Creative but `framework-13-pro-amd`.
- **User Response**: Accepted option A; renamed the physical target to `framework-13-pro-amd`.
- **Decision**: An explicit, mandatory `--target <id>` with values `reference-vm` and `framework-13-pro-amd`. Each `targets/<id>/` declares minimal identity constraints (for example a `target.json`) checked against detected facts: `reference-vm` expects `kvm` virtualization, UEFI, and a QEMU DMI vendor; `framework-13-pro-amd` expects its DMI vendor/product and no virtualization. An unknown or missing id, or facts contradicting the constraints, exit `2` with an actionable reason. The common boundary for every target: `x86_64`, 64-bit UEFI, and at least one non-removable candidate disk that is not the live medium. Other thresholds (minimum disk size, network) are decided with validation.
- **Status**: Accepted

## DEC-007
- **Question**: What artifacts does discovery produce, and how are precedence layers kept distinguishable?
- **Context/Nuances**: The story requires portable facts, detected selections, and explicit overrides to remain distinguishable with precedence baseline < detected < override < runtime private input. The architecture reserves final schemas under `contracts/` and requires fixtures and contract tests for initial schema work; JavaScript uses Node built-ins only (no npm dependencies). Alternatives mentioned and not chosen: omitting `effective` and leaving resolution to Story 2.3; a formal JSON Schema file.
- **User Response**: Accepted as proposed.
- **Decision**: (1) Each Bash collector (`discover-firmware`, `discover-network`, `discover-storage`, `discover-hardware`) emits uninterpreted JSON on stdout, retained as raw evidence. (2) Node produces `target-facts.json` with `format_version: 1` and sections `source` (`run_id`, embedded `commit` and `dirty`, `target_id`), `layers` (`portable_baseline` — empty or minimal in 2.2, filled by installation policy in 2.3; `detected` — firmware, network, storage, hardware capabilities; `target_override` — from `targets/<id>/overrides/`; `runtime_private` — names of required inputs only, never values, empty in 2.2), `effective` (resolved view with a per-value `source` of `baseline`, `detected`, `override`, or `runtime`, satisfying FR34), and `validation` (`valid`/`invalid` plus reasons with `code`, `message`, `next_step`). (3) Default location `evidence/install/<run-id>/` with 0700/0600 permissions and atomic writes; `--output <dir>` overrides it; a human-readable summary of key facts and their provenance goes to stdout. (4) The format is documented in `contracts/target-facts.md` and validated by a hand-written Node validator with fixtures in `tests/fixtures/discovery/` and contract tests; no formal `*.schema.json`.
- **Status**: Accepted

## DEC-008
- **Question**: Which storage facts are collected, and how is disk eligibility determined?
- **Context/Nuances**: Story 2.4 binds confirmation to the storage identity recorded here. Disk serials differ from the DMI serial: they are the stable identity required by the acceptance criterion. Existing partitions do not block eligibility because the engine wipes the whole disk under explicit confirmation (Story 2.4). Removable disks are always ineligible, which excludes installing to a USB SSD.
- **User Response**: Accepted as proposed, including the 20 GiB minimum and the removable exclusion.
- **Decision**: (1) Read-only collection: `lsblk -J -b` with `PATH`, `KNAME`, `TYPE`, `SIZE`, `MODEL`, `SERIAL`, `WWN`, `TRAN`, `RM`, `RO`, `HOTPLUG`, `PTTYPE`, `PTUUID`, `FSTYPE`, `LABEL`, `UUID`, `PARTUUID`, `MOUNTPOINTS`; `/dev/disk/by-id/` links; the live-medium backing device from the `/run/archiso/bootmnt` mount. No `blkid -p`, `smartctl`, or privileged probing. (2) Stable identity per disk: `by-id` (preferring `nvme-eui.*` and `wwn-*`), `WWN`, `SERIAL`, `MODEL`, `PATH`, byte size; absent values are omitted. (3) Disk serials are kept in `target-facts.json`, which lives only in local, ignored, 0600, scanned evidence; Git fixtures use synthetic values. (4) The current layout (partition table, partitions, filesystems, mountpoints) is recorded as information; existing partitions do not make a disk ineligible. (5) Discovery does not select a disk; it lists candidates with `eligible` and reasons; selection belongs to Story 2.3. Ineligible: `loop`/`rom`/`zram`, removable (`RM=1`), read-only, the live medium, any active mountpoint, or size below the minimum. (6) Minimum size 20 GiB, classified as technical necessity (1 GiB ESP, 4 GiB swapfile, base system with margin). (7) No eligible candidate exits `2` with a reason per disk.
- **Status**: Accepted

## DEC-009
- **Question**: Which firmware facts are collected, and how are they validated?
- **Context/Nuances**: BIOS is not supported. Detecting a non-UEFI boot exists only to reject it early with an actionable reason, because some firmware boots the live USB in legacy/CSM mode unnoticed, which would otherwise surface later as a confusing `bootctl install` failure. The live ISO session is already root; "no privilege elevation" means discovery never invokes `sudo` or other elevation and never writes to any device, not that it runs unprivileged. The architecture keeps Secure Boot disabled for the MVP and systemd-boot is unsigned.
- **User Response**: Accepted; clarified that BIOS is not supported (detection serves rejection only).
- **Decision**: (1) `discover-firmware` records, read-only: boot mode (`uefi` if `/sys/firmware/efi` exists, otherwise a non-UEFI value recorded only for rejection), UEFI platform size from `/sys/firmware/efi/fw_platform_size`, efivars availability, Secure Boot state from the `SecureBoot-8be4df61-…` efivar or `bootctl status` without added privilege (`unknown` if undeterminable), and non-sensitive DMI fields from `/sys/class/dmi/id/` (`sys_vendor`, `product_name`, `product_version`, `board_name`, `bios_vendor`, `bios_version`, `bios_date`); never `product_serial`, `product_uuid`, `board_serial`, or `chassis_serial`. (2) Validation exits `2` with `next_step` for: non-UEFI boot ("boot the medium in UEFI mode; disable CSM/legacy"), 32-bit UEFI, efivars unavailable, and Secure Boot enabled ("disable Secure Boot in firmware setup and rerun"). Secure Boot `unknown` is a non-blocking entry in `validation.warnings`. (3) Discovery never invokes privilege elevation and never writes to devices.
- **Status**: Accepted

## DEC-010
- **Question**: Which network facts are collected, and what defines network readiness?
- **Context/Nuances**: Installation needs network for `pacstrap`. MAC addresses identify the machine and are not needed. An HTTPS probe creates outbound traffic but changes no target state; Story 1.4 already uses `REFERENCE_VM_GUEST_HTTPS_URL`. A non-blocking warning for missing network was considered and rejected because the resulting plan could not install.
- **User Response**: Accepted as proposed.
- **Decision**: (1) `discover-network` records interfaces from `ip -j addr`/`ip -j link` (name, wired or wireless via `/sys/class/net/<if>/wireless`, state, presence of global IPv4/IPv6), the default route (`ip -j route show default`), DNS resolution of `archlinux.org` (`getent ahosts`), and an HTTPS probe of `https://archlinux.org/` with `curl` and a bounded timeout. MAC addresses, Wi-Fi credentials, SSIDs, and `iwd` state are never recorded. (2) `network.ready` is true only when a default route exists, DNS resolves, and the HTTPS probe succeeds; the failing step is recorded. (3) Not ready exits `2` with a step-specific `next_step` (for example "connect a cable or configure Wi-Fi with `iwctl`, then rerun"); discovery never configures the network. (4) No mirror checks or `reflector`; mirrors belong to the engine (Story 2.5).
- **Status**: Accepted

## DEC-011
- **Question**: Which hardware capabilities does `discover-hardware` record?
- **Context/Nuances**: Per DEC-001, Story 2.2 only records capabilities; mapping to configuration belongs to Story 2.6. The set is chosen to give 2.6 its inputs (microcode, swap and hibernation sizing, graphics) without growing discovery. No `pciutils` (DEC-002).
- **User Response**: Accepted as proposed.
- **Decision**: Read from `/sys` and `/proc` only: (1) CPU vendor (`AuthenticAMD`/`GenuineIntel`), model, and core count from `/proc/cpuinfo` (input for microcode, TODO-004 of 02-01); (2) `MemTotal` from `/proc/meminfo` (swapfile and hibernation sizing); (3) graphics devices of PCI class `0x03xxxx` under `/sys/bus/pci/devices/*` with `vendor`, `device`, bound `driver`, and `boot_vga`, classified as AMD `1002`, Intel `8086`, NVIDIA `10de`, or QEMU virtual `1af4`/`1234`; (4) battery presence (`/sys/class/power_supply/*` with `type=Battery`), never battery serial or manufacturer; (5) virtualization from `systemd-detect-virt`; (6) Wi-Fi presence referenced from the network facts rather than duplicated. These facts never block on their own; they participate only in the DEC-005 target identity check (for example `--target reference-vm` with virtualization `none` exits `2`). No GPU constraint for `framework-13-pro-amd` in 2.2 (pending DMI capture, TODO-002). Out of scope: USB, sensors, audio, fingerprint reader, Bluetooth, and NVMe detail; Story 2.6 adds them if needed.
- **Status**: Accepted

## DEC-012
- **Question**: What may a target override change in Story 2.2?
- **Context/Nuances**: Detected values are facts; an override must never claim, for example, that a disk is UEFI or that the network is ready. Selections do not exist until Story 2.6, yet the acceptance criterion requires demonstrable four-layer precedence. Rejected: a generic mechanism with an empty production allowlist (exercised only by fixtures) and no overrides at all (fails the criterion).

Unknown keys, or any attempt to override a detected fact, exit `2` as invalid input. `reference-vm` and `framework-13-pro-amd` ship an empty `overrides/` (README only); precedence is demonstrated through fixtures and the `effective` provenance view. Stories 2.3 and 2.6 extend the allowlist (hardware selections, installation policy).

## DEC-015
- **Question**: What is the exact subcommand interface and its exit semantics (closes the open items of DEC-004)?
- **Context/Nuances**: The story distinguishes missing or contradictory facts (invalid input or unmet precondition) from tool failure. The architecture defines `5` for upstream-operation failure with the original child status preserved, `6` for internal contract failures, and a structured error shape. Discovery is non-interactive, so ADR 0004 (Gum) does not apply yet.
- **User Response**: Accepted as proposed.
- **Decision**: (1) `operations/install discover --target <id> [--output <dir>]`, exposed in the ISO as `mirroros-install discover …` through `/usr/local/bin/mirroros-install`; `operations/install discover --help` prints subcommand help; `--output` must be absent or an empty directory, otherwise `2`. (2) Exits: `0` valid facts (warnings allowed); `2` invalid arguments, unknown or contradictory target, missing required fact, outside the supported boundary, network not ready, no eligible disk, or invalid override; `5` unexpected external command failure (for example non-zero `lsblk`) with `child_exit_status` and its stderr kept in evidence; `6` damaged checkout or embedded code, or an internal invariant failure such as the produced document failing its own validator. (3) On `2`, `target-facts.json` is still written with `validation: invalid` and reasons; on `5` or `6`, only raw evidence and the architecture's structured error (`code`, `stage`, `operation`, `message`, `next_step`, `child_exit_status`) are written. (4) No Gum in Story 2.2: plain-text summary on stdout, diagnostics on stderr; the ISO gains only `nodejs`, and `gum` arrives with Story 2.3 or 2.4 per ADR 0004.
- **Status**: Accepted
