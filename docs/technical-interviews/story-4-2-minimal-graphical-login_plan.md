# Story 4.2 — Minimal Graphical Login Through Configure: Consolidated Plan

Current state of the design for Story 4.2, the Epic 4 walking skeleton. Each paragraph cites its decisions in the
[decision log](story-4-2-minimal-graphical-login_log.md).

## Plan split

Story 4.2 is delivered in two plans so that each can be verified on its own. Plan 02-15 builds the `configure` mechanism and the skeleton content (SDDM with its stock theme, sessions started through uwsm with a minimal Hyprland configuration, a terminal, an interactive shell, and tmux, plus the provider selections recorded in `docs/mvp-scope.md`) and validates them only against the running installed system, by running `operations/configure` on the installed reference VM. Plan 02-16 adds the target-root context: embedding the configuration code in the ISO, the guided-installer hook after the base postconditions, `arch-chroot` execution with units enabled but not started, user configuration through `runuser`, no readiness claim when `configure` fails, and the clean-installation-plus-`configure` qualification in the reference VM. The split isolates changes to the engine, the ISO build, and the VM qualification, which are critical and expensive to verify. To avoid rework, the 02-15 scripts are designed from the start around a target-root and context abstraction. The story is only registered once 02-16 completes. [DEC-001]

## Providers

The skeleton selects `foot` as the terminal provider and `bash` with the `starship` prompt as the interactive-shell provider, and records both in `docs/mvp-scope.md` as a reviewed update owned by Story 4.2. foot is lightweight, CPU-rendered, and robust in the reference VM; the loss of ligatures and of the kitty graphics protocol is accepted, and tmux covers tabs and splits. Bash is already delivered by installation, so `configure` does not change the login shell; Starship adds one `extra` package with provenance and is initialized from neutral bash user configuration that carries no personal content. The maintainer's personal Starship configuration arrives later from an external repository through Story 4.6, and interactive conveniences missed from zsh can be added later as a reviewed update. How the user configuration is applied without overwriting the user's files is described under User configuration [DEC-002, TODO-001, DEC-005].

## Layout and step order

`operations/configure` stays the single entry point and owns the common orchestration: arguments, validation before any mutation, the run lock, the execution context, evidence, and the outcome. It delegates the work to step scripts under `capabilities/`, which only apply their own capability. Shared configure helpers for packages, managed files, units, user execution, and postconditions live in `capabilities/lib/`. The execution order is an explicit, hand-readable Bash array in `capabilities/configure-steps`, with no discovery and no dependency graph, so an ordering mistake is visible in review (ADR 0010) [DEC-003].

The skeleton populates five capabilities: `desktop/login/` for SDDM with its stock theme and no autologin plus uwsm, `desktop/compositor/providers/hyprland/` for the minimal Hyprland configuration, `desktop/terminal/` for foot, `workflow/shell/` for bash with Starship, and `workflow/tmux/` for tmux. Each has a Bash `apply` script that declares its prerequisites, the context variables it expects, and its postconditions, and keeps the native files it applies next to it. Only `desktop/login/` is new to the architecture tree, which `docs/architecture.md` gains [DEC-003, DEC-001].

## Package provenance

The skeleton uses only official Arch repository packages, so provenance takes the lightest native form. Each capability carries a plain-text `packages` file with one `<name> <repository>` line per package, which feeds `pacman -S --needed` directly and is not a new schema. `capabilities/README.md` states once the provenance policy of the official-repository source class: pacman signature verification against the keyring provides identity, Arch is responsible for package content, and the MirrorOS maintainer is responsible for inclusion. On every run `configure` checks that the declared repository matches the one pacman resolves, and the evidence records the resolved version and repository. `inventory/` stays empty; the AUR and external-URL provenance forms are defined by the first slice that consumes them, expected to be Story 4.6 or 4.7 [DEC-004].

## User configuration

`configure` prefers system-wide defaults wherever a tool reads them, such as `/etc/xdg/foot/foot.ini`, `/etc/tmux.conf`, and `/etc/sddm.conf.d/`, so `$HOME` stays untouched and any later user configuration overrides them naturally; the real lookup paths are confirmed during implementation. Managed user files are used only where no system-wide alternative exists. The main case is the Hyprland configuration, written in Lua as `~/.config/hypr/hyprland.lua` because hyprlang is deprecated since Hyprland 0.55. A managed file carries a "managed by MirrorOS configure" header and is created when absent and updated only when it carries the header and differs. When it lacks the header or is a symbolic link, for example into an external configuration repository, it is left untouched and reported as owned by the user, and its postcondition only checks existence. `~/.bashrc` is never rewritten: one marked, idempotent block sources a managed file such as `~/.config/mirroros/bash/starship.bash`. Every write under `$HOME` runs as the user, never as root [DEC-005, DEC-002].

The architecture language table already admits Lua as tool-local configuration for Hyprland, so no architecture change is needed [RISK-001]. Because `hyprland.lua` takes precedence over `hyprland.conf`, either file without the MirrorOS header marks the Hyprland configuration as owned by the user: `configure` then creates no Lua file, reports the configuration as user-owned, and only checks that a Hyprland configuration exists, so the user always wins on reruns [DEC-006, TODO-002].

## Invocation and privilege

On the running system `configure` is invoked as `sudo operations/configure [--user <name>]`, and the target user defaults to `SUDO_USER`. Running without root, or with a target user that is missing, nonexistent, or root, ends with outcome `2` before any mutation. Work under `$HOME` always runs through `runuser -u <user> --`. This is the same mechanism the installer context needs inside `arch-chroot`, so both contexts share one privilege model: system steps are explicit, and user steps never run as root. Escalating with `sudo` per step was rejected because it needs repeated prompts or a keepalive and has no equivalent in the chroot [DEC-007, DEC-005, DEC-001].

## Execution-context abstraction

Step scripts say what to do and shared helpers decide how, depending on where `configure` runs. The orchestrator sets `CONFIGURE_CONTEXT` (`running` or `target`) and `CONFIGURE_ROOT` (`/` or the mounted target path). Steps never run effectful commands directly: they call helpers in `capabilities/lib/` for package installation, managed system files with owner, mode, and header, user files and user commands through `runuser`, unit enabling, and read-only queries. Plan 02-15 implements only the running context with `/`, which is the only one it can prove. Plan 02-16 adds the target branch (`arch-chroot`, paths under the target root, units enabled but never started) inside the helpers alone, so no step script is edited. A contract test fails if an `apply` script calls `pacman`, `systemctl`, `install`, or `runuser` directly, which keeps later slices within the rule. No public `--target-root` option exists until 02-16 delivers and proves it [DEC-008, DEC-001, DEC-007].

## Units and graphical login activation

`configure` enables SDDM but never starts or restarts it, in either context. Starting it would switch a TTY run to the login screen mid-run, restarting it would end a session SDDM started, and the installer context cannot start units at all. The postcondition checks that `display-manager.service` resolves to `sddm.service`, that no other display manager is enabled, and that the default target is graphical, and the final outcome tells the user that the graphical login is available at the next boot. The full SDDM → uwsm → Hyprland → foot path is proven by rebooting the reference VM after `configure`, as plan verification rather than a `configure` self-check [DEC-009, DEC-008].

## Verification strategy

Configurations are proven in the VM, not by automated tests, because after this phase the workflow is always VM exploration first and registration second, and tests of what a capability applies would only restate its script. `configure` checks its own postconditions on every run. Automated tests are kept to the small shared mechanism and to the risks a freshly installed VM rarely exercises: the entry-point contract (arguments, root, and target user ending with outcome `2`) in `tests/operations/configure.contract.bats`, which changes anyway because it tests help-only behavior; the static check that no `apply` script calls an effectful command directly; the managed-file rules and the idempotent `.bashrc` block, which protect the user's own files on a real machine; and the pacman guard against partial upgrades. They run without root through a test-only `MIRROROS_CONFIGURE_ROOT` that replaces `/` in the running context, following the `MIRROROS_DISCOVERY_ROOT` precedent, with doubles only for `pacman`, `runuser`, and `id`. Later slices add only `apply` scripts and native files validated in the VM, add tests only when they change the mechanism, and are covered by the static check automatically [DEC-023, DEC-010, DEC-008].

The remaining outcomes, SIGINT and rerun, the lock, the evidence format, `SessionDir`, and the postconditions are covered by the VM checkpoint, which includes interrupting a run with `Ctrl+C` and rerunning it, and a rerun without changes [DEC-023, DEC-016, DEC-020].

The reference VM stays headless with its standard VGA, because changing `reference-vm.conf` is an explicit qualification decision and software rendering would make Hyprland fragile there. The graphical path is a human checkpoint in a VM with a display and `virtio-vga`, booted from a disk installed by the MirrorOS installer, using either the maintainer's laboratory or a QEMU invocation documented in the plan. It covers SDDM password login, the uwsm-started session, the three minimal bindings, foot with bash and Starship, tmux creating and managing a session, and a rerun without mutation. VM GPU problems are recorded as evidence, and any VM-specific need of Hyprland is raised as a finding rather than anticipated. Whether the reference harness gains a display or `screendump` capture for the automated clean-installation proof is decided by plan 02-16 [DEC-010, DEC-001, DEC-009].

## Minimal bindings

The managed `hyprland.lua` carries only three bindings: `SUPER + Return` opens foot through `uwsm app -- foot`, `SUPER + SHIFT + Q` closes the active window, and `SUPER + SHIFT + E` exits the session through `uwsm stop`. The close binding deliberately requires `SHIFT` so that a quick accidental `SUPER + Q` closes nothing. Exiting through `uwsm stop` instead of the Hyprland `exit` dispatcher, and launching applications through `uwsm app --`, follow the uwsm and Hyprland recommendations so graphical-session units stop cleanly. The file carries no visual customization, which belongs to Story 4.8, and no `autogenerated` line; Story 4.3 may adjust the bindings when it sets the conventions [DEC-011, DEC-005].

## Greeter display server

The SDDM greeter runs on Hyprland in Wayland mode, as `docs/mvp-scope.md` already decides, so the login screen does not use an X server, although the `sddm` package still installs `xorg-server` as a dependency (see Session list). A managed `/etc/sddm.conf.d/` drop-in sets `DisplayServer=wayland` and a Hyprland `CompositorCommand`, together with a minimal managed greeter `hyprland.lua` without logo, splash, or animations under a MirrorOS system path such as `/usr/share/mirroros/sddm/hyprland.lua`; both belong to the Hyprland provider, as described under Provider boundary. The approach follows Omarchy's working configuration, and the launch command is `start-hyprland`. SDDM still labels its Wayland mode experimental, so the VM checkpoint is what validates it; falling back to an X11 greeter would contradict the frozen scope and would require a reviewed update with evidence, and is not anticipated [DEC-012, DEC-010, DEC-005].

## Keyboard layout

The greeter and the session use the keyboard layout of the system, so the password typed at the login screen matches the console. As in Omarchy, the layout is read at runtime rather than copied at configuration time: the Hyprland provider installs one shared module, `/usr/share/mirroros/hypr/keyboard.lua`, which reads `XKBLAYOUT` from `/etc/vconsole.conf`, falls back to `KEYMAP`, and finally to `us`. The greeter `hyprland.lua` and the managed session `hyprland.lua` load it with `require` by absolute path, so a later `localectl` change applies at the next greeter or session start without rerunning `configure`, and a user-owned session configuration is left untouched. `configure` still validates the resolved value before any mutation as a known XKB layout in the `xkeyboard-config` `base.lst`; a console-only name ends with outcome `2` and an actionable message instead of a guessed translation. The non-Latin `us` prepend, variants, options, and multiple layouts stay outside the skeleton, and whether `localectl set-x11-keymap` writes `XKBLAYOUT` into `/etc/vconsole.conf` is checked during implementation [DEC-021, DEC-013, DEC-012, DEC-006, DEC-017].

## Runtime and code delivery

`configure` depends only on Bash and the tools delivered by the base installation and `pacman`; it needs no Node.js, `git`, or other package absent from the base, and its prerequisite validation checks this explicitly so the same code runs on the installed system and later inside the chroot. A damaged checkout with missing scripts or helpers ends with outcome `6`, as for the other lifecycle commands. In plan 02-15 the code reaches the installed VM through a documented manual laboratory step outside the product, such as a `git archive` of the tested commit or a clone after installing `git`. Plan 02-16 decides how the installer leaves the code on the target so reruns need no clone. The "no manual steps" rule of the common contract applies to the 02-16 clean-installation proof, before which the story is not registered [DEC-014, DEC-001, DEC-008].

## Evidence

Evidence lives on the configured system rather than in the checkout, so a root run leaves no root-owned files in the user's repository and the location works in both contexts. The default is `/var/log/mirroros/configure/<run-id>/` under `CONFIGURE_ROOT`, mode `0700` and owned by root, and `--output <dir>` selects an absent or empty directory as `install` does. A run writes `configure.log` with each step, its commands, and their output; `configure-run.tsv` with a run header (context, target user, code identity, start, end, outcome, failed step) and one line per step carrying its status (`changed`, `unchanged`, `failed`, `not_run`) and postcondition; and `packages.tsv` with the resolved name, version, and repository of each package [DEC-015, DEC-004, DEC-014].

The records are line-oriented text that Bash writes without escaping, with tabs and newlines in values replaced. `configure` writes no JSON and does not depend on `jq`: installing `jq` first would be a networked mutation that loses evidence exactly when prerequisites fail, a mirror is down, or a run is interrupted, and no 4.2 consumer needs JSON. If `verify` needs structure in Epic 5 it parses these files with Node.js, and `jq` enters as a personal tool with Story 4.6. Story 4.2 has no secret inputs, so evidence is secret-free by construction; because Gitleaks is not on the target, evidence is scanned on the development host during the checkpoint [DEC-015, DEC-010].

## Outcomes, lock, and interruption

`configure` uses the architecture's normalized outcomes rather than the engine's `128+n` signal codes, because a configuration run can always be rerun. Outcome `0` means every step completed and every postcondition holds, including a rerun that changes nothing and reports the postconditions as already satisfied. Outcome `2` is always raised before any mutation: invalid arguments, not running as root, an unresolvable target user, a keymap that is not an XKB layout, a missing base tool, a declared-repository mismatch, or another run holding the lock. Outcome `3` is an explicit SIGINT cancellation, `4` is a completed run whose postconditions do not all hold, `5` is a failed step command or a SIGTERM or SIGHUP termination, and `6` is a damaged checkout or an internal contract violation [DEC-016, DEC-007, DEC-013, DEC-004, DEC-014].

Execution is fail-fast: the first failing step stops the run, and later steps are recorded as `not_run`. For outcomes `3`, `4`, and `5` the final output names the step, the reason, and the next action, which is to rerun `sudo operations/configure`, and never claims readiness. Concurrent runs are excluded by `flock` on `/run/mirroros/configure.lock` under `CONFIGURE_ROOT`. There is no resume state: every rerun starts from the beginning and each step reports `changed` or `unchanged` from its own postconditions, as ADR 0010 requires [DEC-016, DEC-015].

## Provider boundary and dependency validation

Everything specific to Hyprland lives beneath `desktop/compositor/providers/hyprland/`: its packages, the session `hyprland.lua`, the greeter `hyprland.lua`, and the SDDM drop-in that sets `DisplayServer=wayland` and the Hyprland `CompositorCommand`. `desktop/login/` stays provider-neutral with the `sddm` package, a drop-in for the stock theme without autologin, unit enabling, the graphical default target, and `uwsm` as the compositor-independent session start mechanism. Replacing the compositor therefore replaces one directory and one `configure-steps` entry and leaves login, terminal, shell, and tmux untouched; this refines the greeter placement of DEC-012 [DEC-017, DEC-012, DEC-003].

Before any mutation the orchestrator reads the `packages` files of every listed step and checks with read-only `pacman -Sp` that each package exists in its declared repository. Every missing or mismatched package is listed and the run ends with outcome `2`, which reports missing provider dependencies before mutation and implements the provenance repository check in one place. The check relies on current sync databases, and how they are refreshed without a partial upgrade is decided separately [DEC-017, DEC-004, DEC-016].

## Package installation and upgrades

Adding a package to the repository and rerunning `configure` installs that package without upgrading the system, and no path can produce a partial upgrade. By default missing packages are installed with `pacman -S --needed --noconfirm` against the existing sync databases, which `pacstrap` leaves fresh on a new installation and which otherwise match the last full upgrade, so dependencies resolve against the installed versions. Before any mutation a guard checks `pacman -Qu`: when packages are missing and it lists upgradable packages other than `[ignored]` ones, the databases are ahead of the system, and the run ends with outcome `2` advising `sudo pacman -Syu` or a rerun with `--refresh`. The explicit `--refresh` option installs the missing packages with `pacman -Syu --needed --noconfirm` instead, and only when packages are missing, so `configure` never performs routine system updates, which remain with Story 4.7. `pacman -Sy` without `-u` is never used [DEC-019, DEC-017].

When every declared package of a step is installed, `pacman` is not invoked and the step is `unchanged`. Absent sync databases end with outcome `2`. A mirror that no longer serves a recorded version fails the download before the transaction starts, so the run ends with outcome `5`, leaves the system unchanged, and advises upgrading when convenient or using `--refresh`; on a machine not upgraded for a while, adding a package may therefore require an upgrade first, an accepted Arch constraint that always fails safely. Signature and keyring failures also end with outcome `5`, and the keyring is never changed automatically. The evidence records the mode (`default` or `refresh`) and the guard result. This replaces the earlier always-upgrade approach [DEC-019, DEC-018, DEC-016, DEC-015].

## Session list

The `hyprland` package ships both a direct `hyprland.desktop` session and `hyprland-uwsm.desktop`, so SDDM would otherwise offer a session that bypasses uwsm. The Hyprland provider therefore manages `/usr/share/mirroros/wayland-sessions/`, which contains only a symbolic link to `hyprland-uwsm.desktop`, and its SDDM drop-in points `[Wayland] SessionDir=` at it. Using a link keeps package updates of the session file flowing, and no package file is edited. The postcondition requires exactly one listed session whose `Exec` contains `uwsm start` and `hyprland.desktop`, and a package change that breaks this ends the run with outcome `4` instead of silently offering a non-uwsm session. This is stricter than Omarchy, which adds its own session next to the upstream ones [DEC-020, DEC-017].

The official `sddm` package requires `xorg-server` and `xorg-xauth`, so both are installed even though the greeter runs on Wayland, as they are in Omarchy; the resolved package list records them and DEC-012 is unchanged. The greeter is launched with `start-hyprland`, as confirmed in Omarchy's current configuration [DEC-020, DEC-012]. Omarchy's runtime reading of the keyboard layout was adopted, as described under Keyboard layout [TODO-003, DEC-021].

## Font and tool defaults

The skeleton keeps tool configuration to the minimum. Starship needs a Nerd Font for its default glyphs, and `sddm` depends on the virtual `ttf-font`, which pacman would otherwise satisfy with an implicit, unreviewed choice. `desktop/terminal/packages` therefore declares `ttf-jetbrains-mono-nerd` from `extra` as a provisional font that is expected to satisfy `ttf-font` before `sddm` is installed, which implementation verifies. foot receives a minimal system-wide `/etc/xdg/foot/foot.ini` that only sets `font=JetBrainsMono Nerd Font:size=11`. Starship ships no `starship.toml` and tmux ships no `/etc/tmux.conf`; both run on their defaults, and the maintainer's own configuration arrives with Story 4.6. Typography stays open in `docs/mvp-scope.md` under Story 4.8, with a note that Story 4.2 uses a provisional font that Story 4.8 may replace [DEC-022, DEC-002, DEC-005, DEC-004].

## Documentation and attribution

Documentation changes together with the behavior. `operations/configure` and its help describe the running-context behavior and mark the installer context as pending for plan 02-16, and `docs/procedures/configure.md` is rewritten with the implemented contract: invocation with `sudo`, `--user`, `--refresh`, and `--output`, prerequisites, effects, evidence, outcomes, recovery, the warning never to run `pacman -Sy` alone, and the flow for adding a package and rerunning. The `configure` row of `README.md` moves from help only to the running installed system with the installer context pending. `docs/mvp-scope.md` records foot and bash with Starship as reviewed updates and notes the provisional font under Typography. `docs/architecture.md` only gains `capabilities/lib/`, `capabilities/configure-steps`, `capabilities/README.md`, and `desktop/login/` in its tree [DEC-024, DEC-002, DEC-022, DEC-003].

A new `capabilities/README.md` explains the step contract (an `apply` script with prerequisites and postconditions, mandatory helpers, no direct effectful commands), the official-repository provenance policy, the managed-file rules, and how later slices add their steps. It cites Omarchy as the source of two ideas, the greeter on Hyprland and the runtime reading of `vconsole.conf`; because MirrorOS writes its own files, `docs/attribution.md` gains no entry unless a fragment is actually copied, in which case an MIT entry is added in the same change. ADRs and `docs/epics.md` stay unchanged. The VM checkpoint procedure is laboratory work and lives in the plan's verification section rather than in `docs/`. The interview artifacts are committed with the change [DEC-024, DEC-004, DEC-005, DEC-008, DEC-010].
