# Story 2.5 — Install the Approved Base System — Decision Log

## DEC-001
- **Question**: Should Story 2.5 be delivered as one plan or split (core engine + `ext4-systemd-boot`, then `btrfs-rescue`, then `btrfs-limine`)?
- **Context/Nuances**: The story combines an ADR superseding the ADR 0006 hand-over boundary, the `install/engine/apply` contract and implementation, the protected password channel, failure handling, a new success outcome, and 17–22 operations per storage option. `btrfs-limine` remains `experimental` (ADR 0003) and its `install_limine_snapshot_tools` step builds pinned AUR tools. The agent recommended three plans; two plans (ext4 + both Btrfs) was also offered.
- **User Response**: One single plan. Even within one plan, implementation proceeds in order as if it were three plans.
- **Decision**: Plan 02-09 covers all of Story 2.5, including all three storage options. Tasks are ordered in staged implementation slices: (1) engine core with `ext4-systemd-boot` end to end, (2) `btrfs-rescue`, (3) `btrfs-limine`. Splitting into multiple plans was rejected.
- **Status**: Accepted

## DEC-002
- **Question**: Which normative vehicle governs the engine: a new ADR, contract amendments only, or several ADRs?
- **Context/Nuances**: Per `docs/adr/README.md`, an ADR is required only for a critical selection, a design-changing prototype outcome, or an architecture exception. The engine (ADR 0002), the password transport (the architecture already allows protected prompts, file descriptors, and restricted files), the success exit (the confirmation contract is scoped "in this version"), and the no-automatic-retry policy (architecture destructive retry policy, ADR 0002) stay within accepted boundaries and belong in contracts. The hand-over change is different: ADR 0006 states "Supersede this ADR before the installation engine story changes the hand-over boundary", and its acceptance of the live-root session and automatic tty1 startup relied partly on "this delivery reaches no engine". Connecting the engine removes that premise, so the safety argument must be re-evaluated in writing. A possible second ADR trigger is noted: `makepkg` cannot run as root while the live session is root (ADR 0006), which `btrfs-limine` will face.
- **User Response**: Asked for an explanation of ADR criteria and of the hand-over; then approved the narrow version.
- **Decision**: Create a narrow ADR 0008 that supersedes only ADR 0006's hand-over boundary clause and re-evaluates live-root plus automatic startup now that the engine is reachable (the only path to the engine is bound confirmation, protected password entry, and final revalidation, demonstrated by tests). All other engine rules (inputs, digest verification, unknown-kind rejection, password transport, exits, failure/retry/cleanup, records, diagnostics) go into a new `contracts/installation-engine.md` and a new version of `contracts/installation-confirmation.md`. ADR 0008 is drafted as Proposed, approved at a maintainer checkpoint, and accepted before implementation. If the `btrfs-limine` build-user question requires an architecture exception, it may be added to the same ADR.
- **Status**: Accepted

## DEC-003
- **Question**: Which protected transport carries `account_password` from the assistant to the engine and into the installed accounts?
- **Context/Nuances**: The confirmation contract already fixes that the assistant owns entry (with repetition), the engine never prompts, and the value never appears in process arguments, environment variables, plans, logs, records, or evidence, is single-use, and is released when consumed or the run ends. The architecture allows protected prompts, file descriptors, or short-lived restricted files. A `0600` file in a `0700` directory is valid but places the secret on (tmpfs) storage and requires cleanup on every failure and signal path.
- **User Response**: Approved.
- **Decision**: The assistant reads the password twice with `gum input --password` into a local, non-exported Bash variable. It hands the value to `install/engine/apply` through an anonymous pipe on a dedicated file descriptor (for example fd 3), written with the `printf` builtin through process substitution, so it never appears in any process `argv` and never touches disk. The engine reads the descriptor exactly once at startup, before any destructive operation, closes it, and fails without touching the disk if it is missing, empty, or invalid. The value is delivered on stdin to `chpasswd` inside the chroot (`arch-chroot <target> chpasswd`), so the target's `shadow` hashes it with its default method; no live-side hashing tool is used. With `root_account: password` root receives the same value through the same path; with `locked`, root is locked. Canary tests assert absence from `/proc/*/cmdline`, `/proc/*/environ`, terminal output, logs, records, and evidence. The restricted-file transport was rejected.
- **Status**: Accepted

## DEC-004
- **Question**: What does the engine receive, and how does it guarantee that only operations represented by the approved digest are executed?
- **Context/Nuances**: Story 2.5 requires executing only what the approved digest represents and no hidden policy changes. The plan holds declarative operations without command lines; the contract already says an engine must reject unknown kinds. A root user on the live system could invoke the engine directly, so a digest argument cannot be an authorization mechanism.
- **User Response**: Approved.
- **Decision**: `install/engine/apply` is internal and invoked only by the assistant as `install/engine/apply --plan <run>/plans/NN/installation-plan.json --digest <confirmed digest> --output <run>/engine/` plus the password descriptor (DEC-003). Before reading the password or touching the disk, it reads the plan once and works from that in-memory copy (no time-of-check/time-of-use gap), validates it with `validate-plan.mjs` (format 3), recomputes the digest and requires equality with `--digest`, and rejects any unknown kind or any operation set or order that differs from the contract. It executes `operations` in plan order through a `kind → function` dispatch table, and each function uses only the plan's `parameters` and `resolved_at_apply` values, never `policy.json` or another source. Configuration assets are copied from `install/plan/assets/` only when their SHA-256 equals the plan's `source_sha256`; otherwise it fails before writing. `--digest` is integrity binding, not authorization; the authorization argument is that the only documented and tested path to the engine passes confirmation, password entry, and revalidation (ADR 0008).
- **Status**: Accepted (amended by DEC-013)

## DEC-005
- **Question**: How is the engine split between Bash and Node.js ESM?
- **Context/Nuances**: The architecture assigns native Arch integration to Bash and non-trivial structured logic to JavaScript ESM. Plan 02-07 established a Bash flow that never parses JSON itself and calls Node helpers that print plain text. `jq` is present on the ISO only as a transitive dependency and is not in MirrorOS's package list.
- **User Response**: Approved.
- **Decision**: `install/engine/apply` is a Bash orchestrator with per-group Bash functions under `install/engine/lib/` (for example `storage.sh`, `system.sh`, `accounts.sh`, `boot.sh`, `btrfs.sh`, `limine.sh`) that invoke the native commands. Node ESM provides `install/engine/load-plan.mjs` (validation, digest verification, unknown-kind rejection, and a flat NUL-delimited, shell-safe step stream of `kind` plus `key=value` pairs, so Bash needs no `jq`), an atomic `0600` record writer for `engine-run.json` reusing the `write-records.mjs` patterns, and any structured checks such as validating resolved UUIDs or offsets. Production code never imports from `prototypes/`. A Node orchestrator spawning one Bash process per operation was rejected because it splits signal handling and mount state across processes and departs from the established pattern.
- **Status**: Accepted

## DEC-006
- **Question**: How does the engine behave on failure and interruption, and what are the cleanup and retry rules?
- **Context/Nuances**: Story 2.5 requires stopping avoidable dependent operations, retaining original non-secret diagnostics and child status, and never reporting success. ADR 0002 records that the native engine can leave a disk partitioned and mounted and requires the engine contract to define retry, cleanup, and the need for a fresh disk; automatic retry is excluded by the architecture's destructive retry policy. The Ctrl+C-to-`3` mapping covers only the interactive phase.
- **User Response**: Approved.
- **Decision**: The operation sequence is linear, so the first failing operation stops all later ones; no dependency graph is introduced. Stdout and stderr of each native command go to `engine/engine.log` (plain text, no ANSI, `0600`); `engine-run.json` records the failed operation `id`, the child command, its original status, and the completed and not-started operations. The password descriptor is never redirected into the log, verified by canaries. The outcome is `failed` with exit `5` for an external tool failure and `6` for damaged code or assets, and the message states that the disk was partially modified and installation did not complete. On failure or signal, best-effort non-destructive cleanup runs (`swapoff` of an active swapfile, `umount -R` of the target); the disk is never wiped again or "undone", and a cleanup failure is recorded without masking the original error. There is no automatic retry and no resume-from-operation-N: retrying means running `mirroros-install` again, which rediscovers the new layout, generates a new plan, and requires a new confirmation. A signal during the engine is not cancellation: after cleanup the outcome is `failed` with reason `engine_interrupted` and exit `128+n`.
- **Status**: Accepted

## DEC-007
- **Question**: What does success mean in Story 2.5, given that Story 2.6 owns pre-restart installation postconditions?
- **Context/Nuances**: Story 2.6 checks bootloader, mounts, kernel, network prerequisites, zram and memory settings, and swapfile/resume before the normal restart, and withholds completion on failure. Exit `0` is unused today; `approved` with `engine_not_available` is the only positive ending. An alternative was to withhold exit `0` until Story 2.6 (for example exit `2` with `installed_unverified`), which is more conservative but makes a working installation look like a failure to status-only consumers.
- **User Response**: Approved.
- **Decision**: A new outcome `installed` with exit `0` means exactly that every operation of the approved plan completed with status 0 and its `resolved_at_apply` values were validated (well-formed UUIDs, positive integer `resume_offset`). Each operation checks its own immediate effect (for example the boot entry exists, `fstab` holds the UUIDs), but Story 2.6's postcondition suite is not implemented. The final message and the contract state "Base system installed. Installation postconditions are not verified in this version (Story 2.6)." `install-run.json` and `approval-record.json` move to `format_version` 4 with new stages (`password`, `engine`) and outcome `installed`; `approved` is no longer a terminal outcome on the normal path and `engine_not_available` is removed. Story 2.6 will later tighten `installed`/`0` to also require postconditions through its own contract change. Bootability is proven in this story by VM qualification (restart from the installed disk to a login prompt).
- **Status**: Accepted

## DEC-008
- **Question**: How is the engine phase presented (progress, success, failure), given that the frozen guided-installer reference has no such screens?
- **Context/Nuances**: The Omarchy 4.0.4 ISO (the 02-07 reference, inspected read-only outside the repository: `/root/.automated_script.sh`, `/usr/local/bin/omarchy-install-dashboard`, `omarchy-iso-cleanup-disk`, `setup-form.sh`) uses a Bash dashboard as the sole UI owner; the installer runs as a non-interactive child (`setsid`, stdin `/dev/null`) with output in an ANSI-stripped log and progress published through a JSON state file polled every 0.5 s. Its progress screen shows a centered logo, "Installing Omarchy", a 34-column per-mille bar driven by fixed per-phase bands with a time-based asymptotic floor plus a package count from the pacman local database, and rotating tips; no step list or raw output. Success shows the logo, "Installed Omarchy in <duration>", a `ttfx` effect, and a single "Reboot Now" button. Failure shows a red "installation stopped" title, the child status, a media diagnosis, last and failed phase with error, a log tail, a help link, and a menu (upload log, view full log, drop to shell, Reboot, Power off). Ctrl+C kills the child process group and exits 130 without unmounting. Any visual or workflow deviation from the reference requires maintainer approval (02-07).
- **User Response**: Asked to analyze Omarchy first; then approved the adapted version.
- **Decision**: Adopt the Omarchy model, adapted. The assistant is the sole UI owner; the engine is a non-interactive child (stdin `/dev/null`, password only on its dedicated descriptor), writes native output to `engine.log`, and publishes progress in `engine/state.json` (current operation, index/total, per-operation status) that the assistant polls. The progress screen shows the logo, "Installing MirrorOS", a 34-column bar, and the current operation's plan `description` dimmed (for example `[7/17] Install packages…`); the bar is completed operations over total plus the package signal during `install_packages`, with no time-based curve (progress not backed by work would be a false claim) and no tips. Success shows the logo, "Installed MirrorOS in <duration>", and the dimmed DEC-007 postcondition statement, with no `ttfx` effect, and a menu "Restart now" / "Return to shell" (deviating from Omarchy's single button to allow inspection and qualification). Failure follows Omarchy: red "MirrorOS installation stopped", failed operation and child status, the partial-disk-modification warning, a log tail, and the run path, with a menu "View full log" (`gum pager`) / "Return to shell" / "Restart" / "Power off"; no log upload and no media diagnosis. Ctrl+C during the engine follows DEC-006 (signal to the engine process group, engine cleanup, `128+n`). These screens are recorded as D16+ entries in the confirmation contract and approved at the maintainer's attended review.
- **Status**: Accepted

## DEC-009
- **Question**: What are the rules of the real password entry screen?
- **Context/Nuances**: The real screen replaces the explanatory D10/D11/D12 screens. The Omarchy 4.0.4 reference uses a double `gum input --password`. The confirmation contract already states that going back from any screen after confirmation clears the approval and requires renewed review and confirmation. Alternatives offered: Esc cancels the run (agent recommendation), Esc returns to review (option a), and a minimum length (option b).
- **User Response**: Approved, but with option (a) for Esc.
- **Decision**: The screen keeps the D10/D11/D12 context texts (one password for `$username`; root locked or sharing the same password per plan; when root password login is enabled, the gray line "Sharing the password does not give root an independent recovery credential.") and asks `Password>` and `Confirm>` with `gum input --password`. Validation is only non-empty and matching; on failure it shows "Password can't be blank" or "Passwords didn't match" and asks both fields again, with no attempt limit and no strength policy. Esc in either field returns to the review, discards any entered value, and clears the approval, so renewed review and bound disk confirmation are required before the password screen is reached again. Ctrl+C in either field cancels (exit `3`, outcome `cancelled`), discards the value, and the engine is never started. Final revalidation runs after entry; a failed revalidation is `invalidated` and discards the value. The `password` stage is recorded in `install-run.json` and `install.log` without length or any other value-derived data. The minimum-length alternative was rejected.
- **Status**: Accepted

## DEC-010
- **Question**: What state must the target disk be in immediately before wiping, and should the engine tear down mounts and holders as Omarchy does?
- **Context/Nuances**: Discovery already marks a disk with mounted partitions ineligible (`mounted`), but it does not detect active holders (activated LVM, open dm-crypt mappings, assembled md RAID), which the live system may auto-activate through udev. Omarchy 4.0.4 (`omarchy-iso-cleanup-disk`) forcibly unmounts, runs swapoff, deactivates LVM, closes crypt mappings on the selected disk, and then runs `flushbufs`, `partprobe`, and `udevadm settle`. Its reasons are cleaning its own leftovers from a failed attempt in the same live session, archinstall's poor tolerance of busy disks, and a consumer reinstall UX. The first reason also applies to MirrorOS: if DEC-006's best-effort cleanup fails, the target stays mounted, rediscovery marks the disk `mounted`, and the user is stuck until the live system restarts.
- **User Response**: Asked why Omarchy chose forced teardown; approved the refined version.
- **Decision**: No forced teardown of state MirrorOS did not create. Immediately before `wipe_disk_signatures`, after the password has been read, the engine checks that no partition of the disk is mounted or used as swap and that neither the disk nor its partitions have holders (empty `/sys/block/<dev>/holders` and `/sys/class/block/<part>/holders`, no `lvm`, `crypt`, or `raid*` children in `lsblk`). If anything is in use, the engine stops before the first destructive operation with outcome `blocked`, exit `2`, and reason `target_disk_in_use`, whose `next_step` names what to release manually; the disk stays untouched. The facts contract is unchanged (no new ineligibility reason). MirrorOS does clean up its own leftovers: at the start of every run, before discovery, it recursively unmounts the engine's fixed target mount point and turns off any swapfile under it, records this in `install.log`, and never touches anything outside that mount point (the equivalent of Omarchy's `--protected` mode). After `create_partition_table` and `create_partitions`, non-destructive synchronization runs (`blockdev --flushbufs`, `partprobe`, `udevadm settle`) so partition nodes exist before formatting. Forced teardown of the selected disk (the Omarchy model) was rejected because it would be a hidden effect outside the approved plan and LVM/RAID assemblies may span other disks.
- **Status**: Accepted (amended by DEC-020)
- **TODO-002**: Choose the engine's fixed target mount point (`/mnt` or a MirrorOS-owned directory such as `/run/mirroros/target`).

## DEC-011
- **Question**: Which fixed target mount point does the engine use (resolves TODO-002)?
- **Context/Nuances**: DEC-010's start-of-run cleanup recursively unmounts this mount point without asking. In the live session the user may have mounted something at `/mnt` by hand (a USB stick, another system's disk), which would then be unmounted although MirrorOS did not create it. `/run` is tmpfs on the live system. `arch-chroot`, `pacstrap`, and `genfstab` accept any path; the Arch Installation Guide uses `/mnt` only as a convention, and `genfstab -U` output does not depend on it.
- **User Response**: Approved.
- **Decision**: The engine mounts the target at `/run/mirroros/target`, created by the engine with mode `0700`. Everything under it is created by MirrorOS, so the start-of-run cleanup never affects user mounts. `/mnt` was rejected. TODO-002 is resolved.
- **Status**: Accepted

## DEC-012
- **Question**: How are mirrors, the package keyring, and package provenance handled during installation, compared with Omarchy?
- **Context/Nuances**: The live image enables no `reflector.service`; `choose-mirror.service` acts only with a `mirror=` kernel parameter, so the live mirrorlist is the `pacman-mirrorlist` default (worldwide geo mirror), which the prototypes used. `pacman-init.service` initializes the keyring at boot, and `pacstrap` copies the host mirrorlist unless `-M` is given, matching policy `mirrorlist: inherited_from_live_environment_and_recorded`. Omarchy 4.0.4 instead bundles an offline repository (~945 packages, ~3 GB) in the ISO with `SigLevel = Never`, uses its own pinned mirrors (`mirror.omarchy.org` `stable`, plus fallbacks), warms the page cache during the wizard, and deliberately does not wait for `pacman-init.service`, because on real USB hardware it can take minutes and racing it failed `pacstrap` with "required key missing from keyring". The agent first objected to `SigLevel = Never` as a security weakening and then corrected itself: disabling signatures is acceptable only for packages whose integrity is anchored elsewhere (signature-verified at build time inside an artifact with a verified checksum), never for packages fetched from network mirrors, where signatures are the only protection. MirrorOS's traceable artifact (Story 1.3) could provide that anchor. Still, Story 2.5 installs only the base set, the full environment arrives later through convergence over the network (which ADR 0006 already requires), an offline repository gains most value once the exhaustive package inventory exists (Story 3.1, known-good artifact Story 6.3), and it changes the artifact build, the mirrorlist policy, and ISO size, so it needs an ADR. Alternatives considered: online inherited mirrors (chosen), embedded offline repository, Arch Linux Archive date snapshot.
- **User Response**: Questioned why Omarchy's `SigLevel = Never` would not suit a personal distribution with exhaustive package selection; approved the revised recommendation.
- **Decision**: Story 2.5 installs online with inherited live mirrors: no reflector or ranking, `pacstrap -K` copies the live mirrorlist to the target, and `engine-run.json` records the active `Server =` lines and the mirrorlist SHA-256. Signature verification is always on; `SigLevel = Never` is never used. Before any destructive operation the engine waits visibly ("Preparing the package keyring…") for `pacman-init.service` to finish successfully, up to a generous bound (proposed 10 minutes, fixed in the engine contract); only on timeout or failure does it stop as `blocked` with reason `live_keyring_not_ready` and an untouched disk. After `install_packages`, the target's `pacman -Q` (name and version) is stored in engine evidence as a description, not a pinning policy. `pacman_options` apply only to the target `pacman.conf` in `configure_sudo_sysrq_pacman`. No local package cache, own mirror, or offline installation in this story.
- **Status**: Accepted (amended by DEC-020)
- **TODO-003**: Follow-up for Epic 3/6 through an ADR once the exhaustive package inventory exists: evaluate an offline repository embedded in the artifact, built from the inventory, signature-verified at build time, with `SigLevel = Never` only for that repository and integrity anchored to the artifact checksum, as Omarchy does. Record the principle that disabling signatures is acceptable only under such an external integrity anchor.

## DEC-013
- **Question**: Which values must live in the plan (and therefore the digest), and which may be fixed by the engine? (Amends DEC-004.)
- **Context/Nuances**: In `install/plan/generate-plan.mjs` (`parametersFor`), `install_limine_snapshot_tools`, `configure_snapper`, `create_baseline_snapshot`, and `sync_limine_snapshot_entries` have empty parameters; `enable_services` lists only NetworkManager, the time sync service, and `fstrim.timer`, although the contract says "and the option's services"; Limine initramfs hooks are absent. DEC-004 said engine functions use only plan parameters. The digest protects against change between approval and execution and against hidden policy changes; Story 2.5 requires that only operations represented by the digest run, and plan 02-05 already kept command lines out of the plan so the digest does not depend on step implementation. Fixed values such as `packages`, `sudoers`, and `kernel_cmdline` are in the plan for explainability (Story 2.3), not for the digest. The real risk of engine constants is a plan generated by one MirrorOS version executed by another; in the guided flow plan and engine come from the same read-only ISO, and the plan already carries the generating code identity (`facts_binding.commit`, `dirty`) that the engine can compare with its own embedded identity. Alternatives: (A) complete every kind's parameters in a plan format 4 (contract, policy, generator, validator, render, tests, version bump); (B) engine constants plus a code-identity binding. The user prefers simple over complex and asked for an exhaustive, reasoned recommendation.
- **User Response**: Approved option B.
- **Decision**: Engine-owned constants are allowed for option-intrinsic implementation details: Snapper configuration (root `@` only, no timeline), the pinned AUR and upstream commits of the Limine tools, Limine initramfs hooks, boot entry text, and each storage option's own services. They are enumerated per kind in `contracts/installation-engine.md`, recorded in `engine-run.json` (the AUR pins also serve as provenance for Story 3.2), and never read from `policy.json` or any other mutable source. In its pre-check, before reading the password or touching the disk, the engine rejects a plan whose `facts_binding.commit` or `dirty` differs from the engine's own embedded code identity (reason such as `engine_version_mismatch`). Values already in the plan stay there; the plan format stays at version 3 and the generator and validator are unchanged. DEC-004's rule becomes: engine functions use the plan's parameters and apply-time values plus the engine constants enumerated in the contract, bound by code identity; never `policy.json`. The accepted cost is that such constants are visible in the contract and engine record but not in the plan review.
- **Status**: Accepted

## DEC-014
- **Question**: How are the Limine snapshot tools for `btrfs-limine` built and installed?
- **Context/Nuances**: The prototype builds two AUR packages (`limine-mkinitcpio-hook`, `limine-snapper-sync`) inside the target chroot during installation: a temporary system user with a temporary `NOPASSWD: /usr/bin/pacman` sudoers entry for `makepkg --syncdeps`, a networked Gradle/GraalVM native build that needs `unshare --mount --pid --fork --mount-proc`, double pinning (AUR commit verified with `rev-parse`, upstream `#tag=` replaced by a verified `#commit=`), then `pacman -U` and removal of user, sudoers, and directory. The architecture allows AUR packages "through `yay` only after explicit `PKGBUILD` review and unprivileged build". ADR 0003 allows offering the option as experimental before its promotion conditions are met. The agent first recommended an install-time build without sudoers. The maintainer said `btrfs-limine` will likely be the preferred option in their installations (snapshot recovery from the bootloader menu), takes the "experimental" label with caution, and asked for the build-time prebuild alternative in detail. The build runs in a privileged Docker container from a Cosign-verified Arch image, performs a full pacman update, and embeds MirrorOS code under `airootfs/usr/local/lib/mirroros/` with `identity.json`.
- **User Response**: Approved the build-time prebuild.
- **Decision**: The Limine tools are prebuilt during the ISO build and embedded; nothing is compiled at installation time. The repository holds a pinned recipe (for example `image/builder/aur/limine-tools.json`: package name, AUR commit, upstream commit, explicit `makedepends`) and a rewritten build script (for example `image/builder/lib/aur-build.sh`; the prototype is not imported). A new build stage before `mkarchiso`, in the same verified container, installs the declared `makedepends` as root, then builds as a non-root container user with verified double pinning and `makepkg` without `--syncdeps` (no sudoers). The resulting `.pkg.tar.zst` files are placed in the private profile copy (for example `airootfs/usr/local/lib/mirroros/packages/`), never committed, with a generated manifest (`packages.json`: name, version, SHA-256, AUR commit, upstream commit) also recorded in artifact metadata and build evidence. The stage has its own timeout; failure fails the build. At install, `install_limine_snapshot_tools` verifies each package's SHA-256 against the embedded manifest (mismatch is `failed`, exit `6`) and installs with `pacstrap -U` or `pacman -U` in the chroot; runtime dependencies come signed from official repositories. Signatures are never disabled: local unsigned packages are accepted under pacman's default `LocalFileSigLevel = Optional`, with integrity anchored to the ISO checksum and the manifest hash (DEC-012 principle). `base-devel` and `git` are removed from `btrfs-limine` `additional_packages` in `policy.json` (plan format stays 3; only values change). The manifest is part of the artifact and is bound by code identity (DEC-013). ADR 0008 records a narrow clarification: the artifact build uses pinned `makepkg` with review and unprivileged build, while `yay` remains the installed-system path (Epic 3); this is not a privilege exception. Accepted risks: longer networked build (Gradle, GraalVM); library drift between build day and install day for old ISOs (hook is shell, native binary links forward-compatible glibc; covered by qualification and rebuilds); installed tools are foreign packages whose first `yay` update would build unpinned AUR HEAD (Story 3.2 / Epic 3); Gradle dependencies pinned by version only remain an ADR 0003 promotion condition. The install-time build was rejected. The tier question for `btrfs-limine` is handled separately.
- **Status**: Accepted

## DEC-015
- **Question**: Should `btrfs-limine` be promoted within Story 2.5, and with which ESP size and default?
- **Context/Nuances**: ADR 0003 makes `ext4-systemd-boot` the default and normative option and keeps `btrfs-limine` experimental until four conditions are met: measured ESP occupancy and an ESP size decided from it (any change to the 1 GiB ESP requires an ADR), validated persistent restore of `@` from a snapshot entry, validated recovery with a pending hibernation image, and a response to Gradle dependencies pinned by version only. The maintainer wants `btrfs-limine` as the preferred option (snapshot recovery from the bootloader menu) and wanted to skip ESP measurement; they recalled a 4 GB recommendation that the agent could not verify. Omarchy 4.0.4 offers only Limine with Btrfs and Snapper, uses a 2 GiB ESP without published measurement, builds UKIs with `limine-mkinitcpio-hook`, disables Btrfs quotas, keeps a read-only `@factory` snapshot for factory reset, and encrypts with LUKS by default. The MirrorOS prototype reached four snapshot entries on a 1 GiB ESP, and `limine-snapper-sync` stops adding entries at 85% ESP usage and prunes old ones, so an undersized ESP yields fewer entries rather than a broken system. The maintainer chose to follow the Omarchy model.
- **User Response**: Include the promotion in Story 2.5 following the Omarchy model; approved the adapted proposal (2 GiB ESP, Limine as default).
- **Decision**: A new ADR 0009 supersedes ADR 0003's tier classification and its 1 GiB ESP constraint. `btrfs-limine` becomes the default option (tier `default`); `ext4-systemd-boot` and `btrfs-rescue` remain available as `supported`. This changes the architecture's normative ext4/systemd-boot baseline, so ADR 0009 and the corresponding architecture amendment are mandatory. The ESP becomes 2 GiB for all options, decided by reasoning rather than measurement (Omarchy's value plus the tool's self-limiting behavior), as a single `esp.size_bytes` policy value without generator changes; the 20 GiB minimum disk remains enforced by the fit validation. ADR 0003's conditions are closed as follows: ESP by this decision; persistent restore of `@` by one attended validation in Story 2.5 qualification; pending-hibernation recovery as an accepted, documented risk (do not boot a snapshot while a hibernation image is pending); Gradle dependencies as an accepted limitation referred to Story 3.2. ## DEC-019
- **Question**: How are concurrent installer runs excluded, given the unconditional start-of-run cleanup of `/run/mirroros/target`?
- **Context/Nuances**: Raised in review after materialization. DEC-010/DEC-011 unmount the engine's own mount point at the start of every run to recover from failed attempts, but nothing distinguishes those leftovers from a live installation in another console. ADR 0006 keeps other consoles available and `mirroros-install` can be restarted manually, so a second explicit run could unmount the target during `pacstrap`. The `live-startup` coordination only prevents duplicate automatic starts during seeded qualification.
- **User Response**: Approved.
- **Decision**: `confirm-plan` takes a non-blocking exclusive lock (`flock -n` on `/run/mirroros/install.lock`, tmpfs) immediately after the terminal gate and before own-mount cleanup, discovery, and run-directory creation, and holds it until the flow and the engine end. The engine inherits the lock descriptor (for example fd 4) and verifies in its pre-check with `flock -n` on that descriptor that it holds the lock; if invoked without it, it tries to take the lock itself, so direct engine invocation cannot disturb an active run either. A second run exits `2` with reason `install_already_running` on stderr only, writes no run directory or records, touches no mounts, and does not wait. `flock` releases automatically when the holder dies, so DEC-010's recovery of leftovers from dead attempts still works. `discover` and `plan` are read-only and take no lock. Tests: Bats concurrency tests where a held lock makes a second `mirroros-install` and a direct engine invocation exit `2`/`install_already_running` without invoking the `umount` double, and the lock is released after success, failure, cancellation, and signals.
- **Status**: Accepted

## DEC-021
- **Question**: Within the fixed plan order (`install_bootloader` before `install_limine_snapshot_tools`), which operation deploys the Limine EFI binary, regenerates the initramfs, writes normal and snapshot entries, and what does each verify?
- **Context/Nuances**: Raised in review after materialization. `validate-plan.mjs` fixes `install_bootloader → install_limine_snapshot_tools → configure_snapper → enable_services → create_baseline_snapshot → sync_limine_snapshot_entries`. In `prototypes/storage/btrfs-limine/stage.sh`, the boot step only writes `/etc/default/limine` (`ESP_PATH="/boot"`, `SKIP_UEFI=yes` for the fallback path without an NVRAM entry, `KERNEL_CMDLINE[default]`); finalization configures Snapper, writes the mkinitcpio drop-in with the `sd-btrfs-overlayfs` hook immediately before installing the pinned packages, whose pacman transaction rebuilds the initramfs and writes the Limine entries (no `limine-update`), then enables `limine-snapper-sync.service`, takes the baseline, and runs `limine-snapper-sync`. The HOOKS drop-in cannot be written in `install_bootloader` because it references a hook that does not yet exist and any intermediate mkinitcpio run would fail. The reviewer proposed a responsibility split and noted the behavior must be checked at the pinned versions.
- **User Response**: Approved.
- **Decision**: Keep the plan order and split responsibilities explicitly. `install_bootloader` (Limine) writes only `/etc/default/limine` as an engine constant (`ESP_PATH=/boot`, `SKIP_UEFI=yes`, `KERNEL_CMDLINE` from the plan's `kernel_cmdline` plus `rootflags=subvol=@`), deploys no EFI binary, runs no tool, and verifies only the file content. `install_limine_snapshot_tools` verifies the manifest, writes the HOOKS drop-in with `sd-btrfs-overlayfs` immediately before `pacman -U` (with `SNAP_PAC_SKIP=y`), and lets the package transaction regenerate the initramfs, deploy the EFI binary to the fallback path, and write `limine.conf` with normal entries; it verifies `/boot/EFI/BOOT/BOOTX64.EFI`, a `limine.conf` entry carrying `root`, `rootflags`, `zswap.enabled=0`, and resume parameters only when planned, the referenced kernel and initramfs files, and the absence of a UKI; if anything is missing it fails without attempting an alternative mechanism. `configure_snapper` and `enable_services` behave as for `btrfs-rescue`, plus the `limine-snapper-sync.service` constant. `sync_limine_snapshot_entries` runs `limine-snapper-sync` after the baseline and verifies at least one snapshot entry pointing to the baseline with its files present. The engine contract states where each plan `bootloader_options` value (timeout, editor, fallback entry) applies under Limine, or why it does not apply. Before implementing Slice 3, a development VM check confirms that the pinned packages' transaction does exactly this; if it does not, STOP at a decision checkpoint rather than improvise (for example invoking `limine-update` or deploying the EFI binary manually).
- **Status**: Accepted
