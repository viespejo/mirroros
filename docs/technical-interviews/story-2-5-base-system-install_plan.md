# Story 2.5 — Install the Approved Base System — Consolidated Plan

## Scope and structure

Story 2.5 (FR17) applies the approved installation plan through the native Arch engine selected by ADR 0002, behind `install/engine/apply`, and replaces the `engine_not_available` hand-over left by plan 02-07. It is delivered as a single plan, 02-09, covering all three storage options. Within that plan the work is ordered in staged implementation slices, as if it were three consecutive plans: first the engine core with the default `ext4-systemd-boot` option end to end, then `btrfs-rescue`, then `btrfs-limine`, which remains experimental under ADR 0003. Splitting into separate plans was considered and rejected. How qualification and checkpoints bound each slice is still open. [DEC-001, TODO-001]

## Normative vehicle

Most engine rules stay within accepted boundaries and are therefore contract material rather than ADR material: a new `contracts/installation-engine.md` defines `install/engine/apply` (inputs, digest verification, rejection of unknown kinds, password transport, exits, failure, retry and cleanup, records, and diagnostics), and a new version of `contracts/installation-confirmation.md` replaces the `engine_not_available` ending. One narrow ADR is still required. ADR 0006 explicitly demands supersession before the engine story changes the hand-over boundary, and its acceptance of the root live session and automatic tty1 startup rested partly on the fact that no engine was reachable. ADR 0008 therefore supersedes only that hand-over clause and records why live-root and automatic startup remain acceptable once the engine is reachable: the only path to it is bound confirmation, protected password entry, and final revalidation, each demonstrated by tests. ADR 0008 is drafted as Proposed, approved at a maintainer checkpoint, and accepted before implementation begins. The `btrfs-limine` build question turned out not to need a privilege exception, since the Limine tools are prebuilt by a non-root user during the artifact build; ADR 0008 only clarifies that this build uses pinned `makepkg` while `yay` remains the installed-system path. [DEC-002, DEC-014]

## Password transport

The assistant collects the single `account_password` twice with `gum input --password` and keeps it in a local, non-exported Bash variable. It passes the value to `install/engine/apply` through an anonymous pipe on a dedicated file descriptor, written by the `printf` builtin through process substitution, so the secret never appears in a process argument or environment and never reaches disk. The engine reads that descriptor once at startup, before any destructive operation, closes it, and refuses to touch the disk if it is missing, empty, or invalid. Account operations feed the value on stdin to `chpasswd` inside the chroot, letting the target's `shadow` hash it with its default method rather than hashing on the live side; root receives the same value only when `root_account` is `password`, and is locked otherwise. Canary tests prove the value is absent from process command lines and environments, terminal output, logs, records, and evidence. A short-lived restricted file was rejected because it puts the secret on storage and needs cleanup on every failure and signal path. [DEC-003]

## Engine inputs and digest binding

The engine is an internal boundary invoked only by the assistant with the plan path of the confirmed `plans/NN/` directory, the confirmed digest, an output directory under the run, and the password descriptor. Before it reads the password or touches the disk it reads the plan once and works exclusively from that in-memory copy, validates it with the existing format 3 validator, recomputes its digest against the confirmed one, and rejects unknown kinds and any deviation from the contract's operation set and order. Operations then run in plan order through a dispatch table from kind to function, and each function consumes the plan's parameters and apply-time resolved values plus the engine constants enumerated in the engine contract, bound to the plan by code identity; the engine never consults `policy.json` or any other mutable source, so a later policy change cannot silently alter an approved installation. Configuration assets are copied only when their hash matches the plan's `source_sha256`. The digest argument binds integrity and is explicitly not an authorization mechanism, since root on the live system could call the engine directly; authorization rests on the single documented and tested path through confirmation, password entry, and revalidation recorded in ADR 0008. [DEC-004, DEC-013]

## Engine structure

The engine follows the architecture's language policy and the pattern set by plan 02-07. `install/engine/apply` is a Bash orchestrator, and per-group Bash functions under `install/engine/lib/` invoke the native commands for storage, system configuration, accounts, boot, Btrfs, and Limine. Structured work stays in Node ESM: `install/engine/load-plan.mjs` validates the plan, verifies the digest, rejects unknown kinds, and emits a flat NUL-delimited step stream that Bash can read without `jq`, which is only a transitive dependency on the ISO; an atomic record writer produces `engine-run.json` with the same patterns as the confirmation records; and small Node checks validate apply-time values such as UUIDs and offsets. The prototypes remain reference material and are never imported. A Node orchestrator spawning a Bash process per operation was rejected because it would scatter signal handling and mount state across processes. [DEC-005]

## Failure, interruption, cleanup, and retry

Because the contract fixes a linear operation order in which each step depends on the previous ones, the first failing operation stops everything after it, without a separate dependency graph. Each native command's stdout and stderr are kept in a plain-text `engine/engine.log`, and `engine-run.json` records the failed operation, the child command, its original exit status, and which operations completed or never started; the password descriptor is never redirected into these diagnostics, which canaries verify. A failed run ends with outcome `failed`, exit `5` for an external tool failure or `6` for damaged code or assets, and tells the user plainly that the disk was partially modified and installation did not complete. Cleanup is best effort and never destructive: it deactivates an active swapfile and recursively unmounts the target, never wipes again or tries to undo changes, and a cleanup failure is recorded without hiding the original error. Retrying is deliberately not automatic and never resumes from a middle operation; the user reruns `mirroros-install`, whose rediscovery sees the new layout and requires a fresh plan and a fresh confirmation. Interruption by a signal during the engine is a failure rather than a cancellation: after cleanup it records reason `engine_interrupted` and exits `128+n`. [DEC-006]

## Success outcome and records

Story 2.5 introduces a real success ending. Outcome `installed` with exit `0` means precisely that every operation of the approved plan completed successfully and every apply-time value was validated, with each operation checking its own immediate effect; it does not include the pre-restart postcondition suite that Story 2.6 owns, and the final message and contract say so explicitly. The run and approval records advance to format version 4, gaining the `password` and `engine` stages and the `installed` outcome, while `approved` stops being a terminal outcome and `engine_not_available` disappears. When Story 2.6 lands, it will tighten the meaning of `installed` through its own contract change. Withholding exit `0` until then was rejected because status-only consumers would read a working installation as a failure. Bootability itself is demonstrated here through VM qualification that restarts from the installed disk to a login prompt. [DEC-007]

## Engine presentation

The frozen guided-installer reference has no installation screens, so the engine phase adopts the model of the Omarchy 4.0.4 ISO that the reference came from, adapted to MirrorOS's truthfulness rules. The assistant remains the only owner of the console. The engine runs as a non-interactive child whose only input besides arguments is the password descriptor, keeps native command output in `engine.log`, and publishes its current operation and per-operation status in `engine/state.json`, which the assistant polls. While it runs, the screen shows the logo, "Installing MirrorOS", a 34-column bar, and the current operation's plan description. Unlike Omarchy, the bar reflects only completed operations plus the package count during package installation, never a time-based curve, because movement that no work backs would be a false claim; there are no tips. Success shows the installation duration and the statement that postconditions are not verified yet, without an animated effect, and offers "Restart now" or "Return to shell" instead of Omarchy's single button so the installed system can still be inspected and qualified. Failure mirrors Omarchy's screen with the failed operation, child status, a warning that the disk was partially modified, a log tail, and the run path, and offers viewing the full log, returning to the shell, restarting, or powering off, without log upload or media diagnosis. Interruption follows the failure rules. These screens join the contract's inventory of differences from the reference as D16 onward and require the maintainer's attended approval. [DEC-008]

## Password entry

The real password screen takes the place of the explanatory password screens while keeping their context: one password for the user, root either locked or sharing that password according to the plan, and, when root password login is enabled, the reminder that sharing it gives root no independent recovery credential. It asks for the password and its confirmation with Gum's password input and accepts any non-empty pair that matches; a blank or mismatched entry shows a short message and asks both fields again, with no attempt limit or strength policy, a minimum length having been rejected. Esc in either field behaves like going back after confirmation: it returns to the review, discards the value, and clears the approval, so the disk must be reviewed and confirmed again. Ctrl+C cancels the run with exit `3`, discards the value, and never starts the engine. Final revalidation follows entry, and a failure there invalidates the run and discards the value. Records note only that the password stage was reached, never anything derived from the value. [DEC-009]

## Disk state before wiping

The engine never tears down state it did not create. Right before the first destructive operation, with the password already read, it re-reads the disk and confirms it is still the confirmed device with the reviewed layout and eligibility, invalidating approval otherwise, and it verifies that no partition of the confirmed disk is mounted or used as swap and that no LVM, dm-crypt, or md holder sits on the disk or its partitions; anything in use stops the run as `blocked` with `target_disk_in_use`, a next step naming what to release by hand, and an untouched disk. This check lives only in the engine, so the facts contract keeps its version. Forced teardown as practised by Omarchy was rejected because it would act outside the approved plan and could disturb assemblies that span other disks. One part of Omarchy's reasoning does apply, however: a failed attempt whose own cleanup also failed would leave MirrorOS's target mounted and make the disk ineligible on the next run. Each run therefore starts, before discovery, by unmounting the engine's own fixed target mount point and turning off any swapfile beneath it, logging the action and touching nothing else. That mount point is `/run/mirroros/target`, a MirrorOS-owned `0700` directory on the live tmpfs, chosen over `/mnt` so the unconditional cleanup can never unmount something the user mounted by hand. After the partition table and partitions are written, flushing, re-reading the partition table, and settling udev make sure partition nodes exist before formatting. [DEC-010, DEC-011, DEC-020]

## Mirrors, keyring, and package provenance

Installation fetches packages online through the live environment's mirrors exactly as inherited, without reflector or ranking, and `pacstrap` copies that mirrorlist into the target; the engine records the active servers and the mirrorlist hash so the origin of the packages is traceable, and stores the target's installed package names and versions as a description rather than a pinning policy. Signature verification is never disabled. Following Omarchy's observation that `pacman-init.service` can take minutes on real USB hardware, the assistant waits for it visibly and generously during live preparation, before configuration, confirmation, and password entry, offering retry or cancellation with `live_keyring_not_ready` only after the bound expires or the service fails; the engine keeps only a defensive check that never waits. Pacman options are applied only to the installed system. Omarchy's embedded offline repository with `SigLevel = Never` was examined and is not dismissed: disabling signatures is sound when package integrity is anchored to a build-time verification inside a checksummed artifact, which MirrorOS's traceable artifact could provide, but never for packages fetched from network mirrors. Because Story 2.5 installs only the base set, the full environment arrives later over the network, and the idea changes the artifact build and mirror policy, it is deferred to an ADR once the exhaustive package inventory exists. [DEC-012, DEC-020, TODO-003]

## Plan parameters versus engine constants

The plan stays at format version 3. It already carries the values that make it explainable, and those stay in it, but several option-specific steps have no parameters, and it would be costly and contrary to keeping step implementation out of the digest to add them. Instead the engine owns the option-intrinsic details: Snapper's root-only configuration without timeline snapshots, the pinned AUR and upstream commits of the Limine tools, Limine's initramfs hooks, boot entry text, and each storage option's own services. These constants are listed per kind in the engine contract and recorded in the engine run record, where the AUR pins double as provenance for Story 3.2. The one real risk, a plan generated by one MirrorOS version and executed by another, is closed cheaply: in its pre-check the engine refuses any plan whose recorded code identity (commit and dirty state) differs from its own, so the approved digest together with that identity determines exactly what is installed. The accepted cost is that these constants appear in the contract and the engine record rather than in the plan review. Completing every kind's parameters in a new plan format was rejected as heavier than the problem warrants. [DEC-013, amends DEC-004]

## Limine snapshot tools

Because `btrfs-limine` is likely to be the maintainer's preferred option, its fragile install-time AUR build is moved into the artifact build. A pinned recipe in the repository names each tool with its AUR commit, upstream commit, and build dependencies, and a new stage before `mkarchiso`, inside the same verified container, installs those dependencies as root and builds the packages as a non-root user with the prototype's double pin verification but without `--syncdeps` or any sudoers grant. The packages and a generated manifest of names, versions, hashes, and pins travel inside the private profile copy and the artifact metadata and are never committed; a failing stage fails the build. During installation the engine only verifies each package against the embedded manifest and installs it locally, with runtime dependencies still coming signed from the official repositories. Signature checking is never switched off: pacman accepts local packages by default, and their integrity is anchored to the artifact checksum and manifest, consistent with the principle recorded for offline packages. The target therefore no longer needs `base-devel` or `git` for this option, and the manifest is bound to the plan through the code identity check. The trade-offs accepted are a longer networked build, possible library drift for very old ISOs, foreign packages whose later AUR updates fall to Story 3.2 and Epic 3, and Gradle dependencies still pinned only by version, which stays an ADR 0003 promotion condition. [DEC-014, DEC-012, DEC-013]

## Storage options and promotion of btrfs-limine

Story 2.5 also promotes `btrfs-limine`, following an adapted Omarchy model. A new ADR 0009, approved at the same checkpoint as ADR 0008, supersedes ADR 0003's tier classification and its fixed 1 GiB ESP: `btrfs-limine` becomes the default storage option, while `ext4-systemd-boot` and `btrfs-rescue` remain selectable as supported options, which also requires amending the architecture's normative ext4 and systemd-boot baseline. The ESP grows to 2 GiB for every option, as one policy value with no generator change. That size is decided by reasoning rather than measurement, because it matches Omarchy and because `limine-snapper-sync` caps its own ESP usage and prunes old entries, so an undersized ESP costs snapshot entries rather than bootability. ADR 0003's remaining conditions are closed deliberately: persistent restore of `@` from a snapshot entry is validated once in attended qualification because it is the option's reason to exist, booting a snapshot with a pending hibernation image is accepted as a documented risk, and version-pinned Gradle dependencies remain an accepted limitation for Story 3.2. The ADR rejects the rest of Omarchy's model with reasons: no UKI, since there is no Secure Boot and UKIs would enlarge every snapshot copy; no LUKS, since the root stays unencrypted; and Limine is not the only option. A read-only `@factory` snapshot for factory reset is left as a follow-up. Policy changes are limited to values, so the plan format stays at version 3, and counted qualification must cover the new default path. [DEC-015, TODO-001, TODO-004]

## Qualification

Qualification gets its own harness, `vm/reference/qualify-install`, built on the existing reference VM library, because each installation case boots twice: once from the ISO to install and once from the disk alone to prove the result boots. The reference VM configuration advances to version 2 to give installation its own deadline, since the existing 300-second global deadline cannot hold a full install. Counted cases on a clean commit drive the real guided flow on fresh disks: the default `btrfs-limine` path with hibernation and a locked root, `ext4-systemd-boot` without hibernation and with a root password, and `btrfs-rescue` with hibernation must each install, boot from disk, and accept a serial-console login with the canary password. An injected unreachable mirror must end as a retained, diagnosable failure that never reports success, and Ctrl+C at the password screen must leave the disk byte-identical. First boots capture an observation report of mounts, swap, zram, command line, snapshots, and Limine entries as evidence without turning it into the gated postconditions that Story 2.6 owns, and every piece of evidence, serial logs included, is scanned for canaries and secrets. Attended checks complete the picture without being counted: a fidelity review of the new screens, the persistent Limine restore of `@` that justifies the option's promotion, and one real hibernate and resume cycle as an observation. Physical hardware stays out of scope, and the Esc-to-review and disk-in-use paths are proved by automated tests instead of VM cases. [DEC-016, DEC-015, TODO-001]

## Command surface

The public surface does not grow. The guided assistant and its `--plan` entry both reach the engine only through review, bound confirmation, password entry, and final revalidation; a plan produced by a different artifact is turned away before review, so the user is never asked to confirm or type a password for a plan that could not run. No public apply command or non-interactive mode exists, the engine remains an internal boundary, and no flag bypasses confirmation, password entry, or the terminal gate, as the architecture requires. The `discover` and `plan` subcommands and help keep their behavior, while help text and the install procedure are updated to say that installation is now real. [DEC-017, DEC-013]

## Delivery order, checkpoints, and documentation

The plan opens with normative work and no code: ADR 0008 and ADR 0009 as proposals, the new engine contract, the fourth version of the confirmation contract, the plan-contract changes to tiers, ESP, and default option, and drafted amendments to the architecture, PRD, and epics, whose Story 2.5 criteria still name ext4 with systemd-boot as the default. The maintainer reviews these before anything is implemented, after which the ADRs are accepted and the amendments applied. Implementation then proceeds in three slices that behave like consecutive plans. The first delivers the engine core with `ext4-systemd-boot`, the password channel, the new screens, the pre-checks, cleanup, tests with canaries, and the installation harness. The second adds `btrfs-rescue`. The third adds the prebuilt Limine tools, `btrfs-limine`, and its promotion in policy. Each slice ends with a development VM run that is never counted, a short checkpoint, and its own commit. Counted qualification follows on a clean build, with defects fixed in separate commits and the cases repeated at the new head, and attended checks of screen fidelity, persistent Limine restore, and hibernation precede final acceptance. Procedures, the contracts index, and these interview artifacts are updated with the changes they govern; attribution changes only if third-party content is actually incorporated, since Omarchy served as a reference rather than a source. [DEC-018, DEC-001]

## Run exclusion

The unconditional cleanup of the engine's own mount point is only safe if no other installation can be running, so every guided run takes a non-blocking exclusive lock on a tmpfs lock file right after the terminal gate, before cleanup, discovery, or any run directory exists, and holds it through the engine, which inherits the descriptor and confirms it holds the lock, or takes it itself when invoked directly. A second run fails immediately with `install_already_running`, leaves no records, and touches no mounts. Because the kernel releases the lock when its holder dies, leftovers from a dead attempt can still be recovered by the next run. Read-only discovery and planning take no lock. Concurrency tests prove that a held lock stops both a second assistant and a direct engine call before any unmount, and that the lock is released on every ending. [DEC-019, DEC-010, DEC-011]

## Final pre-wipe ordering

Waiting for the live keyring belongs to live preparation, where the network and clock are already checked, so the potentially slow `pacman-init.service` is resolved before the user configures, confirms, or types a password, and the time between final revalidation and wiping shrinks to seconds. The engine nevertheless re-verifies the target at the last possible moment, because an occupancy check alone cannot tell that the device behind a path is still the confirmed disk. Its pre-check order is fixed: the inherited lock, the code identity, plan validation and digest, a non-waiting keyring check, a single read of the password, and finally, immediately before wiping, a fresh read-only look at the disk compared with the plan through the existing safety comparison for identity, layout, and eligibility, together with the occupancy check. A changed disk invalidates approval with the existing identity or layout reason, discards the password, and leaves the disk untouched; nothing before that block writes to disk. [DEC-020, DEC-010, DEC-012]

## Limine boot readiness

The plan's fixed order places `install_bootloader` before the Limine tools exist, so responsibilities are split explicitly rather than left to the implementer, following the prototype's evidence. `install_bootloader` only writes Limine's defaults file with the ESP path, the fallback-path setting, and the plan's command line, and checks that content without claiming bootability. Installing the prebuilt tools is the step that makes the disk bootable: the overlay hook drop-in is written immediately before the local package transaction, whose own hooks regenerate the initramfs, deploy the EFI binary to the fallback path, and write the normal entries, and the engine then verifies those files and fails rather than improvising if any is missing. Snapper configuration, service enablement, and the baseline follow, and the final step writes and checks the snapshot entries. The engine contract also states how each planned boot option maps onto Limine. Because this relies on the pinned packages' behavior, Slice 3 begins by confirming it in a development VM and stops for a decision if reality differs. [DEC-021, DEC-014, DEC-015]

## Qualification coverage by path

The counted installation cases are chosen to exercise every distinct code path rather than every combination. Four installations cover them: the default `btrfs-limine` with hibernation and a locked root, `btrfs-limine` without hibernation, `ext4-systemd-boot` with hibernation and a root password, and `btrfs-rescue` without hibernation, alongside the failure and password-cancellation cases. Each storage option and each hibernation state is installed and booted at least once, and the real runs reach both resume-offset methods, systemd-boot and Limine with and without resume, and Btrfs with and without the swap subvolume. The acceptance criterion claims exactly this coverage; the two remaining combinations are covered by tests with doubles and are not claimed as qualified. A full six-installation matrix was considered and left aside as more machine time than the evidence gain warrants. [DEC-022, DEC-016]
