# Quattro notification integration — Consolidated Plan

Plan 02-42 has no dependencies. First, integrate the tested Quattro-derived notification card and engine code into the MirrorOS product shell and run a short private D-Bus check in the VM before replacing the installed shell. Then deploy to the reference VM with `configure`, restart its graphical session, and verify the installed engine, real bindings, sender and migrated consumers. Before deployment, capture a rollback point covering both the installed runtime and private state; the new runtime can rewrite that state even though `configure` does not. Do not deploy elsewhere. [DEC-015] Remove the built-in notification panel rather than importing the scratch panel. Defer the while-locked counter to a future notification-center plugin; the bar-to-panel acknowledgement test is no longer in scope. Removing the panel does not itself change on-disk history or retention. As a regression check, verify that Weather still receives lock and unlock state through the existing `lockChanged` / `lockedNow` contract when the engine is replaced. Keep the runtime marker reader without the notification counter. Do not change `capabilities/desktop/lock/` or exercise real lock hooks in the private test. [DEC-001, DEC-004]

After private engine validation, adopt the Omarchy `v4.5.0` notification keybindings in a separate commit: `Super+,` contextual action; `Super+Shift+,` dismiss all; `Super+Ctrl+,` keyboard navigation; `Super+Alt+,` dismiss newest; `Super+Shift+Alt+,` replay history; `Super+Ctrl+Alt+,` toggle Do Not Disturb. The latter replaces the removed panel shortcut. The contextual action cannot execute sender-supplied commands, and unrelated bindings remain unchanged. [DEC-002, DEC-004, DEC-011]

After the private engine check passes, validate delivery of the engine, bindings and shared sender in the installed reference VM before migrating the validated consumers in separate commits. Validate each consumer in the VM. [DEC-001, DEC-004, DEC-015]

Keep standard D-Bus actions on live notifications, including the fingerprint invitation's `setup` response to its own service. Recovered cards do not recreate the sender relationship. Reject executable command hints on intake and discard executable fields when loading legacy live or history records, while keeping older notification content readable. This intentionally drops Quattro's ability to leave a command launcher behind after the sender exits or the shell restarts; no identified product consumer requires it. Do not add a token, sender allowlist, or persistent action registration channel in this plan. If a concrete consumer later needs persistent actions, start with a fixed operation and validated data, not arbitrary commands. [DEC-002]

Use the tested Quattro candidate as the notification engine base, not as a replacement for the entire MirrorOS shell. Reuse its cards, stacks, navigation, actions, and expiration; retain the MirrorOS state paths. Verify legacy `live.json` and `history.json` with test copies on the VM's private D-Bus; verification of the while-locked state is deferred with the counter. Retain the candidate's transient filter for incoming notices without trying to infer which legacy rows were transient. Legacy notification content remains readable, subject to the retention limit; executable fields are deliberately discarded under the approved execution boundary. [DEC-002, DEC-003, DEC-004, DEC-008]

Use Omarchy 4.5's fixed history retention: keep at most 100 entries closed within the previous 24 hours. Legacy seven-day and disabled-history preferences no longer govern retention. Verify that older entries are pruned and that eligible new notifications can be stored despite a legacy disabled-history preference, using copies only. [DEC-008]

Work one part at a time. Before moving on, explain what changed, what behavior was preserved, and how the part was verified. Verify state compatibility with synthetic copies in the private run, which must not rewrite installed state. The subsequent installed VM run uses normal runtime persistence only after the rollback point is secured. [DEC-003, DEC-015]

Match Omarchy 4.5 for global silencing: retain manual Do Not Disturb and omit global timed snooze. Users must switch Do Not Disturb off explicitly. This decision does not resolve per-source snooze or the screen-sharing offer. [DEC-005]

Omit per-source timed snooze as well as global timed snooze. MirrorOS will no longer offer a shell control to temporarily silence only one notification source; manual Do Not Disturb remains. The screen-sharing offer is still a separate decision. [DEC-005, DEC-006]

Follow Omarchy 4.5 by omitting notification-specific screen-sharing detection and the timed silence offer. Screen sharing itself is unchanged, and starting a share does not automatically enable Do Not Disturb. Users can enable it manually. [DEC-005, DEC-006, DEC-007]

The new notification engine ignores the legacy `notifications` section of `shell.json` and uses the validated candidate behavior. Leave the old section intact for rollback, without changing how the rest of the shell reads or writes its own preferences. The verification-code exception under Do Not Disturb remains a separate policy decision. [DEC-009]

Use the candidate's `quiet.json` reader and writer at the existing MirrorOS state path. Preserve the stored `dnd` boolean, ignore all legacy fields rather than promoting a timed snooze to manual Do Not Disturb, and write only `dnd` on the next normal runtime save. Do not copy prototype state or add an installer migration: `configure` does not touch user preferences or private shell state. Verify on test copies; after a runtime rewrite, rollback can read `dnd` but cannot recover the discarded fields. [DEC-005, DEC-006, DEC-010]

Keep the candidate's card body click behavior: invoke a live sender's standard `default` action when present, then close the card; otherwise just close it. Do not add window-focus or link-opening fallbacks to that click. Explicit buttons retain their behavior. [DEC-002, DEC-012]

Deliver the shared sender at `/usr/share/mirroros/shell/notifications/mirroros-notification-send` in the existing `desktop/shell` runtime. Product components call that absolute path. After publishing the runtime, create `/usr/bin/mirroros-notification-send` as a convenience symlink with the existing non-overwriting link helper; callers do not depend on the alias. Do not add or reorder configure steps. Validate the sender before migrating the first consumer, and account for a missing sender during a partial update or an active session: only the notice may fail, not the caller's primary operation. [DEC-013]

After validating the engine and delivering the shared sender, migrate consumers in five independently verified commits: Reminders (script and form), Battery, Capture, Clipboard History, and Fingerprint. Fingerprint keeps direct `notify-send --wait`; only its tested glyph changes. Explain and verify each part before moving on. [DEC-001, DEC-013, DEC-014]
