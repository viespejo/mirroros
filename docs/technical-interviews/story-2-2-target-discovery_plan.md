# Story 2.2 — Target discovery and normalization: Consolidated Plan

## Context

Story 2.2 (FR10, FR32, FR34, FR35) builds the first production code under `install/`: MirrorOS inspects a supported target (reference VM or target laptop) without modifying it, normalizes the facts, and validates them before any plan exists. It builds on ADR 0002 (native engine), ADR 0003 (three storage options, selector deferred), and ADR 0004 (Gum as presentation layer). The live ISO currently ships neither `nodejs`, `pciutils`, `git`, nor the MirrorOS code; prototypes delivered their scripts through NoCloud.

## Scope

This plan covers Story 2.2 only: read-only discovery, normalization that keeps precedence layers distinguishable, and validation that exits with normalized statuses. Plan generation and digest (2.3), confirmation (2.4), the installation engine (2.5), and hardware rules plus the storage selector (2.6, ADR 0003) are out of scope. Within 2.2, the "detected selection" layer records detected capabilities such as GPU vendor, battery presence, and virtualization, but does not yet map them to configuration choices. [DEC-001]

## Runtime and delivery

Discovery is split by language: Bash collectors read `/sys`, `lsblk -J`, `ip -j`, `systemd-detect-virt`, and `dmidecode`, detecting graphics through `/sys/bus/pci` so that `pciutils` is not required, while normalization and validation run in Node.js ESM as the language policy prescribes [DEC-002].

Because the live ISO must be rebuilt anyway to add `nodejs`, this plan also embeds MirrorOS production code into the ISO (at least `install/`, plus whatever is needed from `operations/` and `hardware/`), with the source commit recorded in the artifact metadata so that the traceability established in Story 1.3 extends to the embedded code. This touches `image/builder/` and `image/archiso/` and requires an ISO rebuild and a boot requalification of the new bundle through the Story 1.4 path. NoCloud remains a development-only channel for fast iteration; counted qualification runs use the embedded code at a clean commit. Splitting embedding into a separate plan was considered and declined, and so were a Bash-plus-`jq` implementation (contrary to the language policy) and host-side normalization (unusable on the laptop) [DEC-002].

The code reaches the ISO through a build-time capture rather than through a committed copy: `image/builder/lib/source-capture.sh` additionally captures an explicitly declared list of repository subtrees (no globs; for example `install/`, `hardware/`, `targets/`, and the needed parts of `operations/`) with the same clean (`git archive`) and dirty (copy) mechanism it already applies to `image/archiso/`, and places them in the captured profile at `airootfs/usr/local/lib/mirroros/`. The existing Gitleaks scan of the captured profile therefore covers the embedded code. `artifact-metadata.json` gains an `embedded_code` block with the ISO path, the subtree list, and a tree hash per subtree, and an identity file inside the ISO carries the commit and `dirty` state so that discovery can record which code produced its output. Committing a copy or symlink under `airootfs/` was rejected because it duplicates ownership and the builder already rejects symlinks leaving the profile; a local pacman package was rejected as premature and as Story 3.2 provenance work [DEC-003].

## Entry point

Discovery is reached through the existing lifecycle interface: `operations/install` gains a `discover` subcommand that delegates to `install/discovery/` and to normalization, while `--help` keeps its current behavior and both the argument-less invocation and any other argument keep returning `2`, because full installation remains pending. Inside the ISO the command is placed on `PATH` through a literal symlink in `airootfs` (tentatively `/usr/local/bin/mirroros-install` pointing to `/usr/local/lib/mirroros/operations/install`). `docs/procedures/install.md` and `tests/operations/install.contract.bats` change with it, and Stories 2.3–2.5 extend the same command rather than adding parallel surfaces. A standalone `install/discovery/discover` executable was rejected for creating a second user-facing surface [DEC-004]. The symlink name and arguments are fixed in the command interface section [DEC-015].

## Target selection and supported boundary

The target is always named explicitly through a mandatory `--target <id>`, with `reference-vm` and `framework-13-pro-amd` as the supported values; the physical target is no longer the Slimbook Creative [DEC-005, TODO-001]. Each `targets/<id>/` declares minimal identity constraints (tentatively `target.json`) that discovery checks against the detected facts: the reference VM expects `kvm` virtualization, UEFI, and a QEMU DMI vendor, while the Framework expects its DMI vendor and product and no virtualization. An unknown or missing id, or facts that contradict the declared identity, exit with `2` and an actionable reason, which also covers the "contradictory facts" case of the story. Every target must additionally be `x86_64`, boot through 64-bit UEFI, and expose at least one non-removable candidate disk other than the live medium; finer thresholds such as minimum disk size and network readiness are settled with validation. Auto-detection by DMI was rejected because it guesses on failure, and an auto-detect-with-override hybrid was rejected for doubling the tested paths [DEC-005].

The target change is recorded through ADR 0005, which states that the physical target is now a Framework Laptop 13 Pro with an AMD Ryzen AI 300 series processor and only its integrated AMD graphics, with no hybrid or discrete GPU. In the same commit the Slimbook mentions in `docs/architecture.md` and `docs/epics.md` are amended, and the `nvidia-discrete-graphics` and `hybrid-graphics` rules are marked as not applicable to the current target rather than deleted; Story 2.6 decides their removal with the real captured topology. The ADR records the target change only and decides no hardware rule [DEC-006].

Identity constraints store only non-sensitive DMI fields (`sys_vendor`, `product_name`); serial numbers and UUIDs never enter Git or evidence [DEC-006]. Because the laptop is not yet available, the Framework constraint stays "pending capture" and `--target framework-13-pro-amd` exits `2` with an actionable reason until the values are recorded, so this plan exercises the story on the reference VM only [TODO-002].

## Output artifacts and layering

Each Bash collector (`discover-firmware`, `discover-network`, `discover-storage`, `discover-hardware`) prints uninterpreted JSON on stdout, which is retained as raw evidence for diagnosis; interpretation happens only in Node [DEC-007].

Node then produces a single `target-facts.json` (`format_version: 1`). Its `source` section binds the document to the run identifier, the embedded code's commit and `dirty` state, and the selected `target_id`. Its `layers` section keeps the four precedence layers physically separate: `portable_baseline` (empty or minimal in Story 2.2, to be filled by installation policy in Story 2.3), `detected` (firmware, network, storage, and hardware capabilities), `target_override` (read from `targets/<id>/overrides/`), and `runtime_private`, which lists only the names of required private inputs and never their values and is empty in Story 2.2. An `effective` section resolves the layers in precedence order and tags every value with its `source` (`baseline`, `detected`, `override`, or `runtime`), which is what makes hardware-derived choices inspectable for FR34. A `validation` section reports `valid` or `invalid` with reasons carrying `code`, `message`, and `next_step` [DEC-007].

Output goes to `evidence/install/<run-id>/` by default, with 0700 directories, 0600 files, and atomic writes, or to the directory given by `--output <dir>`; stdout carries a concise human-readable summary of the key facts and their provenance. The format is documented in `contracts/target-facts.md` and enforced by a hand-written Node validator backed by fixtures under `tests/fixtures/discovery/` and contract tests, without a formal `*.schema.json`, since the architecture keeps final schemas gated [DEC-007].

## Storage facts and eligibility

Storage discovery is strictly read-only: `discover-storage` runs `lsblk -J -b` with `PATH`, `KNAME`, `TYPE`, `SIZE`, `MODEL`, `SERIAL`, `WWN`, `TRAN`, `RM`, `RO`, `HOTPLUG`, `PTTYPE`, `PTUUID`, `FSTYPE`, `LABEL`, `UUID`, `PARTUUID`, and `MOUNTPOINTS`, reads the `/dev/disk/by-id/` links, and identifies the device backing the live medium from the `/run/archiso/bootmnt` mount. It never uses `blkid -p`, `smartctl`, or any probe that writes or needs privilege [DEC-008].

Each disk carries a stable identity made of its `by-id` link (preferring `nvme-eui.*` and `wwn-*`), `WWN`, `SERIAL`, `MODEL`, `PATH`, and size in bytes, omitting whatever is unavailable; Story 2.4 will bind confirmation to this identity. Unlike the DMI serial, disk serials are retained in `target-facts.json` because they are the stable identifiers the story requires; that file exists only in local, ignored, 0600, secret-scanned evidence, and fixtures in Git use synthetic values. The current partition table, partitions, filesystems, and mountpoints are recorded for later plan review, but an existing layout does not make a disk ineligible, since the engine wipes the whole disk only after explicit confirmation [DEC-008].

Discovery lists candidates and never selects one; selection belongs to Story 2.3. Each disk is marked `eligible` or not with explicit reasons: `loop`, `rom`, and `zram` devices, removable disks (which excludes USB SSD installation), read-only disks, the live medium, disks with any active mountpoint, and disks smaller than 20 GiB are ineligible. The 20 GiB minimum is classified as a technical necessity covering the 1 GiB ESP, the 4 GiB swapfile, and a base system with margin. When no eligible candidate exists, validation exits `2` with a reason for each disk [DEC-008].

## Firmware facts

MirrorOS supports UEFI only. `discover-firmware` records the boot mode, the UEFI platform size from `/sys/firmware/efi/fw_platform_size`, whether efivars are available, and the Secure Boot state read from its efivar or from `bootctl status` without added privilege, recording `unknown` when it cannot be determined. It also records the non-sensitive DMI fields `sys_vendor`, `product_name`, `product_version`, `board_name`, `bios_vendor`, `bios_version`, and `bios_date`, and never the product, board, or chassis serials or the product UUID [DEC-009].

A non-UEFI boot is detected only so that it can be rejected early: some firmware boots the live USB in legacy or CSM mode without the user noticing, which would otherwise surface later as a confusing boot-loader failure. Validation exits `2` with an actionable `next_step` for a non-UEFI boot (boot the medium in UEFI mode and disable CSM or legacy), for 32-bit UEFI, for unavailable efivars, and for an enabled Secure Boot (disable it in firmware setup and rerun), in line with the architecture's MVP posture and the unsigned systemd-boot. An `unknown` Secure Boot state is only a non-blocking entry in `validation.warnings` [DEC-009].

Because the live session is already root, "no privilege elevation" means that discovery never invokes `sudo` or any other elevation mechanism and never writes to a device; it does not require an unprivileged account [DEC-009].

## Network facts and readiness

`discover-network` records each interface's name, whether it is wired or wireless (through `/sys/class/net/<if>/wireless`), its state, and whether it holds a global IPv4 or IPv6 address, together with the default route, DNS resolution of `archlinux.org` through `getent ahosts`, and a bounded `curl` HTTPS probe of `https://archlinux.org/`, the same reachability check used by the Story 1.4 bootstrap. The probe creates outbound traffic but changes no target state. MAC addresses, Wi-Fi credentials, SSIDs, and `iwd` state are never recorded [DEC-010].

The network is ready only when a default route exists, DNS resolves, and the HTTPS probe succeeds; `network.ready` records the outcome and the failing step. A network that is not ready exits `2` with a step-specific `next_step`, such as connecting a cable or configuring Wi-Fi with `iwctl` and rerunning, because a plan generated without connectivity could not install; discovery never configures the network itself. Mirror selection and `reflector` remain the engine's concern in Story 2.5 [DEC-010].

## Hardware capabilities

`discover-hardware` reads only `/sys` and `/proc` and records what Story 2.6 needs as input without mapping anything to configuration yet [DEC-001, DEC-011]: the CPU vendor, model, and core count, which will drive the microcode choice; `MemTotal`, relevant for swapfile and hibernation sizing; every PCI display device (class `0x03xxxx`) with its vendor and device identifiers, bound driver, and `boot_vga` flag, classified as AMD, Intel, NVIDIA, or QEMU virtual graphics; whether a battery is present, without its serial or manufacturer; the virtualization type reported by `systemd-detect-virt`; and the presence of Wi-Fi, referenced from the network facts rather than collected twice [DEC-011].

These facts never block discovery on their own. They take part only in the target identity check, so that, for example, `--target reference-vm` on hardware without virtualization exits `2` [DEC-005, DEC-011]. The Framework target carries no graphics constraint in this story while its DMI identity awaits capture [TODO-002]. USB devices, sensors, audio, the fingerprint reader, Bluetooth, and NVMe detail stay out of scope until Story 2.6 needs them [DEC-011].

## Precedence layers in practice

Detected values are facts and can never be overridden; an override cannot declare a disk UEFI or a network ready [DEC-012]. The portable baseline in this story is therefore the discovery policy itself, kept in a versioned `install/discovery/policy.json` with `minimum_disk_bytes` (20 GiB), `https_probe_url`, and `https_probe_timeout_seconds`, each labeled with its provenance classification. A target may adjust only allowlisted policy keys through `targets/<id>/overrides/discovery.json`; an unknown key or an attempt to override a detected fact exits `2` as invalid input, following the architecture's rule that safety-critical data rejects unknown fields. Both real targets ship an empty `overrides/` directory with a README, so precedence is demonstrated through fixtures and through the `effective` view, whose per-value `source` shows which layer won. Stories 2.3 and 2.6 extend the allowlist with installation policy and hardware selections. An empty production allowlist and the absence of overrides were both rejected [DEC-012].

## Reference-VM qualification

Discovery is qualified by a new `vm/reference/qualify-discovery` that reuses the launch, NoCloud, serial, deadline, cleanup, and evidence libraries under `vm/reference/lib/` while leaving the `qualify-bootstrap` contract of Story 1.4 untouched; adding a mode to `operations/test` was rejected for changing that interface. NoCloud only triggers `mirroros-install discover --target reference-vm` against the embedded code and never delivers code, and `target-facts.json` returns over serial bound to the run identifier, as the Story 1.4 report does [DEC-013].

Three scenarios are counted. The first uses a fresh, empty 32 GiB disk. The second uses a disk with a pre-existing GPT layout and two labeled partitions, prepared on the host without root by running `sfdisk` against a raw file and converting it to qcow2; discovery must record that layout and still mark the disk eligible. The third is negative: `--target framework-13-pro-amd` inside the VM must exit `2`. After each confirmed QEMU exit, `qemu-img compare` between the disk before and after the run must report identical images, which is the evidence that discovery leaves the target unchanged; any difference fails qualification [DEC-013].

The rebuilt bundle, now carrying `nodejs` and the embedded code, must also pass the unchanged `operations/test` boot qualification. Only runs at a clean commit with `dirty: false` count, with evidence under `evidence/reference-vm/discovery/<run-id>/`; development runs that load code through NoCloud do not count [DEC-002, DEC-013].

## Host-level tests

Collectors resolve every system path against `MIRROROS_DISCOVERY_ROOT`, which defaults to `/` and qualifies as small process context; `operations/install discover` deliberately offers no option to change it, so users cannot fabricate facts. External commands are replaced in tests by `PATH` doubles that return fixture JSON and controlled statuses, following the Bats patterns of Stories 1.3 and 1.4 [DEC-014].

Synthetic fixtures under `tests/fixtures/discovery/`, none containing real serials, cover a valid reference VM with an empty disk and with a pre-existing layout, BIOS boot, 32-bit UEFI, Secure Boot enabled, Secure Boot unknown (warning only), each failing network step, each disk ineligibility reason (removable, too small, live medium, mounted), a contradictory identity, overrides with an unknown key or targeting a detected fact, and a synthetic-DMI Framework that exercises the pending-capture path [DEC-014].

The Bats contract suites under `tests/install/discovery/` cover the collectors and the `0`, `2`, and `6` exits, and prove the absence of elevation and writes through a `sudo` double that fails when invoked and an unchanged fixture tree. `node:test` suites in the same directory cover normalization, layering, the `effective` view, the validator, and atomic writes. `tests/operations/install.contract.bats` covers the `discover` subcommand and the unchanged invocations, and `tests/image/builder/` covers the embedded capture, the `embedded_code` metadata block, and the identity file. Node suites run with explicit file globs because Node 24 rejects directory arguments [DEC-014].

Raw collector output stays uninterpreted but drops sensitive fields at collection time, such as the MAC address in `ip -j link`, which refines DEC-007. A redaction test plants MACs, SSIDs, and DMI serials in the fixtures and asserts that none reach `target-facts.json`, the retained raw output, or stdout [DEC-007, DEC-014].

## Command interface and outcomes

The subcommand is `operations/install discover --target <id> [--output <dir>]`, reached in the ISO as `mirroros-install discover` through `/usr/local/bin/mirroros-install`, with `operations/install discover --help` printing its own help. `--output` must name an absent or empty directory so that previous evidence is never overwritten [DEC-015].

Outcomes follow the normalized statuses. Valid facts return `0`, possibly with warnings. Invalid arguments, an unknown or contradictory target, a missing required fact, a target outside the supported boundary, a network that is not ready, the absence of any eligible disk, and an invalid override all return `2`. An external command that fails unexpectedly, such as `lsblk` exiting non-zero, returns `5` and keeps the original child status and stderr in evidence, which separates a missing fact from a broken tool. A damaged checkout or embedded tree, or an internal invariant failure such as the produced document failing its own validator, returns `6` [DEC-015].

On `2`, `target-facts.json` is still written with `validation: invalid` and its reasons so that the user can inspect what was found; on `5` or `6`, only the raw evidence and the architecture's structured error are written. Discovery is non-interactive, so it does not use Gum: the summary is plain text on stdout and diagnostics go to stderr, the ISO gains only `nodejs`, and `gum` enters the image with Story 2.3 or 2.4 under ADR 0004 [DEC-015].

## File layout and embedded subtrees

Discovery lives under `install/discovery/`: a Bash orchestrator `discover` runs the four Bash collectors (`discover-firmware`, `discover-network`, `discover-storage`, `discover-hardware`), hands their raw output to Node, and writes the results. The Node side is split by responsibility into `normalize-facts.mjs` (firmware, network, and storage normalization plus disk eligibility), `resolve-layers.mjs` (baseline, detected, override, and runtime layers into `effective`), `validate-facts.mjs` (format and validation rules), and `write-facts.mjs` (atomic write and the human summary), next to the baseline `policy.json`. Hardware capability normalization goes to the reserved `hardware/discovery/normalize-hardware.mjs`, since that directory owns hardware capabilities only and was rejected as a home for all normalization [DEC-016].

Each target directory, `targets/reference-vm/` and `targets/framework-13-pro-amd/`, holds a `README.md`, a `target.json` with identity constraints (pending capture for the Framework), and an `overrides/` directory containing only a README. `contracts/` gains a `README.md` and `target-facts.md`. VM qualification adds `vm/reference/qualify-discovery` with a guest trigger script, touching `vm/reference/lib/` only if needed. The image gains `nodejs` in `packages.x86_64` and a literal `airootfs/usr/local/bin/mirroros-install` symlink, and the builder changes in `lib/source-capture.sh`, `build-artifact`, and `build-documents.mjs` [DEC-016].

The builder embeds exactly `operations/install`, `operations/lib/lifecycle-discovery.sh`, `install/`, `hardware/discovery/`, and `targets/`; neither `contracts/` nor `tests/` is embedded, because the validator lives in code and the contract file is documentation [DEC-003, DEC-016].

## Documentation and delivery sequence

Documentation changes together with the code it governs. `docs/architecture.md` receives the ADR 0005 amendments, project-tree entries for the new discovery files, `contracts/target-facts.md`, `targets/framework-13-pro-amd/`, and `vm/reference/qualify-discovery`, and one *Image Boundary* sentence stating that the live medium carries embedded MirrorOS code under `/usr/local/lib/mirroros/`. `docs/epics.md` changes only at its two Slimbook mentions. `docs/procedures/install.md` moves from help-only to documenting `discover` while full installation stays Pending; `docs/procedures/build.md` documents the embedded capture, the `embedded_code` block, the identity file, and the live-environment reason for `nodejs`; `docs/procedures/test.md` and `vm/reference/README.md` document `qualify-discovery`. `docs/attribution.md` does not change, because no third-party code is copied [DEC-017].

Work lands in two commits, each preceded by a maintainer review: `docs(adr): record physical target change` with ADR 0005 and the architecture and epics amendments, then `feat(install): discover and normalize the installation target` with the builder, image, discovery, targets, contracts, `operations/install`, `qualify-discovery`, tests, and procedures. The embedding change is not split out because the builder fails when a declared subtree is missing, which would leave an unbuildable intermediate commit. After the second commit the bundle is built at a clean commit, boot is requalified with `operations/test`, and the three `qualify-discovery` scenarios run. A defect found during counted runs leads to a new `fix(...)` commit and a repetition of every counted run [DEC-017].

For fast iteration, `qualify-discovery --development-overlay` copies the working-tree embedded subtrees through NoCloud over `/usr/local/lib/mirroros/` in the guest and always marks the run `counted: false` [DEC-018].
