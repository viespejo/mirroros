# Story 2.3 — Generate an Explainable Installation Plan: Consolidated Plan

## Scope

Story 2.3 is a non-interactive stage. It turns valid discovery facts and installation policy into an installation plan, validates it, computes a digest over its canonical content, persists it atomically, and renders it as plain text derived only from the persisted plan. The interactive review flow, Gum, and digest-bound confirmation belong to Story 2.4, so `gum` does not enter `image/` in this plan, and the whole story remains testable with fixtures and without a TTY [DEC-001].

## Command interface

Plan generation extends the existing lifecycle command instead of adding a parallel surface: `operations/install plan --facts <file> [--choices <file>] [--output <dir>]`. It consumes an existing `target-facts.json` produced by `discover` and never runs discovery itself, which keeps the two stages independently invocable and lets the user regenerate a plan after an edit without rediscovering. The `target_id` is taken from the facts document rather than repeated through `--target`, so the two can never contradict each other. Facts whose `validation.status` is `invalid`, whose `format_version` is unknown, or that fail `validate-facts.mjs` exit `2`. The current behaviors of `--help`, the argument-less invocation, and unknown arguments are preserved. Running discovery and planning in one step was rejected for coupling the stages, and accepting both forms was rejected for doubling the tested paths [DEC-002].

## Installation policy

Base installation choices are owned by a new versioned `install/plan/policy.json` (`format_version: 1`), kept separate from `install/discovery/policy.json` so that discovery thresholds and installation choices do not mix. Every key declares its `value`, its `provenance` as one of `personal_preference`, `hardware_detection`, `arch_guidance`, or `technical_necessity`, and whether it is `editable`. Choices fixed by the architecture, such as UEFI, GPT, the official `linux` kernel, and the unencrypted root, are labeled `technical_necessity` or `arch_guidance` as appropriate and are not editable. The native prototype scenario matrix is the starting point for the content but is not normative: each item was reviewed before it became production policy [DEC-003, DEC-004].

The adopted policy keeps the architecture-fixed choices (UEFI, GPT, a 1 GiB FAT32 ESP at `/boot`, the official `linux` kernel, default mkinitcpio hooks without UKI, UTC hardware clock, and the inherited and recorded mirrorlist) non-editable, labeled `technical_necessity` or `arch_guidance`. Personal preferences from the prototype scenario are adopted as defaults: the package set `base linux linux-firmware sudo neovim man-db man-pages`, zram disabled, the kernel command line without `quiet`, NetworkManager without predefined connections, `systemd-timesyncd`, the `%wheel` sudoers drop-in, `kernel.sysrq = 1`, the pacman options, and `fstrim.timer` [DEC-004].

Only a small set of choices is editable: `swapfile_size` (4 GiB), `locales` and `lang` (`en_US.UTF-8` and `es_ES.UTF-8`, with `LANG=en_US.UTF-8`), `console_keymap` (`us`), `timezone` (`Europe/Madrid`), `hostname` (`mirroros`, which a target may override, for example to `mirroros-ref`), the user name (`mirroros`, in `wheel` with `bash`), `root_account`, and `storage_option`. Hardware-derived swap sizing is left to Story 2.6 [DEC-004].

Filesystem and bootloader are not independent keys. A single `storage_option` determines the filesystem, layout, bootloader, and resume-offset method together, because ADR 0003 defines its options as qualified bundles and independent keys would create unqualified combinations. It is editable and accepts `ext4-systemd-boot` (the default), `btrfs-rescue`, and `btrfs-limine`. The plan shows each option's support tier as read from a tier table in `install/plan/policy.json`, which reflects ADR 0003 today, so `btrfs-limine` is still shown as experimental. The maintainer intends all three to be supported, but removing the experimental tier requires an ADR superseding ADR 0003 and meeting its conditions; that ADR is outside this plan, and when it lands only the tier table changes, not the plan code. Option-specific resume parameters are resolved by the engine in Story 2.5 [DEC-004, DEC-005, TODO-003].

The root account is `locked` by default and then requires no secret. Choosing `password` adds the `root_password` secret requirement, recorded by name only. The choice is explicit in the plan rather than inferred at runtime from whether a password is typed, so the digest covers it and Story 2.4 can show it. The user password is always a required secret. Microcode, graphics drivers, and `multilib` are outside this policy [DEC-004].

## Target disk

Discovery never selects a disk, so selection happens here as the editable choice `target_disk`, expressed by the disk's stable identifier (`by_id`, preferring `nvme-eui.*`, then `wwn-*`). When exactly one disk is eligible it is preselected and labeled `hardware_detection`; when several are eligible, the plan refuses to guess and exits `2` with an actionable reason listing the candidates, unless the choices file names one. Naming an ineligible or unknown disk also exits `2`. The plan copies the selected disk's full identity (path, `by_id`, WWN, serial, model, and size) together with its current layout, which is presented as content that will be destroyed, so that Story 2.4 can bind confirmation to it. If a disk exposes no `by_id`, its path is accepted as a fallback with a warning in the plan and Story 2.4 re-checks model and size; a disk with neither exits `2`. Always requiring manual selection and choosing the largest disk were both rejected [DEC-006].

## Editable choices and precedence

User edits reach the plan only through `--choices <file>`, a flat JSON object with `format_version: 1` that the user keeps wherever they like; it is not versioned under `targets/`, because it belongs to the user rather than to a target. Its keys are restricted to the editable set: `target_disk`, `storage_option`, `swapfile_size`, `locales`, `lang`, `console_keymap`, `timezone`, `hostname`, `user_name`, and `root_account`. An unknown or non-editable key, an invalid value such as an unknown storage option, a nonexistent time zone, or a hostname that violates RFC 1123, and any secret-like field such as `password` or `*_password` exit `2`, so secrets can never travel through this file [DEC-007].

Values resolve in the order `policy` < `detected` < `target_override` < `choice`. Target overrides live in `targets/<id>/overrides/plan.json` behind an allowlist that admits only `hostname` in this story. Secrets sit outside this chain, because the plan only names them. Every value in the plan carries two attributes: `provenance`, the FR12 class that explains why the default exists, and `source`, the layer that set the final value. An edited hostname therefore reads as a personal preference set by user choice. One flag per choice was rejected for widening the surface and making plans harder to reproduce, and hand-editing the plan JSON was rejected because the digest would no longer correspond to a generation [DEC-007].

## Proposed operations

The plan expresses what will happen as an ordered list of declarative operations rather than command lines, so the plan and its digest stay independent of how the native engine implements each step. Every operation has a stable `id`, a `kind`, a `destructive` flag that Story 2.4 uses to highlight consequential steps, `parameters` already resolved from policy and choices, and a human-readable `description`. Order is significant and declared by the contract. The `kind` vocabulary is part of the versioned plan contract, and Story 2.5 must reject any kind it does not know, which is what lets the engine execute only what the approved digest represents [DEC-008].

For `ext4-systemd-boot` the sequence is: `wipe_disk_signatures`, `create_partition_table`, `create_partitions`, and `format_filesystems`, all destructive; then `mount_target`, `install_packages`, `generate_fstab`, `create_swapfile`, `configure_locale_time_console`, `configure_hostname_network`, `create_user` (requiring `user_password`), `configure_root_account` (`locked`, or `password` requiring `root_password`), `configure_sudo_sysrq_pacman`, `install_bootloader`, and `enable_services`. The Btrfs options replace or add their own steps for subvolumes, Snapper with its baseline snapshot, and Limine. Values that only exist during apply, such as UUIDs and `resume_offset`, are declared `resolved_at_apply` with their method and carry no value. Concrete command lines were rejected for coupling the digest to the engine, and a high-level summary was rejected as insufficient for bounded execution [DEC-008].

## Hardware-derived selections

The plan carries a `hardware_selections` section with a stable shape that Story 2.6 will extend without changing: each entry records an `id`, the `fact` it derives from as a dotted path in the facts' `effective` view, the resulting `value`, `provenance: hardware_detection`, and the `rule` that produced it. In this story the section holds the `target_disk` preselection when exactly one disk is eligible, and the 64-bit UEFI boot-mode check that confirms `firmware_mode`, which is a check rather than a choice. An informational `detected_capabilities` block shows the detected graphics vendor, battery, virtualization, and CPU with `rule: not_evaluated` and `next_story: 2.6`, so the user sees what was found without any of it becoming a package or configuration yet. Microcode, graphics drivers, and hardware-derived swap and resume sizing stay with Story 2.6; implementing the microcode rule here was rejected because it would set the rule pattern before that story designs it [DEC-009].

## Digest and bindings

The plan digest is SHA-256 in hex, stored as `digest: { algorithm: "sha256", value: "<hex>" }`, and covers the whole document except the `digest` field itself. It is computed over an in-house canonical serialization inspired by RFC 8785 but restricted to the plan format: object keys sorted by code point, no whitespace, UTF-8, and integers only, because the contract forbids non-integer numbers. Anything that cannot be canonicalized, such as `undefined`, a non-integer number, or a non-JSON type, is an internal contract failure that exits `6`. Only Node built-ins are used [DEC-010].

The signed content deliberately contains no timestamps and no `run_id`; those go to a separate run-metadata file. Identical inputs therefore always yield the same digest, which tests assert, and a different digest always means different content rather than a mere regeneration [DEC-010].

The plan records where it came from. `facts_binding` holds the SHA-256 of the canonical `target-facts.json`, its `run_id`, the `target_id`, and the embedded code's `commit` and `dirty` state, alongside the copied disk identity, so rediscovery that changes any fact changes the plan digest and Story 2.4 can detect a changed target. `policy_binding` holds the SHA-256 of `install/plan/policy.json` and of any target override that was applied, so a policy change also changes the digest [DEC-010].

## Persistence, regeneration, and approval state

Every `plan` invocation is its own run: it creates a new `run_id` and writes to `evidence/install/<run-id>/`, or to `--output`, with 0700 directories and 0600 files. The directory holds `installation-plan.json` with its digest, `installation-plan.txt` rendered from the persisted JSON, and `plan-run.json` with the run metadata (`run_id`, an RFC 3339 timestamp, input paths, the plan digest, the exit status, and reasons). Each file is written to a temporary file in the same directory, flushed, re-read and revalidated, including recomputation of the digest, and only then renamed. Unlike discovery, which keeps invalid facts for inspection, an invalid plan is never persisted as `installation-plan.json`; only `plan-run.json` records the reasons and exit `2` [DEC-011].

Regeneration never overwrites. An edited regeneration is a new run in a new directory, so the earlier plan stays intact with its own digest for comparison, and an `--output` directory that already contains a plan exits `2`. The plan cannot be approved by construction: it has no approval field, and because the validator rejects unknown fields, an injected `approved` or `approval` field is invalid. Approval becomes a separate, digest-bound artifact in Story 2.4. Tests show that a regenerated plan has a different digest, that the original remains byte-identical, and that a plan with an injected approval field is rejected [DEC-011].

## Contract and validation

The plan format is documented in `contracts/installation-plan.md` (`format_version: 1`) and enforced by an in-house `install/plan/validate-plan.mjs`, following the Markdown-contract-plus-validator pattern of Story 2.2 rather than JSON Schema, which would need an npm dependency. The contract is indexed in `contracts/README.md` and documents the operation `kind` vocabulary, the provenance and source labels, the `--choices` format, `targets/<id>/overrides/plan.json`, the validation codes, and the exits. The architecture's directory tree is corrected in the same change: `installation-plan.schema.json` becomes `installation-plan.md`, and the `target-facts.md` contract omitted by Story 2.2 is added, while the other `.schema.json` entries belong to future stories and stay unchanged [DEC-012, DEC-013].

Validation works on four levels. Malformed input covers invalid JSON, wrong types, and non-integer numbers. Incomplete input covers a missing target, operations, digest, bindings, secret requirements, or per-value provenance and source. Unknown fields are rejected throughout the whole document, not only in its safety-critical parts, so any extension requires a new `format_version`. Contradictions are semantic rules: the operation sequence must match `storage_option`; `root_account: password` requires the `root_password` secret and `locked` forbids it; `lang` must be among `locales`; the disk identity must match the bound facts and the disk must be eligible; `swapfile_size` plus the ESP plus the base minimum must fit on the disk; no destructive operation may lack a `target_disk`; every `kind` must be known and in an allowed order; and the digest must match the content [DEC-012].

Errors reuse the Story 2.2 shape of `code`, `message`, and `next_step`, with the codes documented in the contract. Invalid facts, choices, or overrides exit `2`; a generated plan that fails its own validator is an invariant violation and exits `6`; an unexpected external tool failure exits `5` [DEC-012].

## Secret requirements

The plan names its secrets in an ordered `secret_requirements` list and never carries their values. Each entry has a `name` (`user_password`, plus `root_password` when `root_account` is `password`), a human-readable `purpose`, the ids of the operations that consume it in `required_by`, `channel: protected_prompt`, which declares the class of channel without fixing how Story 2.5 implements it, and a `provenance`: `technical_necessity` for the user password and `personal_preference` for the root password, since it only exists by the user's choice. Values, hashes, and length hints are never present; the validator rejects extra fields in these entries and secret-named keys anywhere else. Consistency runs both ways: every operation that needs a secret must have it declared, and no secret may be declared without a consumer. Canary-based tests plant a value and assert that it never appears in `installation-plan.json`, `installation-plan.txt`, `plan-run.json`, stdout, or stderr [DEC-014].

## Rendering and console output

`install/plan/render-plan.mjs` is a pure function of the validated plan, so everything it shows is part of the signed content. It produces `installation-plan.txt`, plain text laid out to read well on the live ISO console: 80 columns, underlined section headers, aligned key and value pairs, `DESTRUCTIVE` as a textual marker, and no ANSI sequences or color. Its eight sections follow the architecture's review flow: the target with the layout that will be destroyed; the choices and defaults with their value, `provenance`, `source`, and an `[editable]` marker; the destructive operations; all operations in order; the secret requirements; the hardware selections, including capabilities that are `not_evaluated`; warnings; and the digest with its bindings [DEC-015].

The console shows a short summary rather than the full plan: target, disk, storage option, the number of destructive operations, required secrets, the digest, and the plan path, ending with "Review installation-plan.txt; approval is not part of this stage." Diagnostics go to stderr. The full plan stays in the file because it would scroll off the console, and paged interactive review with Gum belongs to Story 2.4. Printing the full plan always or behind a `--show` option was not chosen, and a Markdown render was dropped because no renderer exists on the live medium in this story, so it would add nothing over well-laid-out text. Tests compare fixture snapshots, check that the render changes after an edit, that the shown digest matches the JSON, and that lines stay within 80 columns except for unavoidable long values such as `by_id` [DEC-015].

## Live medium delivery and qualification

Plans are generated on the live ISO, where discovery runs, and `install/plan/` reaches `/usr/local/lib/mirroros/` through the existing `install` entry of the explicit capture list, so the builder needs no change. It contains only `.mjs` modules, so `profiledef.sh` needs no new permission entries unless an executable is added [DEC-016].

Fixture tests cover the logic, but only a real run proves `discover → plan` against real facts with the embedded code. `vm/reference/qualify-discovery` therefore gains a `plan` scenario rather than a parallel harness: inside the VM it runs `discover --target reference-vm`, then `plan` with default choices and expects `0`, then `plan` with a choices file that changes the hostname and `storage_option` and expects `0`, a different digest, and a byte-identical original plan, and finally `plan` with an invalid choices file and expects `2`. It also checks that the disk is unchanged with `qemu-img compare`, runs the Gitleaks and canary scans, and checks permissions. Counted runs happen on a clean commit after rebuilding the ISO and requalifying boot with `operations/test`, following the Story 2.2 pattern; the rebuild is also the moment to confirm that the 180-second `container-stop` deadline suffices. Only `reference-vm` is qualified while the Framework identity is still pending capture [DEC-016, TODO-005].

## Relationship with target facts

The facts document does not change. `target-facts.json` keeps `format_version: 1` with the discovery policy as its baseline layer, and discovery and its validator stay untouched: facts describe what was found and the thresholds used to find it, while the plan resolves installation choices with its own precedence. This supersedes the Story 2.2 intention to fill `portable_baseline` with installation policy, and `contracts/target-facts.md` gains a one-line note pointing to `contracts/installation-plan.md` so the change is visible to readers of either contract. Moving installation policy into the facts was rejected because it would require a new facts format version, discovery requalification, and would mix discovered state with choices [DEC-017].

## Delivery

The story ships as one `feat(install)` commit containing the plan modules and policy under `install/plan/`, the `plan` subcommand, the reference VM's `overrides/plan.json` with `hostname: mirroros-ref` (which demonstrates the override layer with real data), the override READMEs of both targets, the new contract with its index entry and the note in the facts contract, the corrected architecture tree, the install procedure, Node and Bats tests with fixtures, the embedded capture and the `plan` qualification scenario, and these interview artifacts. The maintainer reviews at three checkpoints: the contract and policy before the generator is implemented, since they bind Stories 2.4 and 2.5; the full change set before the commit; and the counted evidence before closing. Defects found during counted runs are fixed in new `fix(...)` commits and the counted runs repeat at the new HEAD. Attribution does not change because no third-party content is added, and `docs/epics.md` is not touched [DEC-018].
