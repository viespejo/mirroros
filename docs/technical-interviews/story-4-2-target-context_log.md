# Story 4.2 (part 2) — Configure in the Installer Target Context: Decision Log

Append-only record of the technical interview that plans plan 02-16, which completes Story 4.2. IDs continue the
numbering of the [part 1 decision log](story-4-2-minimal-graphical-login_log.md) (DEC-001 to DEC-024), which stays
unchanged and is cited as prior context.

## DEC-025
- **Question**: At which point does the guided installer invoke `configure` against the target root?
- **Context/Nuances**: The engine is the only owner of the target mount and of cleanup: `finish()` in `install/engine/lib/common.sh` unmounts `/run/mirroros/target` right after `run_postconditions`, so when the assistant receives `installed` the target is already unmounted. `docs/architecture.md` (Integration Points) shows the chain `install/engine/apply → operations/configure`. The engine already runs commands through `arch-chroot "$TARGET"` and uses `SNAP_PAC_SKIP=y` for package transactions inside the chroot. Alternatives: (A) the engine runs `configure` as a final phase after base postconditions pass and before cleanup; (B) the assistant runs it after the engine, with the engine leaving the target mounted, which breaks single ownership of mount and cleanup; (C) the assistant remounts the target, which duplicates layout-specific mount logic outside the engine.
- **User Response**: Agreed with A.
- **Decision**: The engine invokes `operations/configure` from its embedded code as a final phase, only after `run_postconditions` reports the base installation as `installed`, and before `cleanup_target`, while the target is still mounted and the installer lock is held. The base postconditions are therefore always checked before configuration (DEC-001). This is a change of the engine contract (`contracts/installation-engine.md`, the engine record, and the progress state); ADR 0008 is not changed because it governs the entry path into the engine, not its internal phases. Outcome semantics on `configure` failure are decided separately.
- **Status**: Accepted

## DEC-026
- **Question**: How are texts shown during the engine phase of the installer kept from overflowing the console, starting with the long package-installation line under the progress bar?
- **Context/Nuances**: The user observed that the progress line shown during package download overflows. It comes from `OPERATION_DESCRIPTIONS.install_packages` in `install/plan/generate-plan.mjs` (130 characters), shown by `ui_progress` as `[<n>/<N>] <description>`. `measure_terminal` centers the guide on the 80-column logo, so at least 80 columns are always available; the `[22/22] ` prefix leaves 72 for a description. Seven descriptions exceed 72 (`install_packages` 130, `configure_zram` 109, `create_swapfile` 108, `configure_locale_time_console` 86, `wipe_disk_signatures` 79, `configure_hostname_network` 77, `format_filesystems` 76). Descriptions are part of the generated plan and its digest, so plan fixtures and render snapshots are regenerated. A length limit alone does not cover dynamic texts (paths, reasons): D19 and D20 already wrap through `ui_wrapped_style`, but the engine-phase `ui_failure` for an engine that left no valid record includes the run directory path and is not wrapped. The D18 success line (77 characters) fits but must change in plan 02-16 because success will include `configure`.
- **User Response**: Asked whether trimming everything to 80 columns and making it a rule would be enough for every text of this phase; agreed with the two-part rule and the proposed texts.
- **Decision**: (1) Every fixed text shown during the engine phase (D17, D18, and the new `configure` phase) fits 80 columns including its prefix; operation descriptions are therefore at most 72 characters. The rule is recorded in `contracts/installation-confirmation.md` (D17) and enforced by a test over `OPERATION_DESCRIPTIONS`. (2) The engine-phase `ui_failure` for an engine without a valid record is shown wrapped like D19 and D20; this extends the contract's wrapping scope to that screen only, and `ui_failure` in other phases is unchanged. (3) New descriptions: `install_packages` "Install packages."; `wipe_disk_signatures` "Remove existing signatures from the target disk."; `format_filesystems` "Format the ESP and the root partition."; `configure_zram` "Configure zram as preferred swap."; `create_swapfile` "Create the fallback swapfile, which also holds the hibernation image."; `configure_locale_time_console` "Configure locale, time, and console keymap."; `configure_hostname_network` "Set the hostname and configure NetworkManager.". The other descriptions already fit. (4) Plan fixtures and render snapshots are regenerated in the same change.
- **Status**: Accepted

## DEC-027
- **Question**: Which outcome does the installer report when the base installation is installed and verified but `configure` fails?
- **Context/Nuances**: Engine outcomes today are `installed`/0, `not_verified`/4, `failed`/5, plus `blocked`, `invalidated`, and `128+n` on signals; the assistant selects its screen by the outcome string. After base postconditions pass, a `configure` failure leaves a verified base system that boots to a text console without the graphical environment. DEC-001 forbids reporting readiness when `configure` fails. The current engine interruption message ("retrying requires a new run with a new plan and confirmation") would be false during the `configure` phase, because rerunning `configure` on the installed system is enough. Retrying from the live medium would require remounting the target outside the engine, which DEC-025 rejected.
- **User Response**: Agreed with the recommendation.
- **Decision**: A new engine outcome `not_configured` with exit status 4 ("finished but not ready", like `not_verified`; the assistant distinguishes them by the outcome string) covers every `configure` outcome other than 0 (2, 3, 4, 5, 6). `engine-run.json` records the `configure` outcome, the failed step, and the path of its evidence inside the target (`/var/log/mirroros/configure/<run-id>/`). An interruption during the `configure` phase also ends `not_configured` with `configure` outcome 3, not `failed`/`128+n`: in that phase the engine's signal handlers wait for `configure` to end and record its outcome. The assistant gains a screen D22: "Base system installed and verified; environment configuration failed at step `<step>`.", the next action (boot the installed system, log in at the console, and run `configure` there; the exact invocation depends on how the code is left on the target), and a menu "View configure log" / "Restart" / "Return to shell" / "Power off". Readiness is never claimed. There is no retry option from the live medium; recovery is always a rerun on the installed system.
- **Status**: Accepted

## DEC-028
- **Question**: How does the `configure` code reach the ISO, and how is it left on the target so later reruns need no clone? (Completes DEC-014.)
- **Context/Nuances**: `image/builder/lib/source-capture.sh` embeds `SOURCE_CAPTURE_EMBEDDED_PATHS` (`operations/install`, `operations/lib/lifecycle-discovery.sh`, `install`, `hardware/discovery`, `hardware/rules`, `targets`) under `/usr/local/lib/mirroros` on the live medium, with an `identity.json` (commit and dirty state) that the engine reads in `read_identity`. `/usr/local/bin/mirroros-install` is the live launcher. `configure` currently derives its code identity from `git rev-parse` and records `unavailable` without `.git`. Rejected alternatives: a pacman package built with the artifact (recipe, signing, and versioning without a current consumer) and a clone on the target (needs git and network; excluded by DEC-014).
- **User Response**: Agreed with the recommendation.
- **Decision**: (1) `operations/configure` and `capabilities` are added to `SOURCE_CAPTURE_EMBEDDED_PATHS`, sharing the installer's capture, dirty check, and `identity.json`. The engine runs `configure` from the live medium's embedded code with `--target-root`; the helpers enter the target through `arch-chroot`. (2) Before invoking `configure`, the engine copies to the target only what `configure` needs (`operations/configure`, `operations/lib/lifecycle-discovery.sh`, `capabilities/`, and `identity.json`) at the same path `/usr/local/lib/mirroros/`, owned by root with modes 0755/0644, and creates the launcher `/usr/local/bin/mirroros-configure` as a symbolic link to `operations/configure`. Copying first guarantees that the D22 recovery command exists even when `configure` fails. (3) Without `.git`, `configure` reads `identity.json` from its code root and records commit and dirty state instead of `unavailable`. (4) The copy is a snapshot of the installed version for reruns without a clone; development keeps running `sudo operations/configure` from a checkout. The copy is never synchronized or updated automatically.
- **Status**: Accepted

## DEC-029
- **Question**: How is the `target` branch implemented inside `capabilities/lib/` without editing any `apply` script (DEC-008)?
- **Context/Nuances**: In the target context two systems coexist: the live medium, where the engine and the `configure` orchestrator run from the embedded code (reading `packages`, validating, locking, writing evidence, ordering steps), and the target, mounted at `/run/mirroros/target`, entered only through `arch-chroot`. Helpers that depend on the target's pacman database, users, or systemd must run inside the target: `pacman -Sp`, `-Q`, `-Qu`, and installs (`validate.sh`, `packages.sh`); `id -u <user>`; `runuser` (`files.sh`); `systemctl is-enabled`, `enable`, `get-default`, `set-default`, `list-unit-files`, and `cat` (`units.sh`). Path-based system file helpers (`cfg_system_file`, `cfg_system_link`, `cfg_session_is_only`, `cfg_keyboard_validate`, the lock, and evidence) already use `cfg_path` and work from the live medium over `CONFIGURE_ROOT`. Formatting and logging helpers (`cfg_clean`, `cfg_record`, `cfg_log`) are context-independent. `cfg_display_manager_is` uses `readlink -f`, which in the target context would resolve an absolute link target against the live medium. The engine already runs package transactions inside the chroot with `SNAP_PAC_SKIP=y` after `configure_snapper`. The user asked what "flock on the host" meant; it was clarified that the lock is taken by the orchestrator on the live medium over `$CONFIGURE_ROOT/run/mirroros/configure.lock`, so `flock` must exist on the live medium; the lock file lands in the target's on-disk `/run` directory, which a tmpfs hides at boot, as DEC-016 already placed it.
- **User Response**: Agreed after the clarification.
- **Decision**: (1) A single wrapper `cfg_exec` runs `"$@"` in the `running` context and `arch-chroot "$CONFIGURE_ROOT" "$@"` in the `target` context. Every command and query of the first group goes through it, including the read-only validation queries, so validation uses the target's package database, users, and units, never the live medium's. `cfg_context` no longer exits 6 for `target`. (2) User files run through `cfg_exec runuser -u "$TARGET_USER" -- bash -c …`, so `HOME` resolves from the target's `passwd`. (3) System files, links, the lock, and evidence keep operating from the live medium over `cfg_path`, without chroot. (4) Package transactions in the target run with `SNAP_PAC_SKIP=y`, as the engine does, so installation creates no snap-pac pre/post snapshots; in the running context snap-pac behaves normally. (5) In the target context validation requires `arch-chroot` and `flock` on the live medium, and `bash`, `pacman`, `runuser`, `systemctl`, and the other base tools inside the target. (6) `cfg_display_manager_is` reads the unresolved link (`readlink`) and compares its base name, instead of `readlink -f`.
- **Status**: Accepted

## DEC-030
- **Question**: What is the contract of the public `--target-root` option?
- **Context/Nuances**: DEC-008 deferred the public option to this plan, together with its integration and test. In the target context `SUDO_USER` has no meaning, because the engine runs as root on the live medium. DEC-015 keeps evidence on the configured system. `MIRROROS_CONFIGURE_ROOT` is a test-only process context for the running context. DEC-027 offers no retry from the live medium in the assistant.
- **User Response**: Agreed with the recommendation.
- **Decision**: (1) Form: `operations/configure --target-root <dir> --user <name> [--refresh] [--output <dir>]`, run as root; it sets `CONFIGURE_CONTEXT=target` and `CONFIGURE_ROOT=<dir>`. (2) Validation before any mutation, outcome 2: `<dir>` is absolute, exists, is a mount point (`mountpoint -q`), and is not `/`; `--user` is mandatory in the target context (no `SUDO_USER` default); the user exists in the target's `passwd` and is not root. (3) Evidence defaults to `<dir>/var/log/mirroros/configure/<run-id>/` on the configured system (DEC-015); the engine does not pass `--output` and only records that path in `engine-run.json` (DEC-027); `configure-run.tsv` records `context target`. (4) `MIRROROS_CONFIGURE_ROOT` remains test-only and running-context only; combining it with `--target-root` is a usage error with outcome 2. Target-context tests use an `arch-chroot` double on `PATH`, a temporary directory as the root, and a `mountpoint` double so no real mount is needed. (5) The option is documented in the help and in `docs/procedures/configure.md` as the installer context; a root user on the live medium may use it manually for recovery against a target they mounted, but the assistant does not offer it, and the advertised recovery remains `sudo mirroros-configure` on the installed system. (6) The engine invokes `operations/configure --target-root /run/mirroros/target --user <planned user>` with stdin `/dev/null` and its output appended to `engine.log`.
- **Status**: Accepted

## DEC-031
- **Question**: Is `configure` part of the plan the user approves, or a fixed engine phase outside the plan?
- **Context/Nuances**: The engine executes the approved plan, whose digest is bound to the code identity and whose operations are shown at review before the two-step confirmation. `configure` mutates heavily (many packages, SDDM enabled). As a plan operation (`configure_environment`), the postconditions checker, which runs after all operations, would have to be split or would check the base after configuration, contradicting DEC-025, and the plan schema, validator, generator, render, and fixtures would change. As a fixed engine phase, what runs is determined by the approved plan plus the code identity, because `capabilities/` is embedded under the same `identity.json` that the plan already binds (DEC-028).
- **User Response**: Agreed with B.
- **Decision**: `configure` is a fixed engine phase outside the plan operations, after the base postconditions (DEC-025). The plan schema does not change. So that the mutation is not unseen, the plan review screen adds one fixed line within 80 columns (DEC-026), for example "After the base system is verified, the graphical environment is configured."; the exact wording is a new item of the confirmation contract.
- **Status**: Accepted

## DEC-032
- **Question**: What does the progress screen (D17) show during the `configure` phase, and what does the success screen (D18) say?
- **Context/Nuances**: The bar is completed plan operations over their total; the line `[n/N] <description>` comes from the engine's `state.json`; during package installation a second line shows "Packages installed: N"; during postconditions the last operation remains shown. D18 says "Base system installed. Configuration checks passed before the first restart.", which stops being accurate once success includes `configure`. `configure` already logs a `== <step> ==` marker per step.
- **User Response**: Agreed with the recommendation.
- **Decision**: (1) The progress total becomes the plan operations plus one: the `configure` phase is a final unit, so the bar reaches 100% only when `configure` ends with 0. (2) During the phase the main line is `[N+1/N+1] Configure the graphical environment.`. (3) A second line shows `Configure step: <k>/<total> <step>`. `configure` emits its step marker with the position, `== <k>/<total> <step> ==`; the engine reads the `configure` output line by line, appends it to `engine.log`, and on each marker updates `state.json` with two new optional fields, `configure_step` and `configure_position`, validated by `engine-record.mjs`. No package count is shown in this phase. (4) D18 becomes "Installed MirrorOS in <duration>" followed by the dimmed line "Base system verified and graphical environment configured." (59 characters), replacing the previous line. (5) The DEC-026 width rule extends to step names: a test checks that `Configure step: k/N <step>` fits 80 columns for every entry of `configure-steps`.
- **Status**: Accepted

## DEC-033
- **Question**: Does the reference VM change for the automated clean-installation-plus-`configure` proof without manual steps (the decision DEC-010 deferred to plan 02-16)?
- **Context/Nuances**: `reference-vm.conf` version 2 runs headless (`-display none`) with the standard QEMU VGA. `qualify-install` drives the real guided installer, then boots the installed disk and logs in at tty1 through the QEMU monitor, proving the login with a serial marker. After `configure` the target boots into `graphical.target` with SDDM, and Arch's `sddm.service` declares `Conflicts=getty@tty1.service`, so the tty1 login proof stops working. Correction of the 02-15 SUMMARY: the user reports that the 02-15 human checkpoint required launching the laboratory VM with `--gl` (virtio-vga-gl with VirGL); without GL, Hyprland ran with CPU software rendering. A first proposal changed the reference VM to `virtio-vga` (version 3), added a non-gating greeter `screendump`, automated SDDM/Hyprland checks, and an automated rerun. The user judged the screenshot and graphical automation redundant with the human checkpoint and a waste of resources. The Epic 4 common contract only requires that a clean installation plus `configure` in the reference VM succeeds without manual steps, which `qualify-install` already exercises because the engine now runs `configure` inside the installation (DEC-025).
- **User Response**: Asked whether automating boot and screenshots was necessary; agreed with the reduced proposal.
- **Decision**: (1) `reference-vm.conf` does not change (version 2, standard VGA, `-display none`); there is no `screendump` and no automated graphical check. (2) The automated, gating proof of a clean installation plus `configure` without manual steps is `qualify-install` itself: every installing case expects `installed`/0 with the `configure` outcome 0 recorded in `engine-run.json`. (3) The existing disk-boot login proof moves from tty1 to tty2, because SDDM conflicts with `getty@tty1`; an SDDM failure on the standard VGA is irrelevant to that proof, and any interference with VT switching is a finding. (4) The human checkpoint, in the laboratory VM with `--gl`, installed from the new ISO with no manual code delivery, covers the complete graphical path, the rerun through `sudo mirroros-configure` without mutation, and the evidence. (5) The 02-15 finding is corrected: `--gl` was required, and without GL Hyprland renders on the CPU.
- **Status**: Accepted

## DEC-034
- **Question**: Which `qualify-install` cases cover `configure`, and what happens with the installation deadline?
- **Context/Nuances**: The installing cases (`default`, `limine-nohib`, `ext4`, `btrfs-rescue`) now always run `configure` because it is part of the installation. `failure` cuts the network at `install_packages`, before `configure`, and `cancel-password` never reaches the engine; neither changes. `REFERENCE_VM_INSTALL_DEADLINE_SECONDS=2700` is a `reference-vm.conf` value; `configure` adds downloads (Hyprland, SDDM with its xorg dependencies, fonts), and its duration was not measured in 02-15. Forcing a `configure` failure in the VM would require cutting the network right after the base postconditions, a fragile timing.
- **User Response**: Agreed with the recommendation.
- **Decision**: (1) No new VM case for `not_configured`; that path (record, outcome, D22 screen, interruption during the `configure` phase) is covered by engine and assistant Bats tests with doubles. (2) The four installing cases expect the `configure` outcome 0 in `engine-run.json` (DEC-033); the plan checkpoint runs `default` as mandatory and the others per the usual `docs/procedures/test.md` practice. (3) The deadline stays at 2700 s and `reference-vm.conf` is untouched (DEC-033); `qualify-install` evidence already records the duration. If a run exceeds the deadline, the task stops and raising the value is decided explicitly with that measurement, never speculatively.
- **Status**: Accepted

## DEC-035
- **Question**: The SDDM greeter keyboard selector displayed `??zz`, and the greeter password layout was never verified. How is this closed?
- **Context/Nuances**: Both the greeter and the session `hyprland.lua` load the shared `keyboard.lua`, which resolved `us`. Upstream SDDM issue #2149 reports `ZZ` instead of `US` with SDDM Wayland and Hyprland, which suggests a display-only problem but does not prove it. The 02-15 guest had `KEYMAP=us`, the default layout, so that run could not show whether the greeter really applies the system layout.
- **User Response**: Agreed with the recommendation, using `es` as the test keymap.
- **Decision**: (1) Functional verification in the human checkpoint, without anticipating a configuration change: the laboratory VM is installed with console keymap `es` and an account password containing a key whose position differs between `us` and `es` (for example `ñ`, or `-`, which `es` places where `us` has `/`); the checkpoint confirms that typing the password with the `es` layout logs in through the greeter and records what the selector displays. (2) If the login works, `??zz` is documented as cosmetic in the Hyprland provider notes of `capabilities/README.md`, citing SDDM #2149, and the configuration is unchanged. (3) If it fails, it is a defect that blocks closing Story 4.2 and is fixed in the greeter configuration under the Hyprland provider before the checkpoint is approved.
- **Status**: Accepted
