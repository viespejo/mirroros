# Story 2.1 — Installation Engine Research: Consolidated Plan

## Scope and sequencing

The Story 2.1 research umbrella is split into three plans in a new phase `02` (Epic 2). Grouping the tracks does not amend Story 2.1 acceptance criteria and does not authorize any architectural exception; the current baseline (UEFI, GPT, systemd-boot, unencrypted ext4, resizeable swapfile, no custom TUI, no project-owned Python) remains normative [DEC-001].

Plan 02-01 establishes the non-production `prototypes/` frame, including a record of the three tracks with their questions, stop conditions, and exclusions, and executes only Track 1: one shared fixed reference-VM scenario, the Archinstall JSON/CLI and native Arch-command prototypes, their comparison, and an engine ADR when the evidence is conclusive. It depends only on `01-05-reference-vm-bootstrap-validation` [DEC-001].

Storage/recovery (Btrfs/Snapper, rescue-based recovery versus Limine snapshot integration) follows in plan 02-02 on top of the selected engine, and a mock-data frontend demonstration may follow in plan 02-03; the frontend choice never determines the engine choice [DEC-001, TODO-001, TODO-002].

## Shared fixed scenario

The shared scenario is derived by walking the Arch Installation Guide section by section, from pre-installation through *Reboot*, plus the minimal post-installation needed to boot and log in (user, sudo, network). Every item is classified as fixed by architecture, personal preference, or technical necessity, and the comparison marks each item for Archinstall as expressible through JSON/CLI, requiring native finalization before reboot, or unsupported. Architecture-fixed items (UEFI, GPT, systemd-boot, unencrypted ext4 root, resizeable swapfile, official `linux` kernel) are recorded but not reopened; desktop, Niri, dotfiles, NVIDIA, CachyOS, and hibernation verification stay out of scope. This scenario serves the prototypes only and does not define production installation policy, which remains with Story 2.3 [DEC-003].

Localization: the target generates `en_US.UTF-8` and `es_ES.UTF-8`, sets `LANG=en_US.UTF-8` with no additional `LC_*` overrides, and uses console keymap `us` [DEC-002]. Graphical keyboard layouts are deferred to the desktop work [DEC-002, TODO-003].

Storage: the reference VM's 32 GiB disk uses GPT with only two partitions, a 1 GiB FAT32 ESP mounted at `/boot` so systemd-boot reads kernel and initramfs directly, and an ext4 root over the remaining space with default mount options; there is no separate `/home` or swap partition, and fstab is generated by UUID [DEC-004].

Swap and resume: a 4 GiB `/swapfile` on the ext4 root (sized to the reference VM's RAM) is created with `mkswap --size 4G --file /swapfile` and listed in fstab. The systemd-boot entry carries explicit `resume=UUID=<root>` and `resume_offset=<offset>` computed with `filefrag`, relying on the default systemd-based initramfs, and a pre-first-boot postcondition checks that both values match the real swapfile. For Archinstall, this is expected to be native finalization, and its zram swap must be disabled; that adaptation is part of the comparison. A real hibernation cycle is not required in this plan and may only appear as an optional non-blocking check [DEC-005].

Packages and repositories: both prototypes install exactly `base linux linux-firmware sudo neovim man-db man-pages` plus the network package, using the mirrorlist inherited from the live environment and recording it in their evidence so neither engine gains a network advantage. `base-devel` belongs to user-level `configure` work, CPU microcode to hardware adaptation, and `multilib` to whichever capability first requires it; none is part of the base scenario [DEC-006, TODO-004, TODO-005]. The user's former installer `viespejo/VARBS` (2021) informs personal habits but is not a template [DEC-006].

Networking: the installed system runs NetworkManager with its default Wi-Fi backend and DNS handling, and no predefined connections or copied live-environment profiles; the reference VM obtains its address by DHCP. After the first boot, a default route, DNS resolution of `archlinux.org`, and an HTTPS response must be observed. This item is expected to be expressible through Archinstall's `network_config`, pending prototype confirmation [DEC-007].

Time and identity: the installed system uses time zone `Europe/Madrid`, a UTC hardware clock set with `hwclock --systohc`, and an enabled `systemd-timesyncd`; the reference VM's hostname is `mirroros-ref`, with no `127.0.1.1` entry in `/etc/hosts` because `myhostname` resolves the local name. Postconditions check these values through `timedatectl` and `hostnamectl` [DEC-008].

Accounts and credentials: administration happens through `sudo`, and root is locked unless a root password is supplied at installation time [DEC-009, DEC-011]. The reference VM user `mirroros` belongs only to `wheel` and uses `bash`; a validated sudoers drop-in grants `%wheel ALL=(ALL:ALL) ALL` without the `NOPASSWD` or `!tty_tickets` relaxations used in VARBS. The password is a synthetic, disposable, per-run value delivered only through a protected channel and doubles as a canary that scanning must not find in any evidence or result. Postconditions cover the locked root, group membership, sudo access, sudoers validity, and a successful login. For Archinstall, the comparison records how its `--creds` file can be supplied and whether credentials leak into its logs or saved configuration [DEC-009].

Boot: `mkinitcpio` keeps its default systemd-based hooks and produces classic images; unified kernel images wait for the deferred Secure Boot decision. systemd-boot is installed with `bootctl install`, kept current by `systemd-boot-update.service`, and configured with a default Arch entry, `timeout 3`, and `editor no`, plus a fallback entry when the `linux` preset generates one. The kernel command line is `root=UUID=<root> rw resume=UUID=<root> resume_offset=<offset>` without `quiet`. Postconditions require a clean `bootctl status`, an existing default-entry payload on the ESP, a successful boot without the installation medium, and the expected `/proc/cmdline`; entries are compared by semantics rather than filenames because Archinstall names them differently [DEC-010].

On real targets, the username, user password, and an optional root password are entered at installation time through a protected channel, and an omitted root password leaves root locked; the scenario's values are prototype defaults. The fixed scenario supplies a synthetic per-run root password as a second canary, so a full run exercises two secrets, and checks that root login works; the omitted-root case is verified per engine at configuration/contract level rather than by a second full installation. The input interface itself belongs to Stories 2.3–2.5 [DEC-011].

System tweaks: `/etc/sysctl.d/90-sysrq.conf` sets `kernel.sysrq = 1` to keep full REISUB recovery, checked after the first boot; Archinstall offers no option for it, so it counts as native finalization [DEC-012].

`pacman.conf` enables `Color`, `ParallelDownloads = 5`, `VerbosePkgLists`, and `ILoveCandy`, verified through effective `pacman-conf` values, and `fstrim.timer` is enabled; cache cleanup through `paccache.timer` is left to `configure` because it needs `pacman-contrib`. Archinstall is expected to cover only parallel downloads, leaving the remaining options to native finalization [DEC-013].

## Prototype execution harness

Both prototypes share a prototype-owned harness in `prototypes/installation/lib/`, so the installation engine is the only difference between `archinstall-json-cli/run` and `native-arch/run`. The harness leaves `vm/reference/` untouched: it reads the VM shape from `reference-vm.conf` without changing it, copies and adapts the minimal launch logic instead of sourcing it, and defines its own installation deadlines, because the 300 s qualification deadline belongs to the 01-05 contract [DEC-014].

Every run uses two boots. The first boots the unmodified qualified bundle ISO (`archinstall 4.5-1`) with a fresh disk and a NoCloud medium that carries the engine script and synthetic secrets; it installs and powers off. The second boots the installed disk alone, where one systemd verification unit, identical for both engines and documented as known prototype contamination, checks the postconditions and reports run-id-bound JSON over the serial console. Host-side disk inspection was rejected because it would require host root [DEC-014].

Evidence is retained privately in `evidence/prototypes/installation/<engine>/<run-id>/`, allowlisted, scanned, and searched explicitly for both canary values. Only the temporary NoCloud medium in `build/` excludes the two canary values from its scan, and that exception is recorded; evidence scanning has none [DEC-014].

Interactive criteria are measured separately from the unattended runs. Full unattended runs, through a mode that exists only in the prototypes and sets no precedent for production, measure outcome, postconditions, exits, duration, and credentials. One attended observation session per engine, driven by a versioned checklist in the prototype README and run with the user over the serial console on a disposable disk, covers plan visibility and editability (Archinstall's reviewable `user_configuration.json` and menu; the native generated command script), confirmation (Archinstall with and without `--silent`; a minimal native typed confirmation without the digest binding reserved for Story 2.4), and cancellation both at confirmation, where the disk must stay untouched and the exit status is recorded, and through `SIGINT` during package installation, where a non-success exit, retained diagnostics, and the partial disk state are recorded. These results are labeled "observed manually" in the comparison [DEC-015].

Failure behavior is compared through one reproducible, host-safe injection run unattended in both engines: a NoCloud-delivered mirrorlist pointing to an unreachable server makes package installation fail. Each engine's result records engine and `run` exit statuses, preservation of the original pacman message, whether dependent steps continue, the partial disk state, and the absence of any success claim. Recovery evidence covers what the engine leaves for a retry and whether a fresh disk is needed; automatic retry is not tested because the architecture's destructive retry policy forbids it [DEC-016].

## Comparison and metrics

The comparison lives in `prototypes/installation/README.md`, while each prototype's `README.md` records its question, scenario, checklist, and result. It combines a scenario matrix, listing every DEC-002–DEC-013 item with its classification and its Archinstall status (JSON/CLI, native finalization, unsupported), with a table of the ten Story 2.1 criteria in which every cell states whether it was measured, observed manually, or source-reviewed, and cites its evidence run-id [DEC-017].

Maintenance cost is measured through the item counts per Archinstall class, the MirrorOS-owned lines of each prototype excluding the shared harness, the upstream configuration keys depended upon, upstream change exposure from source review pinned to exact revisions (Archinstall configuration-format breaks versus the stability of `pacstrap`, `arch-chroot`, `bootctl`, and `genfstab`), and the dependencies each path adds. Each engine gets two successful full unattended runs for a first repeatability signal, one failure-injection run, and one attended session, all against the same qualified bundle `20261005T190610Z-e22955f3-62e8-4985-86da-cd5d703659ab` [DEC-017].

## Decision checkpoint and stop conditions

The comparison ends in a checkpoint where the user decides and the agent only drafts. Conclusive evidence produces an Accepted `docs/adr/0002-installation-engine-selection.md` with question, evidence run-ids, trade-offs, selection, and the replacement boundary behind `install/engine/apply`, together with the `docs/architecture.md` updates that stop treating Archinstall as a candidate (and restate the ban on project-owned Python if Archinstall wins). `install/engine/apply` itself is left to Story 2.5. Inconclusive evidence produces no forced ADR: the comparison and the next required experiment are recorded, and Story 2.1 stays open [DEC-018].

Work stops on a path when Archinstall would need its Python API, a plugin, or project-owned Python (the item becomes unsupported, without workarounds); runs are recorded as `blocked_external` when the qualified bundle fails to boot or official mirrors fail persistently, without altering the VM or bundle; and any need to modify `vm/reference/`, `reference-vm.conf`, or production code halts work for consultation. The storage/recovery and frontend tracks are only registered in `prototypes/README.md` with their questions, stop conditions, and exclusions [DEC-018].

## Validation, documentation, and attribution

Prototype code receives `bash -n` and `shellcheck` with the repository configuration, but no Bats or contract suites: tests arrive with the production implementation after the ADR. The canary search, whose silent failure would hide a leak, is proven once through a recorded negative control. Boundary checks confirm that no production path sources or imports `prototypes/`, that no `*.py` file exists, and that `vm/reference/` and `reference-vm.conf` are unchanged, and redacted Gitleaks scans cover history, working tree, `build/`, and the new evidence without exceptions [DEC-019].

The `docs/architecture.md` project tree gains `prototypes/installation/README.md` and `prototypes/installation/lib/`, and per-prototype `results/` directories give way to `evidence/prototypes/installation/<engine>/<run-id>/`. The repository validation procedure stays untouched, and the harness README clarifies that the canary exclusion is limited to the temporary NoCloud scan. Attribution does not change; external references are pinned [DEC-019].

## Commits and traceability

A first commit introduces the `prototypes/` frame and three-track register, the harness, both prototypes, and the architecture tree update. Counted runs execute from that commit with a clean tree and record the commit and `dirty` state; dirty development runs may help but never count. A second commit adds the comparison READMEs and, at the checkpoint, ADR 0002 and the architecture update when the evidence is conclusive. A prototype defect found during counted runs is fixed in a new commit after consulting the user, and that engine's counted runs are repeated so all its evidence references one commit [DEC-020].
