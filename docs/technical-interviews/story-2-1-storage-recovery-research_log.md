## DEC-002
- **Question**: How is mandatory MVP hibernation handled across the three variants?
- **Context/Nuances**: Plan 02-01 verified only that the boot entry's `resume_offset` matched the swapfile; a real cycle was out of scope. On Btrfs the swapfile needs a dedicated NOCOW subvolume that is never snapshotted (an active swapfile cannot live in a snapshotted subvolume), and its offset is computed with `btrfs inspect-internal map-swapfile -r` instead of `filefrag`. Subvolumes have no size; they share the filesystem's space and can only be limited through qgroups, which Snapper can use for space-aware cleanup at a known performance cost (layout and qgroups are decided later). Btrfs snapshots are not recursive, so rolling back `@` does not touch a separate swap subvolume. The real risk is modifying a filesystem offline while a hibernation image is pending (a rescue-based rollback, or booting a snapshot read-write), then resuming an image that assumes the old on-disk state; this risk also applies to the ext4 control repaired from rescue media. A real hibernation cycle under QEMU/OVMF is expected to work but is not yet proven in the harness. Rejected alternatives: (a) configuration-level postcondition only, which does not measure the main coupling; (c) making the real cycle a blocking adoption condition, which lets a VM result gate a decision the architecture already treats as insufficient for real hardware.
- **User Response**: Chose option (b); asked whether subvolumes define sizes and whether rollback only affects snapshotted subvolumes, not the swap subvolume.
- **Decision**: Every variant has a configuration-level postcondition: `resume=UUID` and `resume_offset` match the real swapfile (on Btrfs, computed with `btrfs inspect-internal map-swapfile -r`, with the swapfile in a dedicated NOCOW subvolume excluded from snapshots). Every variant, including the control, also gets one real hibernate-and-resume cycle in the reference VM as a measured criterion. One observed case per variant (all three) records what happens when recovery is attempted (rescue-based rollback, or Limine snapshot boot) while a hibernation image is pending. Safeguard: if the VM cannot hibernate reliably even with the control, the criterion is recorded as `blocked_external` rather than as a variant failure. The ADR states that target-laptop hibernation requires its own validation.
- **Status**: Accepted

## DEC-003
- **Question**: Which subvolume layout and quota policy do both Btrfs variants share?
- **Context/Nuances**: The two Btrfs variants should differ only in their recovery mechanism, so they share one layout. The layout decides what a rollback reverts and what survives it. A flat layout keeps `@snapshots` outside `@`, so `@` can be replaced from rescue media, and matches what Limine snapshot tooling expects. Keeping `/var/lib/pacman` inside `@` makes the package database roll back together with the files it describes. Rejected alternatives: Snapper's default nested layout (`.snapshots` inside `@`), which complicates rescue-based rollback; qgroups, which carry a known performance cost and known issues with many snapshots. Mount options were proposed as defaults, but the user reopened compression, so mount options are decided separately (DEC-004).
- **User Response**: Accepted the recommendation; asked about Btrfs compression.
- **Decision**: Partitions as in the control: a 1 GiB FAT32 ESP and a Btrfs filesystem over the remaining space. Flat subvolume layout: `@` → `/` (snapshotted and rolled back; includes `/var/lib/pacman`), `@home` → `/home` (user data not reverted by system rollback), `@log` → `/var/log` (diagnostics survive rollback), `@pkg` → `/var/cache/pacman/pkg` (package cache kept out of snapshots), `@snapshots` → `/.snapshots` (outside `@`), `@swap` → `/swap` (NOCOW, never snapshotted, holds `/swap/swapfile`, DEC-002). Subvolumes have no size limits; qgroups are disabled and Snapper cleanup uses number limits (`NUMBER_LIMIT`), not space-aware limits.
- **Status**: Accepted

## DEC-004
- **Question**: Do the Btrfs variants use transparent compression, and with which mount options?
- **Context/Nuances**: `zstd:1` reduces the space of system files and the package cache, reduces SSD writes, often speeds up I/O, and costs little CPU; Btrfs skips incompressible data (e.g. `.pkg.tar.zst`), and Fedora uses `zstd:1` by default. NOCOW disables compression, so the swapfile stays uncompressed, which is correct for hibernation. Only data written after mounting with the option is compressed, so it must be active before `pacstrap`. `compress-force` is discouraged. Compression does not affect recovery; applied equally to both Btrfs variants it does not separate them, and it only shows against the ext4 control in secondary metrics. If Btrfs is adopted it would be adopted with compression, so the evaluated configuration matches the one that would be used. `noatime` is common with snapshots, but its benefit over `relatime` is marginal and would add a variable.
- **User Response**: Asked whether compression should be used because it is reputed to be good; accepted the recommendation.
- **Decision**: Both Btrfs variants mount every subvolume with `compress=zstd:1` from installation time (before `pacstrap`), with no effect on NOCOW `@swap`; `relatime` is kept as in the control; `compress-force` and `noatime` are not used. Secondary metrics recorded for all three variants: space used after installation (`compsize` on Btrfs, `df` on ext4) and installation duration. They are informative and do not decide the ADR on their own.
- **Status**: Accepted

## DEC-005
- **Question**: When and how are snapshots created in both Btrfs variants?
- **Context/Nuances**: Recovery needs a known-good snapshot taken before the damage. Both Btrfs variants share the creation policy and differ only in how they return to it (rescue media or Limine). `snapper` and `snap-pac` come from the official `extra` repository, so they raise no provenance issue. User data is covered by the mandatory external backup. Rejected alternatives: hourly timeline snapshots (noise and space without system-recovery value); manual snapshots only (unrealistic and dependent on memory); snapshots of `@home` (not system recovery, overlaps the external backup).
- **User Response**: Accepted the recommendation.
- **Decision**: One Snapper configuration, `root`, for `@` only; no other subvolume is snapshotted. `snap-pac` creates pre/post snapshots around every pacman transaction. The installation ends with an initial `post-install baseline` snapshot. Timeline snapshots are disabled (`TIMELINE_CREATE="no"`). Cleanup by number: `NUMBER_LIMIT=10` with `snapper-cleanup.timer` enabled and no quotas (DEC-003). No `ALLOW_USERS`; snapshots are managed through `sudo`.
- **Status**: Accepted

## DEC-006
- **Question**: How is Limine integrated with snapshots in the third variant?
- **Context/Nuances**: `limine` is in the official `extra` repository. The usual tools that generate per-snapshot boot entries (`limine-snapper-sync`, `limine-mkinitcpio-hook`) are believed to come from the AUR; this is to be confirmed by pinned source review as the first related task. The architecture treats AUR packages as explicitly reviewed external sources and lists Chaotic-AUR and the CachyOS repository among deferred decisions. Limine cannot read Btrfs, so kernels live on the ESP; booting an old snapshot with the current kernel breaks the match with the snapshot's `/usr/lib/modules`, which the tools solve by copying each snapshot's kernel and initramfs to the ESP, putting pressure on the 1 GiB ESP. Rejected alternatives: (b) a MirrorOS-owned Bash generator of Limine snapshot entries, which evaluates something nobody proposes to adopt and adds owned code; (c) the CachyOS repository or Chaotic-AUR, which the architecture defers.
- **User Response**: Accepted option (a) with the proposed nuances.
- **Decision**: The Limine variant uses the AUR integration tools pinned to exact commits and reviewed, built inside the prototype with `makepkg` as an unprivileged user (`base-devel` and `git` only in this variant). The comparison records the commits, the review, and the provenance cost. Stop condition: if the tools require the CachyOS repository or Chaotic-AUR, or cannot be pinned, the variant is marked unsupported with no workaround. The ESP stays at 1 GiB as in the control; its occupancy with N snapshots is measured and a shortfall is recorded as a finding, not fixed on the fly. Secure Boot stays deferred; Limine is installed unsigned. If an ADR adopted this variant, AUR provenance would follow Story 3.2.
- **Status**: Accepted

## DEC-007
- **Question**: Which damage is injected to compare recovery across the three variants?
- **Context/Nuances**: Damage must be reproducible, host-safe, applicable to ext4 and Btrfs alike, and go through pacman so `snap-pac` snapshots naturally. The ESP is outside snapshots in every variant: rolling back `@` restores `/usr/lib/modules` but not the kernel and initramfs on `/boot`, while the Limine tooling keeps a per-snapshot copy, which is where the variants are expected to differ. Expected outcomes (hypotheses, not conclusions): the control repairs D1 and D2 from rescue media (chroot, remove the package, or `mkinitcpio -P`); Btrfs with rescue rolls back D1 but still needs initramfs regeneration for D2; Limine fixes both by booting the previous snapshot. Rejected alternatives: D1 only (hides the ESP difference); deleting files without pacman (`snap-pac` does not act, unrealistic); corrupting Btrfs itself (a backup case, not a rollback case).
- **User Response**: Accepted the recommendation.
- **Decision**: Two damages, each delivered as a synthetic local package installed with `pacman -U` (no network; built by the prototype and recorded in evidence). D1, userspace damage inside `@`: the package installs configuration that prevents reaching login (for example an fstab or systemd drop-in that forces emergency mode). D2, boot damage on the ESP: the package's post-install hook makes the `/boot` initramfs unusable (for example by truncating it), causing a kernel panic. Measured per variant and damage: recovery success (the 02-01 verification unit passes the relevant postconditions again), recovery steps and duration, whether rescue media is required, whether failure diagnostics survive (`@log` on Btrfs, `/var/log` on ext4), and whether a marker file written to `/home` after the baseline survives.
- **Status**: Accepted

## DEC-008
- **Question**: How are installations, damage, and recoveries executed (unattended versus attended), and how many runs are counted?
- **Context/Nuances**: The 02-01 harness provides two-boot installation, NoCloud delivery, and run-id-bound JSON reports over serial. Rescue-based recovery can be automated by booting the qualified ISO with a NoCloud medium carrying the recovery script, which is also the candidate documented procedure. Limine recovery requires choosing a boot-menu entry; automating it would need QEMU monitor keystrokes (fragile) or configuration edits (no longer measuring the real path). The matrix is 3 variants × 2 damages = 6 cases, plus each variant's hibernation cycle and pending-hibernation case (DEC-002). Engine repeatability was already shown in 02-01; here the variable is recovery. Rejected alternatives: fully attended runs (about six long sessions, less reproducible); automating the Limine menu with `sendkey` (fragile and misleading); two counted runs per case (doubles cost without new signal).
- **User Response**: Accepted the recommendation.
- **Decision**: One counted unattended run per variant and damage: install, baseline, write the `/home` marker, inject D1 or D2, confirm the system actually fails, recover, and verify again. For the control and Btrfs with rescue, recovery is automated too (a third boot from the ISO with the recovery script over NoCloud, then a fourth boot from disk with verification). For Limine, everything is automated except the menu selection, a short attended step over the serial console recorded as "observed manually". The real hibernation cycle is automated for all three variants (`systemctl hibernate`, then a boot from disk verifying resume). The pending-hibernation recovery case is one attended session per variant. A case with an unexpected or inconsistent result is repeated once before it is recorded. Evidence lives in `evidence/prototypes/storage/<variant>/<run-id>/` under the 02-01 rules (0700/0600, commit and `dirty`, allowlist, canary search, Gitleaks).
- **Status**: Accepted

## DEC-010
- **Question**: How do the Btrfs variants reuse `verify-postconditions.sh`, given that DEC-009 assumed it runs unchanged? (Amends DEC-009.)
- **Context/Nuances**: `verify-postconditions.sh` hardcodes the ext4 root (line 116), `/swapfile` and its `filefrag` offset (lines 80, 120–144), and `bootctl`, `loader.conf`, and `systemd-boot-update` (lines 164–201). On Btrfs several checks would fail, and with Limine the whole `boot_*` group would. Rejected alternatives: running it unchanged and filtering expected failures afterwards (hides real failures among expected ones); copying and adapting it (drift between copies).
- **User Response**: Accepted the correction.
- **Decision**: `verify-postconditions.sh` gains a backward-compatible parameter that excludes check groups (`storage_*`, `swap_*`, `boot_*`), defaulting to no exclusions so 02-01 behavior is preserved; the DEC-009 `native-arch` regression run covers it. The control runs it in full. The Btrfs variants exclude `storage_*` and `swap_*`, and the Limine variant also excludes `boot_*`; the storage check script takes over the excluded groups with equivalents: Btrfs root and subvolumes, fstab by UUID with `subvol=`, active `/swap/swapfile` with the `map-swapfile` offset, and for Limine its configuration, snapshot entries, and a command line with `rootflags=subvol=@`, `resume`, and `resume_offset`. The JSON report lists which groups were excluded and which checks replaced them, so no postcondition disappears silently.
- **Status**: Accepted
